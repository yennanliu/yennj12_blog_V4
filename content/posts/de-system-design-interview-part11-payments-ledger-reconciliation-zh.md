> 多數人遇到金融題，第一反應是把它當成「資料量比較小的點擊流」。  
> 然後在第一個追問就卡住：「上個月已經交給稽核的報表，今天重跑數字不一樣了，為什麼？」  
> 支付資料平台的難處不在每秒幾筆，而在**每一分錢都要說得出來歷，而且去年說過的話今年還要能原樣重說一遍**。  
> 這一題考的是你會不會把「不可變、可對帳、可重現」當成設計的起點。

[Part 10](/posts/de-system-design-interview-part10-mock-interview-scenarios-zh/) 用電商點擊流示範了完整的 45 分鐘。從本篇開始的五篇各換一個產業，用同一套六步框架走一遍，重點放在**該產業特有的限制、面試官的追問，以及候選人怎麼說明取捨**。本篇是支付業：資料量不大，但錯一筆就是真的錢。

---

## 面試情境

> **面試官**：「我們是一家支付服務商，每天處理約 5,000 萬筆交易。財務團隊需要三樣東西：每天與收單銀行的清算檔對帳、每天產出商戶的結算報表，以及能應付稽核的歷史資料。請設計這個資料平台。」

---

## 一、這一題在考什麼

把它和 Part 10 的點擊流放在一起比較，就能看出評分重點完全不同。

| 面向 | 點擊流 | 支付 |
|---|---|---|
| 一筆資料的價值 | 極低，掉 0.1% 可接受 | 每一筆都是錢，掉一筆就是事故 |
| 重複的後果 | 指標略為膨脹 | 商戶被多扣或多付 |
| 修正錯誤的方式 | 重算分區覆寫 | 不能覆寫，只能用反向分錄沖銷 |
| 歷史資料 | 重算後以新數字為準 | 已關帳的數字必須能原樣重現 |
| 外部對照 | 沒有 | 銀行與卡組織有另一份帳，兩邊要對得上 |
| 規模難度 | 高 | 低 |

所以這一題的三個主軸是：**不可變的帳本**、**與外部帳的對帳**、**時間旅行式的可重現**。如果候選人把大部分時間花在討論 Kafka 分區數，就是答錯方向。

## 二、0–10 分鐘：釐清與估算

> **候選人**：「我先確認幾件事。交易的來源系統是什麼？是一個帳本資料庫，還是多個服務各自記錄？」
>
> **面試官**：「有一個核心帳本服務，後面是 PostgreSQL。每筆交易會寫成數筆分錄。」
>
> **候選人**：「所以帳本資料庫是事實來源，資料平台是它的下游，不負責即時餘額或授權決策，對嗎？」
>
> **面試官**：「對，線上的餘額查詢不在這題的範圍。」
>
> **候選人**：「清算檔是怎麼來的？格式、頻率、會不會重送或更正？」
>
> **面試官**：「每家收單銀行每天透過 SFTP 送一到數個 CSV 檔。會晚到，偶爾會送更正檔。」
>
> **候選人**：「對帳的結果誰在用？發現不一致之後的流程是什麼？」
>
> **面試官**：「財務營運團隊每天早上處理差異。他們希望 9 點前看到昨天的對帳結果。」
>
> **候選人**：「資料要保留多久？已經產出的報表之後會不會被要求重現？」
>
> **面試官**：「依法規保留七年。稽核會抽查任一天的報表，要求我們重現當時的數字。」
>
> **候選人**：「最後，交易在事後還會變動嗎？例如退款、爭議款。」
>
> **面試官**：「會。退款通常幾天內，持卡人爭議可能在幾個月後才進來。」

**評註**：候選人第二個問題就劃清了範圍（不負責線上餘額），避免後面被拉去設計交易系統。「清算檔會不會重送或更正」與「報表會不會被要求重現」這兩個問題，直接問出了本題最難的兩個需求。

估算（假設每筆交易平均產生 4 筆分錄、每筆分錄約 300 bytes、尖峰為平均的 5 倍）：

```
transactions/day   = 50,000,000
ledger entries/day = 50M × 4                 = 200,000,000
avg txn/s          = 50M / 86,400            ≈ 580 /s
peak txn/s         = 580 × 5                 ≈ 2,900 /s
raw size/day       = 200M × 300 B            = 60 GB
Parquet/day        = 60 GB / 6 (assumed)     ≈ 10 GB
7 years            = 10 GB × 2,555           ≈ 26 TB
```

> **候選人**：「七年大約 26 TB，每天 10 GB，尖峰不到每秒三千筆。這個規模用單一叢集的批次作業就能處理，所以我不會把複雜度花在吞吐量上。設計的重點會是三件事：分錄不可變、與清算檔對得上、任何一天的報表都能重現。」

**評註**：候選人用估算**排除**了一個方向，並說出接下來的重點。這比算出數字本身更有價值。

## 三、10–15 分鐘：資料契約

> **候選人**：「我想先確認帳本分錄的結構，因為後面所有的檢查都建立在它上面。」

```
entry_id        string     -- 全域唯一，(txn_id, entry_seq) 也唯一
txn_id          string     -- 交易識別；一筆交易的所有分錄共用
idempotency_key string     -- 上游呼叫端提供，防止同一請求被記兩次
account_id      string     -- 商戶帳、手續費帳、待清算帳 ...
direction       string     -- DEBIT / CREDIT
amount_minor    long       -- 以最小貨幣單位表示的整數（分），不用浮點數
currency        string     -- ISO 4217
effective_at    timestamp  -- 業務上生效的時間
recorded_at     timestamp  -- 寫入帳本的時間
reverses_entry  string     -- 若為沖銷分錄，指向被沖銷的那一筆
external_ref    string     -- 收單銀行的參考號，對帳用
```

> **候選人**：「四個重點。第一，金額用整數的最小單位存，加上幣別；浮點數加總一億筆之後會出現對不上的尾差。第二，分錄只追加、不更新；錯了就寫一筆方向相反的分錄去沖銷，並用 `reverses_entry` 指回原分錄。第三，每筆交易的借方合計必須等於貸方合計，這是我之後的第一道品質檢查。第四，時間有兩個：`effective_at` 是業務時間，`recorded_at` 是我們得知的時間，重現歷史報表要靠後者。」
>
> **面試官**：「卡號呢？」
>
> **候選人**：「完整卡號不應該進入資料平台。它在支付閘道就應該被代碼化，帳本與下游只看到代碼與末四碼。這樣資料湖就不在卡片資料的合規範圍內，稽核範圍小很多。」

**評註**：`amount_minor` 用整數、借貸平衡、只追加並以沖銷修正——這三點是金融資料的基本功，沒提到其中任何一項都是明顯的失分。

## 四、15–25 分鐘：架構與三個演進階段

```
╔══════════════════════════════════════════════════════════════════════╗
║  Phase 1  Nightly export + manual matching (early stage)             ║
╚══════════════════════════════════════════════════════════════════════╝

┌──────────────┐ nightly dump ┌──────────────┐      ┌────────────────┐
│ Ledger DB    │─────────────▶│ Warehouse    │─────▶│ Finance ops:   │
│ replica      │              │ tables       │      │ SQL + sheets   │
└──────────────┘              └──────┬───────┘      └────────────────┘
┌──────────────┐  manual load        │
│ Bank files   │─────────────────────┘
└──────────────┘
```

**可行的範圍**：每天數十萬筆交易、一兩家銀行。**失效的原因**：比對邏輯在試算表裡，無法稽核也無法重跑；清算檔重送時沒有人知道哪一版被用過。

```
╔══════════════════════════════════════════════════════════════════════╗
║  Phase 2  Immutable lake + automated reconciliation (target)         ║
╚══════════════════════════════════════════════════════════════════════╝

┌───────────┐  CDC   ┌──────────────────┐   ┌───────────────────────┐
│ Ledger DB │───────▶│ Bronze: entries  │──▶│ Silver: ledger        │
└───────────┘        │ append-only      │   │ invariants checked    │
                     └──────────────────┘   └──────────┬────────────┘
┌───────────┐ SFTP   ┌──────────────────┐              │
│ Bank      │───────▶│ Bronze: files    │──┐           │
│ files     │        │ raw + hash + ver │  │           ▼
└───────────┘        └──────────────────┘  │  ┌───────────────────┐
                     ┌──────────────────┐  └─▶│ Matching job      │
                     │ Silver: parsed   │────▶│ by external_ref   │
                     │ settlement lines │     └────────┬──────────┘
                     └──────────────────┘              ▼
          ┌───────────────────────┐          ┌───────────────────┐
          │ Gold: merchant        │◀─────────│ recon_result      │
          │ settlement report     │          │ + open breaks     │
          └───────────────────────┘          └───────────────────┘
```

> **候選人**：「目標設計的四個要點。一，帳本用 CDC 同步到只追加的 Bronze，不是每晚全量匯出，因為我需要每一筆分錄的寫入紀錄。二，銀行檔案原樣保存，連同檔案雜湊與版本，解析後的結果是另一層。三，比對是一個可重跑的批次作業，輸出每一筆的比對狀態。四，所有 Silver 與 Gold 表在發佈前都要通過不變量檢查，沒過就不發佈，下游繼續看到前一天的結果。」

| | Phase 1 | Phase 2 | Phase 3 |
|---|---|---|---|
| 帳本同步 | 每晚匯出 | CDC，只追加 | CDC，小時級增量 |
| 清算檔 | 人工載入 | 自動擷取，含雜湊與版本 | 加上檔案到達的 SLA 監控 |
| 比對 | 試算表 | 每日自動比對 | 日內多次增量比對 |
| 可重現性 | 無 | 依 `recorded_at` 重現 | 加上會計期間鎖定與調整分錄 |
| 稽核 | 無 | 每筆結果可追到來源分錄與檔案列 | 完整血緣與存取紀錄 |

## 五、深挖一：對帳到底怎麼比

> **面試官**：「說明一下比對作業的邏輯。」
>
> **候選人**：「最簡單的情況是一對一：我們的一筆交易對應清算檔的一列，用 `external_ref` 做全外連接，結果分成五類。」

| 狀態 | 意義 | 後續 |
|---|---|---|
| `MATCHED` | 兩邊都有，金額與幣別一致 | 無 |
| `AMOUNT_MISMATCH` | 兩邊都有，金額不同 | 人工調查；常見原因是手續費或匯率 |
| `MISSING_EXTERNAL` | 我們有，銀行沒有 | 可能只是時間差，先等待 |
| `MISSING_INTERNAL` | 銀行有，我們沒有 | 最嚴重，可能是漏記或重複請款 |
| `DUPLICATE` | 同一參考號在任一邊出現多次 | 調查重送或重複入帳 |

> **候選人**：「有兩個實務上的複雜度要處理。
>
> 第一是**時間差**。銀行的日切時間和我們不同，而且可能在不同時區。我們在 23:50 記的一筆交易，可能出現在銀行隔天的檔案裡。所以 `MISSING_EXTERNAL` 不能立刻當成異常：我會讓它保持『待配對』並在接下來幾天的檔案中繼續尋找，超過約定天數（例如三個營業日）才升級成需要處理的差異。每筆差異都要記錄已存在幾天。
>
> 第二是**多對一**。銀行實際撥款常常是一筆總額，對應我們幾千筆交易扣掉手續費後的淨額。這時要做兩層比對：先用明細檔逐筆對交易，再把明細加總後與撥款金額核對。」
>
> **面試官**：「金額差一分錢算不算一致？」
>
> **候選人**：「逐筆比對我不設容忍值，差一分就是 `AMOUNT_MISMATCH`，因為分錄是整數，沒有四捨五入的理由。只有牽涉匯率換算的彙總層比對，才依合約設定明確的容忍範圍，而且容忍掉的差額本身要記成一筆分錄，不能消失。」

**評註**：候選人主動提出時間差與多對一，這兩個是真實對帳系統中差異的最大來源。「容忍掉的差額也要入帳」顯示理解帳本的基本原則：錢不會憑空出現或消失。

> **面試官**：「怎麼確認比對作業本身沒有漏掉東西？」
>
> **候選人**：「比對完成後有三個守恆檢查。兩邊的輸入筆數，各自要等於五種狀態的筆數合計，沒有任何一列在連接中消失。兩邊的輸入金額合計，要等於各狀態的金額合計。另外，Silver 帳本本身的借方合計等於貸方合計。這些檢查沒過，結果就不發佈。筆數與金額合計只是粗篩，但在這裡它們檢查的是作業有沒有弄丟資料列，逐筆的正確性則由比對本身負責。」

## 六、深挖二：清算檔重送、晚到與更正

> **面試官**：「銀行昨天的檔案今天早上又送了一次，內容有三列不一樣。」
>
> **候選人**：「我把檔案當成不可變的版本來管理。每個收到的檔案都原樣存進 Bronze，並記錄內容雜湊、收到時間，以及它宣稱涵蓋的清算日期。同一個清算日期的第二個檔案：如果雜湊相同，是單純的重送，直接忽略；如果雜湊不同，就是新版本，登記為該日期的版本 2。
>
> 比對作業永遠使用每個清算日期的最新版本，並且記錄它用的是哪一版。新版本到達會觸發該清算日期的比對重跑。因為比對是『輸入版本 → 輸出分區』的純函數，重跑是安全的。
>
> 重跑後有些交易的狀態會改變，例如從 `MISSING_EXTERNAL` 變成 `MATCHED`。我會保留前一次的結果作為歷史，讓財務營運看得到『這三筆是因為更正檔才配對上的』。」
>
> **面試官**：「檔案到 9 點都沒來呢？」
>
> **候選人**：「檔案到達本身要有監控：每家銀行有預期到達時間，超過就告警。9 點的報表照常產出，但該銀行的部分標示為『清算檔未到』而不是顯示成一整批 `MISSING_EXTERNAL`。把『還沒資料』和『資料不一致』混在一起，會讓營運團隊每天花時間排除假警報，最後開始忽略告警。」

**評註**：以內容雜湊區分重送與更正、把檔案版本當成比對作業的輸入，這延續了 [Part 2](/posts/de-system-design-interview-part2-batch-pipeline-ingestion-zh/) 的可重跑原則。最後一段區分「未到」與「不一致」，是營運意識的訊號。

## 七、深挖三：關帳之後數字還能重現嗎

> **面試官**：「稽核要你重現三月底交出去的月報。但四月的時候，有幾筆三月的交易被持卡人爭議並退款了。你重跑三月的報表會得到什麼？」
>
> **候選人**：「這取決於問的是哪一個問題，而兩個問題都合理。
>
> 一個是『以我們**現在**所知，三月發生了什麼』；另一個是『以我們在**三月底當時**所知，三月發生了什麼』。稽核要的是後者。只有一個時間欄位的資料模型無法區分這兩者，這就是我在契約中保留兩個時間的原因。」

```
                 effective_at (when it happened in the business)
                      March                    April
                 ┌─────────────────────┬─────────────────────┐
 recorded_at     │  entry A  +100      │                     │
 March           │  (sale, Mar 12)     │                     │
                 ├─────────────────────┼─────────────────────┤
 recorded_at     │                     │  entry B  −100      │
 April           │                     │  (chargeback,       │
                 │                     │   reverses A)       │
                 └─────────────────────┴─────────────────────┘

 March report as known on Mar 31:  recorded_at <= Mar 31   ->  +100
 March report as known today:      still +100; the −100 belongs to April
```

> **候選人**：「我的做法有三個部分。
>
> 一，**修正永遠記在當期**。四月才知道的退款，是一筆 `effective_at` 與 `recorded_at` 都在四月的沖銷分錄，並指回三月的原分錄。三月的分錄不會被改動，所以三月的合計不變。
>
> 二，**重現用 `recorded_at` 篩選**。要重現三月底交出去的報表，就只讀 `recorded_at` 不晚於當時關帳時間點的分錄。因為分錄只追加，這個查詢永遠得到相同的結果。
>
> 三，**關帳是一個明確的動作**。每個會計期間關帳時，我記錄關帳時間點與當時的輸出雜湊。之後任何人重跑，都可以驗證得到相同的雜湊。」
>
> **面試官**：「為什麼不直接用 table format 的時間旅行？」
>
> **候選人**：「時間旅行靠的是保留舊快照，而快照會因為儲存成本與維護作業而過期，通常只留幾天到幾週。要保證七年後還能重現，不能依賴基礎設施剛好還留著舊檔案；資料模型本身要帶有『何時得知』這個維度。時間旅行我會用在短期的操作上，例如昨天的作業寫錯了要回復。」

**評註**：這是本題最能區分資歷的一段。候選人先釐清問題有兩種解讀，再說明資料模型如何同時支援兩者，最後解釋為何不用看似更簡單的方案——並給出那個方案適用的範圍。

---

## 八、為什麼選 X 不選 Y

| 選擇 | 選 X 的理由 | 不選 Y 的理由 | 翻轉條件 |
|---|---|---|---|
| 只追加 + 沖銷分錄 vs 更新原資料列 | 歷史不可竄改、已關帳的數字不變、每次修正都有紀錄 | 更新後無法說明「當時的數字為何是那樣」 | 非財務的衍生資料（例如儀表板用的聚合表）可以覆寫 |
| 整數最小單位 vs 浮點數或小數字串 | 加總無誤差、比較可用等號 | 浮點數累加產生尾差，逐筆比對會出現假差異 | 匯率與費率本身需要小數，用定點小數型別並明訂進位規則 |
| CDC vs 每晚全量匯出 | 取得每一筆分錄的寫入事件與時間；來源負載低 | 全量快照看不到兩次匯出之間發生過什麼 | 帳本本身已是只追加且有可靠的 `recorded_at`，以它做增量即可，不一定需要 CDC |
| 雙時間欄位 vs 依賴快照時間旅行 | 七年後仍可重現；不受快照過期影響 | 快照保留期通常只有幾天到幾週 | 只需要短期回復（數日內），時間旅行就夠 |
| 檔案版本化 vs 以最新檔覆蓋 | 知道每次比對用的是哪一版；更正的影響可追溯 | 覆蓋後無法解釋昨天的結果為何與今天不同 | 無，金融資料的外部輸入一律保留原件 |
| 逐筆零容忍 vs 設定金額容忍值 | 整數金額沒有合理的誤差來源，差異即問題 | 容忍值會掩蓋系統性的小額錯誤 | 涉及匯率換算的彙總層比對，依合約設定並將差額入帳 |
| 每日批次比對 vs 即時串流比對 | 清算檔本身是每日批次，即時比對沒有對象 | 串流引入狀態與晚到的複雜度，卻不會更早拿到銀行資料 | 對方提供即時通知（例如逐筆的清算事件流）且營運需要日內處理 |
| 檢查未過則不發佈 vs 先發佈再修正 | 財務報表「晚」可以解釋，「錯」不行 | 錯誤數字一旦被引用，更正成本遠高於延遲 | 內部探索用的非正式資料 |

## 九、常見追問與回答要點

面試官在這類題目中常用的追問，以及回答時應該帶到的重點。

**「同一筆交易被記了兩次怎麼辦？」**
分三層防線。來源端以 `idempotency_key` 防止同一請求重複入帳；同步層以 `entry_id` 去重，CDC 重送不會產生重複資料列；檢查層驗證 `(txn_id, entry_seq)` 唯一。若三層都沒擋住，對帳會出現 `MISSING_EXTERNAL`（我們多記了一筆），這也是對帳存在的意義。

**「多幣別怎麼處理？」**
每筆分錄保留原幣別金額。換算成報表幣別時，同時記錄使用的匯率、匯率來源與時間，換算結果另存欄位。對帳一律用原幣別比對；用換算後的金額比對會把匯率差異誤判成交易差異。

**「七年保留和使用者要求刪除個資衝突時？」**
財務紀錄的法定保留義務通常優先於刪除請求，但只限於履行該義務所需的欄位，具體範圍要由法遵確認。設計上把個資（姓名、聯絡方式）與帳務資料分開存放，帳本只留代碼；刪除請求處理個資那一側，帳務紀錄保留到期滿。

**「報表需要比 T+1 更即時呢？」**
商戶想看當日交易量屬於營運指標，可以從 CDC 流做近即時的聚合，並標明是「未對帳的暫定數字」。正式的結算金額仍然只來自通過對帳的批次結果。這與 [Part 3](/posts/de-system-design-interview-part3-streaming-realtime-zh/) 的暫定值與最終值是同一個模式。

**「怎麼測試這條管線？」**
三種測試。以已知答案的合成資料驗證比對邏輯的每一種狀態；以不變量（借貸平衡、筆數守恆、金額守恆）作為每次執行的執行期檢查；新版邏輯上線前與舊版雙軌執行數日，比較兩者輸出的差異。

**「爭議款幾個月後才來，對帳怎麼算？」**
它是一筆新的交易事件，有自己的參考號，會出現在當期的清算檔中，並在當期比對。它透過 `reverses_entry` 連回原交易，所以可以從原交易查到完整的生命週期，但不會回頭改動原交易當時的比對結果。

## 十、系統效應與系列導航

從 Phase 1 到 Phase 2 的前後對照。標示為目標的數字是設計目標，不是量測值。

| 指標 | 改造前（每晚匯出 + 人工比對） | 改造後（不可變資料湖 + 自動對帳） |
|---|---|---|
| 對帳完成時間 | 當日下午，視人力而定 | 每日 9:00 前（目標） |
| 自動配對比例 | 無 | 絕大多數交易自動配對，人工只處理差異 |
| 清算檔重送的處理 | 人工判斷，容易重複計入 | 以雜湊辨識，版本化後自動重跑 |
| 重現任一日的報表 | 無法保證 | 以 `recorded_at` 篩選，結果可用雜湊驗證 |
| 差異的可追溯性 | 試算表中的註記 | 每筆結果連回分錄與檔案列，含存在天數 |
| 錯誤資料流入報表 | 可能 | 不變量檢查未過則不發佈 |
| 新增的維運工作 | 無 | CDC、檔案到達監控、關帳流程、檢查規則維護 |

**本篇重點**

- 金融題先用估算排除吞吐量方向，把時間留給正確性、對帳與可重現。
- 分錄只追加、以沖銷修正；金額用整數最小單位；每筆交易借貸平衡是第一道檢查。
- 對帳的結果是每筆交易的狀態；時間差與多對一是差異的主要來源，「未到」與「不一致」要分開呈現。
- 外部檔案保留原件並版本化，比對作業記錄所用的版本。
- 用業務時間與記錄時間兩個維度，讓已關帳的數字在多年後仍可重現。
