> 多數人把即時系統的難題理解成「怎麼算得夠快」。  
> 實際上每秒一萬筆事件，一台筆電就算得完。  
> 難的是事件會**亂序到達、重複到達、晚十分鐘才到達**，而作業隨時可能重啟——在這些條件下數字還要對。  
> 串流面試考的是正確性，延遲只是你為正確性付出代價時的限制條件。

這是系列的第三篇。[Part 2](/posts/de-system-design-interview-part2-batch-pipeline-ingestion-zh/) 的批次管線處理的是「有界」的資料：一天的分區有頭有尾，錯了可以整個重算。串流處理的是**無界**資料，沒有「算完」的那一刻。本篇說明這個差異帶來的四個問題——順序、重複、時間、狀態——以及面試中該怎麼回答。

---

## 面試情境

> **面試官**：「我們是外送平台，每天約 3,000 萬張訂單。營運團隊需要一個即時儀表板，顯示每個城市每分鐘的訂單數與成交金額（GMV），資料延遲要在 10 秒內。另外財務會拿儀表板的日合計去比對隔天的帳，兩邊必須一致。請設計這個系統。」

注意題目裡藏了兩個互相拉扯的要求：**10 秒內**與**必須一致**。

---

## 一、核心問題：無界資料的四個麻煩

先算規模。假設每張訂單在生命週期中產生約 8 個狀態事件、每個事件 1 KB、用餐尖峰是平均的 5 倍：

```
orders/day      = 30,000,000
events/day      = 30M × 8                 = 240,000,000
avg events/s    = 240M / 86,400           ≈ 2,800 /s
peak events/s   = 2,800 × 5               ≈ 14,000 /s
peak ingress    = 14,000 × 1 KB           ≈ 14 MB/s
```

題目中的兩個指標要先定義口徑，否則「去重」沒有意義：一張訂單有 8 個狀態事件，不能每個事件都算一次。這裡約定**訂單數與 GMV 只在訂單進入「已付款」狀態時計入一次**（以 `order_id` 為準）；取消與退款以負值沖銷，計入沖銷發生的那一分鐘。批次路徑使用同一份定義。

14 MB/s 並不大。這個數字本身就是一個該說出口的結論：**這題的難度不在吞吐量，而在正確性**。把時間花在設計上百節點的叢集，是答錯方向。

無界資料帶來批次不會遇到的四個麻煩：

| 麻煩 | 批次為什麼沒有 | 串流中的後果 |
|---|---|---|
| 順序 | 整批到齊後可以排序 | 「已取消」比「已建立」先到 |
| 重複 | 重跑時整個分區覆寫 | 重試或重啟後同一事件被算兩次 |
| 時間 | 資料到齊才開始算 | 12:00 的事件 12:07 才到，那一分鐘的結果早已送出 |
| 狀態 | 作業結束就釋放 | 計數器要永遠活著，重啟後還得記得算到哪 |

後面每一節各處理其中一個。

## 二、三個演進階段

```
╔══════════════════════════════════════════════════════════════════════╗
║  Phase 1  Polling the replica (POC, a few cities)                    ║
╚══════════════════════════════════════════════════════════════════════╝

┌───────────────┐  SELECT city, COUNT(*), SUM(amount)  ┌─────────────┐
│ Orders DB     │  ... GROUP BY city, minute           │ Dashboard   │
│ read replica  │◀─────────────────────────────────────│ every 60 s  │
└───────────────┘                                      └─────────────┘
```

**作法**：儀表板每分鐘對唯讀副本下一次聚合查詢。

**優點**：零新元件；數字直接來自交易資料庫，天生與帳一致。

**何時失效**：新鮮度是 60 秒加上副本延遲，達不到 10 秒；查詢範圍一大就拖慢副本；每多一個儀表板使用者就多一份查詢負載。訂單量在每天數十萬張以下時，這其實是合理的答案，值得先提出再說明為何不夠。

```
╔══════════════════════════════════════════════════════════════════════╗
║  Phase 2  Stream aggregation (MVP)                                   ║
╚══════════════════════════════════════════════════════════════════════╝

┌──────────┐  CDC   ┌─────────────┐      ┌─────────────────┐
│ Orders DB│───────▶│ Kafka       │─────▶│ Flink           │
└──────────┘        │ key=order_id│      │ dedup + 1-min   │
                    │ 12 parts    │      │ event-time      │
                    └─────────────┘      │ window by city  │
                                         └────────┬────────┘
                                                  │ upsert (city, minute)
                                                  ▼
┌─────────────┐   query, p99 < 100 ms    ┌─────────────────┐
│ Dashboard   │◀─────────────────────────│ Serving store   │
└─────────────┘                          │ (ClickHouse)    │
                                         └─────────────────┘
```

**新增元件**：變更擷取、可重播的佇列、有狀態的串流引擎、服務層儲存。

**解決**：新鮮度降到數秒；讀取負載離開交易資料庫；多個下游可以各自消費同一個事件流。

**仍存在的問題**：晚到事件怎麼算入日合計？串流作業的邏輯有 bug 時怎麼修正歷史數字？這兩個問題決定了財務對帳能不能過。

```
╔══════════════════════════════════════════════════════════════════════╗
║  Phase 3  Stream + batch reconciliation (scale, finance-grade)       ║
╚══════════════════════════════════════════════════════════════════════╝

                      ┌─────────────┐  speed path   ┌───────────────┐
                 ┌───▶│ Flink       │──────────────▶│ Serving store │
┌──────────┐     │    └─────────────┘  provisional  │               │
│ Kafka    │─────┤                                  │ minute rows:  │
│ retain 7d│     │    ┌─────────────┐  batch path   │ status =      │
└──────────┘     └───▶│ S3 raw      │──────────────▶│ provisional / │
                      │ + nightly   │  final rows   │ final         │
                      │ Spark job   │  win on read  └───────────────┘
                      └─────────────┘
```

**新增元件**：原始事件歸檔、每晚的批次重算、資料列上的「暫定／最終」標記。

**解決**：儀表板 10 秒內看到暫定值；隔天批次用完整資料產生最終值，日合計與帳一致。兩個互相拉扯的需求由兩條路徑分別滿足。

兩個要講清楚的細節。第一，**最終值不能被暫定值蓋回去**：串流在批次發佈後仍可能因晚到事件或故障重播而再次寫入同一個 `(city, minute)`，所以兩條路徑寫入各自的資料列（或以條件寫入拒絕覆蓋 `final`），查詢時最終值優先。第二，**批次要有明確的截止點**：例如隔日 02:00 以當時已到達的資料產生最終值，並與交易系統的日結數字比對；截止後才到的事件與退款調整，靠例行重算最近幾天的分區來修正，修正前後的差異要留下記錄。

**代價**：同一份邏輯存在於串流與批次兩處，要確保兩邊定義一致。第七節會討論這個代價以及何時可以不付。

## 三、Kafka 基本功：分區、順序與容量

**直覺**：Kafka 是一本只能往後寫的帳簿，分成很多冊（partition）。每個讀者自己記得讀到第幾頁（offset），所以多個讀者互不干擾，而且可以翻回去重讀。

這個「可重讀」的特性是它與傳統訊息佇列的關鍵差別。傳統佇列把訊息交給消費者後就刪除；Kafka 依保留期限留著（預設 7 天），讓新的下游可以從頭消費，也讓出錯的作業可以倒帶重算。

面試中要說清楚的三個設計決定：

**決定一：用什麼當 key。** Kafka 只保證**同一個分區內**有序。key 相同的訊息會進同一個分區，所以 key 的選擇等於在決定「哪些事件之間必須有序」。

| key 選擇 | 保證 | 風險 |
|---|---|---|
| `order_id` | 同一張訂單的事件依寫入 Kafka 的順序被消費 | 分佈均勻，幾乎無傾斜 |
| `city_id` | 同一城市的所有事件有序 | 大城市的分區成為熱點 |
| 無 key（輪流分配） | 無順序保證 | 「已取消」可能先於「已建立」被處理 |

本題選 `order_id`：訂單狀態機需要有序，而依城市聚合是下游引擎的工作，不該用分區 key 來做。要補一句前提：Kafka 保證的是**寫入順序**，不是業務發生的順序。來源是 CDC 時，寫入順序就是資料庫的提交順序，兩者一致；若事件由多個服務各自送出，就要在事件中帶上每張訂單遞增的版本號，由下游丟棄過期版本。

**決定二：幾個分區。** 分區數決定消費端的最大平行度（一個消費者群組內，一個分區同時只被一個消費者讀取）。估算方式：

```
needed by throughput = 14 MB/s peak / ~10 MB/s per partition  ≈ 2
needed by parallelism = target consumer parallelism           = 8
headroom for growth (×1.5)                                    → 12
```

`~10 MB/s per partition` 是保守的經驗值，實際上限取決於硬體與訊息大小。分區數可以增加但**不能減少**，而且增加後同一個 key 會對應到不同分區、破壞既有的順序保證，所以一開始留一些餘裕比事後擴充便宜。但也不要一次開到上千個：每個分區都有檔案控制代碼、複寫與 leader 選舉的成本。

**決定三：耐久性設定。** 三副本、`acks=all`、`min.insync.replicas=2`。意思是訊息寫入至少兩個副本才算成功，容許一台 broker 掛掉而不丟資料，也不中斷寫入。

在 AWS 上的選擇是 MSK（受管 Kafka）或 Kinesis Data Streams。Kinesis 省去叢集維運，以 shard 為單位（每個 shard 寫入 1 MB/s 或 1,000 筆/秒）；本題尖峰 14,000 筆/秒至少需要 14 個 shard。需要 Kafka 生態（Connect、Debezium、既有工具）時選 MSK，團隊小且想要最少維運時選 Kinesis。

## 四、交付語意與 Exactly-Once

[Part 1](/posts/de-system-design-interview-part1-framework-fundamentals-zh/) 說過 exactly-once 的實務意義是「重複處理也不影響結果」。在串流中要把這句話落實到整條鏈的三段：

```
   (1) produce            (2) process               (3) sink
┌──────────┐  retry?  ┌──────────────────┐  retry?  ┌──────────────┐
│ Producer │─────────▶│ Kafka → Flink    │─────────▶│ Serving store│
└──────────┘          │ state + offset   │          └──────────────┘
                      └──────────────────┘
 dup on resend         dup on restart from          dup on re-emit
 fix: idempotent       last checkpoint              fix: upsert by key
 producer              fix: checkpoint state        or 2-phase commit
                       and offset together
```

**第一段：寫入 Kafka。** 生產者送出後沒收到確認就會重送，可能造成重複。冪等生產者（idempotent producer）替每則訊息附上序號，broker 看到重複序號就丟棄。Kafka 3.0 起這是預設行為。

**第二段：處理。** 引擎重啟後會從上一次記錄的 offset 重新讀取，那之後處理過的事件會再處理一次。Flink 的做法是**檢查點（checkpoint）**：定期把「讀到的 offset」與「當下的狀態（計數器）」作為同一個一致的快照存到 S3。重啟時兩者一起回到快照那一刻，所以重讀的事件會被加到**還沒加過它們**的計數器上，結果不會重複。

關鍵在於 offset 與狀態必須一起存。若恢復後 offset 回到較早的位置、狀態卻停在較新的值，重讀的事件會被重複計入；反過來，offset 已前進而狀態回到舊值，中間那段事件就漏算了。

**第三段：寫出。** 從檢查點恢復後，引擎會重新送出恢復點之後的結果，下游會收到重複的輸出。兩種解法：

| 解法 | 作法 | 取捨 |
|---|---|---|
| 冪等寫入 | 以 `(city, minute)` 為鍵 upsert，重送只是覆寫同一筆 | 簡單、延遲低；需要 sink 支援 upsert |
| 兩階段提交 | 輸出先寫成未提交，檢查點完成時才一起提交 | 適用於無法 upsert 的 sink（如寫到另一個 Kafka topic）；下游要等到提交才看得到，延遲等於檢查點間隔 |

本題的聚合結果有天然的鍵 `(city, minute)`，所以選冪等寫入。這是面試中很好的一句話：「我不需要端到端交易，因為輸出本身可以設計成冪等的。」

還有一種重複上面三段都擋不住：**來源本身就送了兩次**。例如應用程式逾時後重新送出同一個事件，對 Kafka 而言是兩則不同的訊息。這只能靠業務鍵去重——在引擎中以 `event_id` 為鍵保留一段時間的狀態（例如 24 小時），看過就丟棄。

## 五、Event Time、Watermark 與視窗

### 5.1 兩種時間

- **事件時間（event time）**：事件實際發生的時間，寫在事件裡。
- **處理時間（processing time）**：引擎處理到它的時間。

用處理時間最簡單，但結果會隨系統狀況改變：Kafka 壅塞五分鐘後一次湧入的事件，會全部被算到「現在這一分鐘」，儀表板上出現一根假的尖峰。重播歷史資料時更糟，一整天的訂單會被算進同一分鐘。**凡是結果需要可重現的，都必須用事件時間。**

### 5.2 Watermark

用事件時間就要面對一個問題：12:00–12:01 這個視窗什麼時候算「收齊」了？事件可能晚到，引擎不能永遠等下去。

**直覺**：watermark 是引擎的一句聲明——「我認為時間戳早於 T 的事件都已經到了」。它隨著看到的事件時間往前推進，推過視窗的結束時間時，視窗就關閉並輸出結果。

**機制**：最常用的策略是容許固定的亂序程度：`watermark = 目前看過的最大事件時間 − 容許延遲`。

```
allowed out-of-orderness = 5 s          window [12:00:00, 12:01:00)

arrival order ──────────────────────────────────────────────────────▶
event time   12:00:58   12:01:02   12:00:59   12:01:06   12:00:57
max seen     12:00:58   12:01:02   12:01:02   12:01:06   12:01:06
watermark    12:00:53   12:00:57   12:00:57   12:01:01   12:01:01
                                      │           │          │
                                      │           │          └─ LATE:
                                 in window   watermark passes   window
                                 (accepted)  12:01:00 -> FIRE   closed
```

第三個事件（12:00:59）雖然亂序到達，但 watermark 還沒過 12:01:00，所以正常計入。第五個事件（12:00:57）到達時視窗已關閉，成為**晚到資料**。

容許延遲是一個直接的取捨：**設得越大，結果越完整，但輸出越晚**。本題要求 10 秒內看到資料，容許延遲就不可能設成 5 分鐘。

### 5.3 晚到資料的三種處理

| 處理方式 | 作法 | 適用 |
|---|---|---|
| 丟棄 | 視窗關閉後到的事件直接忽略，並計數 | 只看趨勢的監控 |
| 更新已輸出的結果 | 視窗關閉後再保留一段時間（allowed lateness），晚到事件觸發重新輸出 | 下游可 upsert 時；本題的速度路徑 |
| 導到旁路 | 寫入另一個輸出，交給批次處理 | 需要完整正確的對帳；本題的批次路徑 |

本題的組合：watermark 容許 5 秒亂序，視窗關閉後保留 10 分鐘接受更新（upsert 覆寫同一筆），更晚的由隔夜批次補上。**無論選哪一種，都要把晚到筆數做成指標**——它是容許延遲設得對不對的唯一依據。

為了滿足 10 秒的新鮮度，視窗不必等到關閉才輸出。可以設定每 5 秒輸出一次目前的累計值，儀表板上「當前這一分鐘」的數字會持續跳動，視窗關閉時成為定值。

### 5.4 視窗類型

| 類型 | 定義 | 例子 |
|---|---|---|
| 滾動（tumbling） | 固定長度、不重疊 | 每分鐘訂單數 |
| 滑動（sliding） | 固定長度、每隔一段滑動、互相重疊 | 過去 5 分鐘的訂單數，每分鐘更新 |
| 工作階段（session） | 以閒置間隔切分，長度不固定 | 使用者一次瀏覽行為（30 分鐘無動作即結束） |

一個常被追問的陷阱：**watermark 是所有輸入分區中最小的那個**。某個分區沒有流量（例如深夜的小城市剛好雜湊到同一個分區），它的 watermark 不前進，就會卡住整個作業的視窗輸出。症狀是「有資料進來但沒有結果輸出」。解法是設定閒置逾時，讓沒資料的分區暫時不參與 watermark 計算。

## 六、狀態、背壓與串流 Join

### 6.1 狀態

串流作業的「記憶」稱為狀態：視窗內的累計值、去重用的 `event_id` 集合、join 時等待配對的事件。狀態有三個面試重點。

**狀態大小要估算。** 去重狀態保留 24 小時的 `event_id`：2.4 億個鍵，每個鍵連同額外負擔約 100 bytes，大約 24 GB。這已經超過一般 JVM 堆積的舒適範圍，所以要用存在本地磁碟的狀態後端（RocksDB），並開啟增量檢查點，每次只上傳變動的部分。

**狀態必須有過期時間（TTL）。** 沒設定 TTL 的狀態只增不減，作業會在上線幾週後因磁碟或檢查點過大而失敗。每一個有狀態的運算都要回答「這份狀態什麼時候可以丟」。

**狀態跟著 key 走。** 依 `city_id` 分組聚合時，大城市的 key 會讓某個平行實例特別忙——Part 1 的傾斜問題在串流中重現。本題的緩解方法是兩階段聚合：先依 `(city_id, order_id % 16)` 做局部聚合，再依 `city_id` 合併。

### 6.2 背壓與消費延遲

當下游處理速度跟不上上游，壓力會一路往回傳，稱為**背壓（backpressure）**。在以 Kafka 為來源的系統中，它最終表現為**消費延遲（consumer lag）**：最新 offset 與消費者已讀 offset 的差距。

消費延遲是串流系統最重要的單一指標，因為它直接反映資料新鮮度的損失。把筆數除以**輸入速率**，可以估計目前的結果落後多久：

```
lag (records) / input rate (records/s) ≈ how far behind, in seconds

lag = 840,000 records, input at 14,000/s  ->  ~60 s behind  (SLA is 10 s)
```

更直接的量法是**最舊一筆尚未處理事件的年齡**（現在時間減去它的事件時間），告警應該設在這個值上。

延遲持續上升時的診斷順序：先看是不是流量尖峰（輸入速率上升）；再看哪個運算元在背壓（通常是 sink 寫入太慢或某個 key 傾斜）；最後才考慮增加平行度。直接加機器而不找瓶頸，在傾斜的情況下完全沒有效果。

### 6.3 串流 Join

本題需要把訂單事件與「餐廳屬於哪個城市」關聯。串流中的 join 依對象分三種：

| 類型 | 情境 | 作法 | 注意 |
|---|---|---|---|
| 串流 × 串流 | 訂單事件 join 付款事件 | 兩邊各保留一段時間的狀態，在時間區間內配對 | 區間越長狀態越大；超過區間的配對會遺失 |
| 串流 × 緩慢變動的表 | 訂單 join 餐廳資料 | 把維度表的 CDC 流載入成狀態，依事件時間查詢當時的版本 | 維度表要放得進狀態 |
| 串流 × 外部查詢 | 訂單 join 需要即時查的服務 | 非同步呼叫外部儲存並加上本地快取 | 外部系統成為延遲與可用性的瓶頸 |

餐廳資料量小（數十萬筆）且變動不頻繁，適合第二種：把餐廳表的變更流廣播到每個平行實例作為狀態，join 完全在本地完成，沒有網路呼叫。

## 七、Lambda、Kappa 與服務層

### 7.1 兩種架構

**Lambda 架構**同時維護兩條路徑：串流路徑快但可能不完整，批次路徑慢但完整，服務層合併兩者。第二節的 Phase 3 就是這個形狀。

**Kappa 架構**只有串流一條路徑。需要重算時，啟動新版作業從佇列的起點重播所有歷史事件，追上後切換過去。

| | Lambda | Kappa |
|---|---|---|
| 程式路徑 | 兩套（串流 + 批次） | 一套 |
| 修正歷史資料 | 重跑批次 | 重播事件流 |
| 主要風險 | 兩套邏輯逐漸不一致 | 重播大量歷史很慢；佇列要保留足夠久 |
| 適合 | 需要與外部帳務精確對齊；晚到資料多 | 邏輯單純、事件保留期夠長、容許重播時間 |

本題選 Lambda 的理由是具體的：財務要求日合計與帳一致，而晚到事件與退款調整可能在隔天才出現，批次路徑能看到完整資料。**如果題目沒有對帳要求，Kappa 加上 upsert 式的晚到更新就夠了**，而且少維護一套程式。

降低 Lambda 雙重邏輯風險的做法：把聚合定義寫成同一份 SQL，分別在串流引擎與批次引擎上執行；並每天比對兩條路徑的結果差異，差異超過門檻（例如 0.1%）就告警。

### 7.2 服務層怎麼選

儀表板查詢的形狀決定服務層。本題是「依城市與時間範圍讀取已聚合的資料列」。

| 選項 | 查詢能力 | 延遲 | 適合 |
|---|---|---|---|
| 鍵值儲存（DynamoDB、Redis） | 只能依鍵查，無法臨時切分維度 | 個位數毫秒 | 維度固定、查詢模式已知 |
| 即時 OLAP（ClickHouse、Druid、Pinot） | 任意維度過濾與聚合 | 數十到數百毫秒 | 儀表板需要下鑽、切換維度 |
| 資料倉儲（Redshift） | 完整 SQL | 秒級；高並行時成本高 | 新鮮度要求在分鐘級以上 |

維度只有城市時，預先聚合後寫入 DynamoDB 最便宜也最快。一旦營運開始要求「再依餐廳類型、配送方式切分」，預先聚合的組合數會爆炸，這時改用即時 OLAP 儲存較細粒度的資料並在查詢時聚合。面試中把這個翻轉條件說出來即可，不需要一開始就選最重的方案。

## 八、為什麼選 X 不選 Y

| 選擇 | 選 X 的理由 | 不選 Y 的理由 | 翻轉條件 |
|---|---|---|---|
| Kafka／Kinesis vs 傳統訊息佇列（SQS、RabbitMQ） | 可重播、多個消費者群組獨立消費、分區內有序 | 傳統佇列消費後即刪除，無法倒帶重算 | 工作佇列型任務：每則訊息只需被處理一次、不需順序與重播 |
| Flink vs Spark Structured Streaming | 逐筆處理、事件時間與狀態的支援最完整、延遲可到次秒 | 微批次的延遲通常在秒級，複雜的事件時間邏輯較受限 | 團隊已有 Spark 技能與批次程式、延遲要求在數秒到分鐘級 |
| 事件時間 vs 處理時間 | 結果可重現，重播與壅塞不影響數字 | 處理時間的結果取決於系統當下的狀況 | 純粹監控系統本身的吞吐量，或事件沒有可信的時間戳 |
| 冪等 upsert sink vs 兩階段提交 | 延遲低、實作簡單 | 兩階段提交讓可見延遲等於檢查點間隔 | sink 無法依鍵覆寫，例如輸出到另一個 Kafka topic 供計費使用 |
| key 用 `order_id` vs `city_id` | 分佈均勻，保住訂單狀態順序 | `city_id` 造成大城市分區熱點 | 下游必須以城市為單位嚴格依序處理 |
| Lambda vs Kappa | 批次路徑能納入晚到與調整，與帳務對齊 | 單靠串流難以保證與隔日帳完全一致 | 無對帳需求、事件保留期足夠重播、邏輯單純 |
| 預先聚合到鍵值儲存 vs 即時 OLAP | 維度固定時最便宜、延遲最低 | OLAP 叢集多一套系統要維運 | 需要多維度下鑽或臨時查詢 |

## 九、症狀到診斷

串流系統的問題很少以「作業失敗」的形式出現，多半是數字悄悄變得不對。面試官若問「上線後你怎麼知道它是健康的」，可以用這張表回答。

| 症狀 | 先看的訊號 | 常見原因 | 處置 |
|---|---|---|---|
| 儀表板資料越來越舊 | 消費延遲持續上升 | 流量超過處理能力；sink 寫入變慢；單一 key 傾斜 | 找出背壓的運算元；批次化 sink 寫入；兩階段聚合 |
| 有輸入但沒有輸出 | watermark 停止前進 | 某個來源分區閒置 | 設定閒置逾時 |
| 重啟後數字暴增 | 重啟前後同一視窗的值不同 | sink 非冪等；或從較早的 offset 重讀但狀態未還原 | 改為依鍵 upsert；確認由檢查點恢復 |
| 日合計比帳少 | 晚到丟棄計數偏高 | 容許延遲太短；用戶端離線後補送 | 延長更新保留期；由批次路徑補齊 |
| 檢查點越來越慢，最後逾時 | 檢查點大小與耗時的趨勢 | 狀態無 TTL 持續成長；背壓使檢查點訊號傳不下去 | 設定狀態 TTL；開啟增量檢查點；先解決背壓 |
| 某一分鐘出現假尖峰 | 事件時間與處理時間的差距 | 用了處理時間，上游壅塞後集中到達 | 改用事件時間 |

應該設告警的最小指標集合：消費延遲（換算成秒）、watermark 與現實時間的差距、檢查點耗時與失敗次數、晚到丟棄筆數、串流與批次日合計的差異比例。

## 十、系統效應與系列導航

以情境為例，從輪詢副本（Phase 1）到串流加批次對帳（Phase 3）的變化。

| 指標 | 改造前（每分鐘輪詢副本） | 改造後（串流 + 批次對帳） |
|---|---|---|
| 資料新鮮度 | 60–90 秒 | 5–10 秒（暫定值） |
| 儀表板查詢對交易資料庫的負載 | 隨使用者數線性增加 | 零 |
| 作業重啟後重複計數 | 不適用 | 無（檢查點 + 依鍵 upsert） |
| 晚到事件 | 下一次輪詢自然納入 | 10 分鐘內更新；更晚由批次補上 |
| 日合計與帳務的差異 | 0（同一資料來源） | 隔日最終值 0；當日暫定值 < 0.1%（目標值） |
| 邏輯出錯後修正歷史 | 不需要（每次現算） | 從 S3 原始事件重跑批次 |
| 需要維運的元件 | 0 | 5（CDC、Kafka、Flink、服務層、批次作業） |

改造前的那一欄在正確性上其實不差。這是值得在面試結尾說出來的判斷：**串流換到的是新鮮度與對交易資料庫的解耦，付出的是正確性從免費變成要靠設計爭取**。

**本篇重點**

- 先算規模：多數即時題的吞吐量不大，難度在順序、重複、時間與狀態。
- Kafka 的 key 決定哪些事件有序；分區數決定平行度，只能加不能減。
- exactly-once 要三段都處理：冪等生產者、狀態與 offset 一起做檢查點、冪等或交易式的 sink。
- 用事件時間與 watermark 取得可重現的結果；容許延遲是完整性與新鮮度的交換。
- 「快」與「準」衝突時，用暫定值加最終值兩條路徑分別滿足。
