> 多數人聽到「設計一個資料平台」，三十秒內就在白板上畫出 Kafka → Spark → S3。  
> 面試官記下的卻是：「沒問資料量、沒問誰在查、沒問多新鮮才算夠。」  
> DE 系統設計考的不是你認得幾個方框，而是你能不能**從查詢模式與資料量倒推出每個方框為什麼在那裡**。  
> 先問、再算、後畫——順序對了，後面四十分鐘才有東西可以深挖。

這個系列共五篇，寫給準備 Data Engineer（DE）系統設計面試的人。Part 1 給你兩樣東西：一套每題都能套用的**六步答題框架**，以及後面四篇會反覆用到的**資料系統基本功**。讀完你應該能在面試前十分鐘把題目收斂成「幾個數字加一組取捨」，而不是一張工具清單。

## 面試情境

> **面試官**：「我們的 App 每天產生約 5 億筆使用者行為事件。產品團隊想看每日漏斗報表，資料科學家想撈原始事件訓練模型，營運想要一個近即時的儀表板。請你設計支撐這三種需求的資料平台。你會先問我什麼？」

最後那句才是題目。本文用這個情境貫穿全文。

## 一、DE 系統設計在考什麼

DE 的系統設計和後端工程師（SWE）的系統設計共用同一套分散式基本功，但**評分重點不同**。SWE 題的主角是一個請求的生命週期；DE 題的主角是**一筆資料從產生到被查詢的生命週期**，而且它會被重跑、被修正、被晚到的資料推翻。

| 面向 | SWE 系統設計 | DE 系統設計 |
|---|---|---|
| 主要單位 | 請求（request） | 資料集、分區、事件 |
| 延遲指標 | p99 回應時間（ms） | 資料新鮮度（秒 / 分 / T+1）與查詢時間 |
| 正確性 | 單次交易的一致性 | 可重跑、去重、對得上帳 |
| 失敗後 | 重試該請求 | 重跑某一天、回補（backfill）三個月 |
| 成本主體 | 運算節點 | 儲存量 + 掃描量 |
| 介面契約 | API schema | 資料 schema 及其演進 |

面試官通常在四個維度上打分：

1. **需求收斂**：你有沒有把模糊題目變成可量化的目標。
2. **取捨判斷**：每個選擇有沒有說出「放棄了什麼、什麼條件下會改選」。
3. **正確性意識**：重複、亂序、晚到、重跑，你主動提了幾個。
4. **營運意識**：怎麼知道它壞了、壞了之後怎麼修、一個月要花多少錢。

注意這四項沒有一項是「認得多少工具」。工具名稱是你說明取捨時順帶出現的東西。

## 二、六步答題框架

45 分鐘的面試建議這樣分配。時間是參考值，重點是**前兩步不能省**，因為後面每個決定都要回頭引用它們。

```
┌──────────────────────────────────────────────────────────────────────┐
│ 1 Clarify  │ 2 Estimate │ 3 Contract │ 4 Design │ 5 Deep dive │ 6 Ops │
│   5 min    │   5 min    │   5 min    │  10 min  │   15 min    │ 5 min │
└─────┬──────┴─────┬──────┴─────┬──────┴────┬─────┴──────┬──────┴───┬───┘
      │            │            │           │            │          │
      ▼            ▼            ▼           ▼            ▼          ▼
  who queries  events/s     schema,     boxes and    2-3 hard    failure,
  how fresh    GB/day       keys,       arrows,      problems    backfill,
  how correct  TB/year      grain       one path     in depth    cost, SLA
```

**步驟 1：釐清需求（Clarify）。** 把問題分成五類來問，每類一到兩個問題就夠：

| 類別 | 要問的問題 | 答案會決定什麼 |
|---|---|---|
| 消費者 | 誰在查？分析師、模型、還是線上服務？ | 服務層用什麼引擎 |
| 新鮮度 | 資料多久內要能查到？秒、分鐘、還是隔天？ | 批次還是串流 |
| 正確性 | 數字拿來做什麼？看趨勢還是算錢？ | 要不要 exactly-once 與對帳 |
| 規模 | 每天幾筆、每筆多大、尖峰是平均的幾倍？ | 分區數、叢集大小、成本 |
| 保留與合規 | 資料留多久？有沒有個資、要不要能刪除？ | 儲存分層與治理設計 |

以本文情境為例，問完之後題目會從「設計資料平台」變成三條明確的路：漏斗報表 T+1 即可、原始事件要保留 13 個月供訓練、儀表板要求 1 分鐘內新鮮但允許 1% 誤差。**三種新鮮度意味著你不需要讓整個平台都跑串流**——這是第一個可以講出來的取捨。

**步驟 2：估算（Estimate）。** 算四個數字，見下一節。

**步驟 3：資料契約（Contract）。** 這一步是 DE 特有的，也最常被跳過。在畫架構之前先寫下：事件長什麼樣子、唯一鍵是什麼、用哪個時間欄位、最細的粒度（grain）是什麼。

```
event_id      string   -- 用戶端產生的 UUID，去重的依據
user_id       string
event_type    string   -- page_view / add_to_cart / purchase
event_time    timestamp -- 事件發生時間（用戶端），分析以它為準
ingest_time   timestamp -- 伺服器收到時間，用來衡量延遲與晚到
properties    map<string,string>
```

寫出 `event_id` 與兩個時間欄位，你就已經替後面的去重與晚到資料處理鋪好了路，面試官會看到你知道問題在哪裡。

**步驟 4：高階設計（Design）。** 先畫一條最簡單、能動的路徑，再加東西。每加一個元件就說一句它解決哪個需求。

**步驟 5：深挖（Deep dive）。** 面試官通常會挑兩到三個點往下問。如果他沒挑，你自己挑最有風險的：資料傾斜、重複、晚到、回補。

**步驟 6：營運（Ops）。** 監控什麼指標、失敗怎麼恢復、成本大約多少、下一個瓶頸在哪。

## 三、容量估算：四個必算的數字

估算的目的不是精確，而是**把數量級定下來**，讓後面的選擇有依據。算四個就夠：每秒事件數、每日資料量、一年儲存量、每月大約多少錢。

以情境的 5 億筆事件／天為例，假設每筆 JSON 約 1 KB、尖峰是平均的 4 倍：

```
events/day        = 500,000,000
avg events/s      = 500M / 86,400            ≈ 5,800 /s
peak events/s     = 5,800 × 4                ≈ 23,000 /s
raw bytes/day     = 500M × 1 KB              = 500 GB/day
peak ingress      = 23,000 × 1 KB            ≈ 23 MB/s

columnar on disk  = 500 GB / 6 (assumption)  ≈ 85 GB/day
13 months         = 85 GB × 395              ≈ 34 TB
S3 Standard       = 34,000 GB × $0.023       ≈ $780 / month
```

幾個要說出口的假設：

- **壓縮比 6 倍**是把 JSON 轉成 Parquet + 壓縮後的常見範圍（約 5–10 倍），實際值取決於欄位重複度，要用真實資料量一次。
- **$0.023/GB-月**是 S3 Standard 在 us-east-1 前 50 TB 的牌價；面試中說「每 GB 每月兩分多美元」就夠。
- **尖峰倍數**要問，電商大促可能是 10 倍以上。

這些數字立刻能導出結論：

| 數字 | 導出的判斷 |
|---|---|
| 尖峰 23 MB/s | 一台機器的網路就能接住，但需要多個分區來平行消費與容錯；Kinesis 每個 shard 寫入上限是 1 MB/s 或 1,000 筆/秒，所以至少 23 個 shard，留餘裕取 32–48 |
| 85 GB/天 | 每日批次處理是「幾十個核心、幾十分鐘」的量級，不需要上百節點的叢集 |
| 34 TB | 儲存費每月數百美元，**不是成本主體**；主體會是查詢掃描量與運算 |
| 全表掃描一次 | 以 Athena 每掃描 1 TB 收 $5 計，掃完 34 TB 一次約 $170——這就是為什麼分區設計值得花時間 |

最後一列是很好的面試語句：「儲存便宜、掃描貴，所以我的設計重點會放在讓查詢少掃資料。」

## 四、OLTP、OLAP 與列式儲存

**直覺**：OLTP（線上交易處理）像櫃檯，一次處理一位客人的一張單；OLAP（線上分析處理）像月底盤點，一次看過所有單子但只在意其中幾欄。兩種工作對儲存的要求相反。

| | OLTP | OLAP |
|---|---|---|
| 典型查詢 | 依主鍵讀寫一筆 | 掃描上億筆、聚合少數欄位 |
| 儲存佈局 | 列式存放（row-oriented） | 欄式存放（column-oriented） |
| 延遲目標 | 個位數毫秒 | 秒到分鐘 |
| 並行量 | 數千到數萬 QPS | 數十到數百個查詢 |
| AWS 代表 | Aurora、RDS、DynamoDB | Redshift、Athena、EMR |

**機制**：差別在同一張表的位元組在磁碟上怎麼排。

```
Row-oriented (OLTP)              Column-oriented (OLAP)
┌────┬───────┬──────┬───────┐    ┌──────────────────────────┐
│ id │ user  │ type │ price │    │ id:    1, 2, 3, 4, ...   │
├────┼───────┼──────┼───────┤    ├──────────────────────────┤
│ 1  │ u_17  │ view │ 0     │    │ user:  u_17, u_17, u_42  │
│ 2  │ u_17  │ cart │ 120   │    ├──────────────────────────┤
│ 3  │ u_42  │ view │ 0     │    │ type:  view, cart, view  │
└────┴───────┴──────┴───────┘    ├──────────────────────────┤
 read one row  = 1 seek          │ price: 0, 120, 0, ...    │
 SUM(price)    = read all cols   └──────────────────────────┘
                                  SUM(price) = read 1 column
```

列式存放把一筆資料的所有欄位放在一起，讀一筆只要一次定位。欄式存放把同一欄的值放在一起，帶來三個效果：

1. **欄位裁剪（column pruning）**：查詢只碰 3 個欄位，就只讀那 3 欄。100 欄的寬表中讀 3 欄，I/O 大約是原來的 3%（假設各欄大小相近）。
2. **壓縮率高**：同一欄的值型別相同、重複度高，字典編碼與 run-length 編碼效果好。`event_type` 只有十幾種值，幾乎可以壓到每筆不到 1 byte。
3. **述詞下推（predicate pushdown）**：每個資料區塊記錄欄位的最小值與最大值，查詢條件不在範圍內就整塊跳過。

**限制**：欄式存放寫入一筆要動到多個位置，單筆更新很貴。所以 OLAP 系統偏好批次寫入、不可變檔案，更新用「重寫檔案」或「另存差異檔再合併」來做——Part 4 的 table format 會回到這裡。

面試中常見的錯誤是拿 OLTP 資料庫直接跑分析。可以這樣說明界線：資料量在數千萬筆以下、查詢不多時，在 PostgreSQL 的唯讀副本上跑報表完全合理；一旦分析查詢開始掃描上億筆或拖慢線上交易，就該把資料搬到欄式儲存。

## 五、檔案格式與壓縮

資料湖上的檔案格式選擇會直接影響查詢成本，幾乎每場面試都會被問到「為什麼用 Parquet」。

| 格式 | 佈局 | Schema | 適合 | 不適合 |
|---|---|---|---|---|
| CSV | 列式、純文字 | 無 | 人工交換、小量匯出 | 型別不明、巢狀資料、大量分析 |
| JSON Lines | 列式、純文字 | 自描述 | 原始落地、schema 還在變 | 體積大、解析慢 |
| Avro | 列式、二進位 | 隨檔案或 registry | 串流訊息、逐筆寫入、schema 演進 | 只讀少數欄位的分析 |
| Parquet | 欄式、二進位 | 存在檔尾 footer | 分析查詢、資料湖主力 | 逐筆追加、頻繁小量寫入 |
| ORC | 欄式、二進位 | 存在檔尾 | Hive 生態的分析 | 生態較窄 |

記憶方式：**資料在移動時用列式（Avro），資料靜止待查時用欄式（Parquet）**。Kafka 訊息用 Avro 或 Protobuf，落到 S3 之後轉成 Parquet。

Parquet 檔案內部分成多個 row group，每個 row group 內每欄一個 column chunk，檔尾 footer 存放 schema 與各區塊的統計值。查詢引擎先讀 footer，再決定要讀哪些 row group 的哪些欄——這就是上一節欄位裁剪與述詞下推的實體基礎。

壓縮演算法的取捨是 CPU 換空間：

| 演算法 | 壓縮率 | 速度 | 常見用途 |
|---|---|---|---|
| Snappy | 較低 | 很快 | 熱資料、頻繁查詢的預設選擇 |
| Zstd | 高 | 快 | 近年多數場景的折衷首選 |
| Gzip | 高 | 慢 | 冷資料、歸檔 |

一個容易失分的細節：**可分割性（splittable）**。一個 10 GB 的 gzip 壓縮 CSV 無法被切開平行讀取，只能由單一 task 從頭解到尾。Parquet 的壓縮是在 column chunk 內部做的，所以檔案本身仍可依 row group 平行讀取。遇到「上游每天丟一個巨大的 .csv.gz」的情境，要主動提這一點。

## 六、分散式基本功：分區、複寫與一致性

資料量超過單機之後只有兩件事可做：把資料**切開**（partitioning）放到多台機器，以及把每份資料**多存幾份**（replication）以防機器掛掉。面試中大部分的深挖題都是這兩件事的變形。

### 6.1 分區：Hash 與 Range

| | Hash 分區 | Range 分區 |
|---|---|---|
| 作法 | `hash(key) % N` | 依 key 的範圍切段 |
| 優點 | 分佈均勻 | 範圍查詢只需讀相鄰分區 |
| 缺點 | 範圍查詢要掃所有分區 | 容易有熱點（例如依時間寫入全打到最後一段） |
| 例子 | Kafka 預設 partitioner、DynamoDB partition key | HBase row key、依日期分區的資料湖 |

兩者共同的敵人是**資料傾斜（skew）**：少數 key 佔了大部分資料。例如依 `user_id` 分區時，一個爬蟲帳號就產生了過半的事件，它所在的分區就成為整個系統的瓶頸。

```
hash(user_id) % 4

P0  ████████                      8%
P1  ██████████████████████████   62%   <- bot account lands here
P2  ███████                       7%
P3  ███████████████████████      23%

throughput of the whole job = throughput of P1
```

處理傾斜的三個標準答案，面試中依情境挑著說：

1. **換 key 或複合 key**：用 `user_id + 日期` 或 `event_id` 分區，前提是下游不需要同一使用者的事件有序。
2. **加鹽（salting）**：把熱 key 拆成 `key#0` … `key#9` 分散到多個分區，聚合時先在加鹽後的 key 上聚合一次、去鹽後再聚合一次。
3. **隔離熱 key**：已知的超大 key 走獨立路徑處理。

### 6.2 複寫與 Quorum

複寫最常見的是 leader–follower 模式：寫入先到 leader，再複製到 follower。關鍵問題是 leader 何時回覆「寫入成功」。

- **同步複寫**：等 follower 確認才回覆。不丟資料，但延遲高，follower 慢就拖累寫入。
- **非同步複寫**：leader 寫完就回覆。快，但 leader 掛掉時尚未複製的資料會遺失。

Kafka 的 `acks=all` 加上 `min.insync.replicas=2`（三副本）是典型的折衷：至少兩個副本寫入才算成功，容忍一台掛掉而不丟資料。

無 leader 的系統（Cassandra、DynamoDB 的設計源頭）用 quorum 表達同一件事。N 個副本中，寫入要 W 個確認、讀取要問 R 個；只要 **W + R > N**，讀取必定至少碰到一個擁有最新值的副本。N=3 時取 W=2、R=2 是常見設定。

### 6.3 CAP 與 PACELC

CAP 定理的實用說法是：**網路分區（P）發生時，你只能在一致性（C）與可用性（A）之間選一個**。因為分散式系統無法排除網路分區，真正的選擇只有 CP 或 AP。

CAP 只描述故障時的情況。PACELC 補上了平時：即使沒有分區（Else），你仍然要在延遲（Latency）與一致性（Consistency）之間取捨。這在面試中更有用，因為系統 99.9% 的時間都沒有分區。

| 系統 | 分區時 | 平時 | 面試中怎麼用 |
|---|---|---|---|
| DynamoDB（預設讀取） | 偏可用 | 偏低延遲 | 最終一致讀取便宜一半；需要時改用強一致讀取 |
| Cassandra | 偏可用 | 偏低延遲 | 一致性等級可逐查詢調整 |
| HBase / ZooKeeper | 偏一致 | 偏一致 | 寧可拒絕也不回傳舊資料 |
| 傳統單主 RDBMS | 偏一致 | 偏一致 | 交易正確性優先 |

對 DE 而言，最常用到的結論是：**分析型管線大多可以接受最終一致，但必須可重現**。儀表板晚 30 秒看到資料沒關係；同一個查詢今天和明天對同一天算出不同數字，就會有人來找你。

## 七、交付語意與冪等

任何跨網路的資料傳遞都會遇到同一個問題：送出後沒收到確認，要不要重送？三種語意由此而來。

```
at-most-once    send, never retry         -> may LOSE data
at-least-once   retry until acked         -> may DUPLICATE data
exactly-once    each record's effect is applied once
                = at-least-once delivery + idempotent or transactional sink
```

**直覺**：exactly-once 不是「訊息只送一次」，那在會失敗的網路上做不到。它是「送很多次也沒關係，結果和送一次一樣」。

所以實務上的做法是**至少一次交付，加上冪等（idempotent）的寫入**。冪等的意思是同一個操作做一次和做十次，結果相同。三種常見手法：

| 手法 | 作法 | 例子 |
|---|---|---|
| 以鍵覆寫（upsert） | 用唯一鍵寫入，重複的寫入覆蓋同一筆 | 以 `event_id` 為主鍵 `MERGE` |
| 分區覆寫 | 重跑時整個分區重新產生並原子替換 | `INSERT OVERWRITE` 某一天的分區 |
| 去重視窗 | 記住最近看過的鍵，丟棄重複 | 串流中保留 24 小時的 `event_id` 狀態 |

這也是步驟 3 堅持先定義 `event_id` 的原因：**沒有唯一鍵就沒有冪等，沒有冪等就沒有安全的重試**。Part 2 會把這個原則用在批次回補上，Part 3 則用在串流的 exactly-once。

## 八、為什麼選 X 不選 Y

基本功階段最常被追問的六個選擇。每一列都附上「翻轉條件」——什麼情況下被否決的那個選項反而是對的。

| 選擇 | 選 X 的理由 | 不選 Y 的理由 | 翻轉條件 |
|---|---|---|---|
| Parquet vs JSON（資料湖主儲存） | 欄位裁剪與統計值讓查詢少掃 10 倍以上；體積小 5–10 倍 | JSON 每次查詢都要全檔解析，掃描費與時間線性成長 | 原始落地層、schema 每週在變、資料量每天不到幾 GB |
| 欄式倉儲 vs 交易資料庫唯讀副本 | 聚合上億筆仍在秒級；不影響線上交易 | 列式掃描全表慢，且與線上流量搶資源 | 資料 < 數千萬筆、報表少、團隊沒有人力維運第二套系統 |
| Avro vs Parquet（串流訊息） | 逐筆編碼、schema 演進規則明確、適合 registry | Parquet 需要湊滿一批才寫得出一個檔案 | 訊息其實是微批次落檔而非逐筆傳遞 |
| Hash vs Range 分區 | 分佈均勻、不易有寫入熱點 | Range 依時間寫入會集中在最後一段 | 查詢以範圍掃描為主（時間序列、前綴查詢） |
| 至少一次 + 冪等 vs 端到端交易 | 實作簡單、跨系統都適用 | 分散式交易延遲高、不是每個 sink 都支援 | sink 無法提供唯一鍵或覆寫語意，且數字是計費依據 |
| 分層新鮮度 vs 全面串流 | 只有儀表板走串流，其他走批次，成本與複雜度低一個量級 | 全串流要為每條管線處理狀態、晚到與重跑 | 多數消費者都需要分鐘級新鮮度 |

## 九、常見失分點與自我檢查

以下是實際面試中最常出現、也最容易修正的問題。

**跳過需求直接畫圖。** 補救方法是養成固定開場白：「在開始設計之前，我想先確認三件事：誰在用這些資料、需要多新鮮、數字要多準。」

**只說工具名稱，不說為什麼。** 「我用 Kafka」不得分；「尖峰 23 MB/s、需要多個下游各自以自己的速度消費、而且要能重播，所以用可重播的 log 型佇列，在 AWS 上可以是 MSK 或 Kinesis」才得分。

**沒有主動提到失敗。** 資深與否的分水嶺通常在這裡。每畫一個箭頭，問自己：這裡重送會怎樣？這裡晚到會怎樣？

**估算過度精確。** 把 500M / 86,400 算到小數點後兩位是浪費時間。四捨五入到一位有效數字，然後說出它導出什麼決定。

**所有東西都要即時。** 串流系統的營運成本遠高於批次。除非需求明確要求，否則預設批次，並說明你為何如此選擇。

進入白板之前的自我檢查清單：

- [ ] 我知道誰在查詢、用什麼方式查詢
- [ ] 我知道新鮮度要求是秒、分鐘還是天
- [ ] 我算過每秒筆數、每日 GB、年度 TB
- [ ] 我寫下了唯一鍵與時間欄位
- [ ] 我能說出每個元件對應哪一個需求
- [ ] 我至少準備了兩個可以深挖的失敗情境

回到本文情境，一個合格的開場總結大致如下：三種消費者對應三種新鮮度；尖峰約 23 MB/s、欄式儲存後每天約 85 GB、13 個月約 34 TB；事件以 `event_id` 去重、以 `event_time` 為分析基準；主體走每日批次寫入 Parquet 資料湖，只有儀表板那一條另外走串流聚合。**講到這裡大約十分鐘，還沒提到任何一個需要辯護的工具，卻已經把後面三十分鐘的討論範圍定好了。**

## 十、系列導航

**本篇重點**

- DE 系統設計評的是需求收斂、取捨、正確性與營運意識，工具名稱只是載體。
- 六步框架：釐清 → 估算 → 契約 → 設計 → 深挖 → 營運；前兩步決定後面所有選擇。
- 四個數字（每秒筆數、每日 GB、年度 TB、每月費用）要能導出設計結論。
- 欄式儲存靠欄位裁剪、壓縮與述詞下推讓分析查詢少讀資料。
- exactly-once 的實務做法是「至少一次交付 + 冪等寫入」，前提是有唯一鍵。
