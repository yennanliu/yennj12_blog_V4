> 多數人準備系統設計的方式，是背下十張「標準架構圖」。  
> 面試官只要換一個數字或加一句「如果事件晚到三天呢」，背下來的圖就接不下去。  
> 能通過的人靠的不是記得更多圖，而是**每一步都說得出這個決定是從哪個需求、哪個數字推出來的**。  
> 這一篇不給你新的圖，而是示範同一套推導在真實對話中怎麼走完 45 分鐘。

前四篇分別建立了[答題框架](/posts/de-system-design-interview-part1-framework-fundamentals-zh/)、[批次](/posts/de-system-design-interview-part2-batch-pipeline-ingestion-zh/)、[串流](/posts/de-system-design-interview-part3-streaming-realtime-zh/)與[儲存](/posts/de-system-design-interview-part4-storage-warehouse-lakehouse-zh/)的判斷方式。本篇把它們放進兩場模擬面試：一場完整的 45 分鐘，一場精簡版；最後附上十一種常見題型的速查表。之後的 Part 6 到 Part 9 再各以一個產業（支付、廣告、叫車、影音串流）做完整的案例演練。Part 10 到 Part 14 回頭把最常被追問的五個主題（新鮮度、重跑、事件正確性、Schema 演進、儲存與查詢效率）的策略選項逐一展開，Part 15 是資安 SaaS 的案例。

## 面試情境

> **面試官**：「我們是一家電商，App 與網站的日活躍使用者約 2,000 萬。請設計一個點擊流（clickstream）分析平台，收集使用者行為事件並支援分析。」

題目刻意只有兩句話。接下來的每個數字與限制，都要靠候選人問出來。

---

## 一、怎麼讀這篇

對話以引言區塊呈現，穿插的「評註」說明這一段在評分上發生了什麼。時間標記對應 Part 1 的六步框架，`sec` 是本文的章節編號（第二到第六節）：

```
 0        5        10       15            25                 40     45
 ├────────┼────────┼────────┼─────────────┼──────────────────┼──────┤
 │clarify │estimate│contract│   design    │    deep dives    │ ops  │
 │ sec 2  │ sec 2  │ sec 3  │   sec 4     │      sec 5       │sec 6 │
 └────────┴────────┴────────┴─────────────┴──────────────────┴──────┘
```

建議的練習方式是：先只讀面試官的問題，自己答一遍並計時，再對照候選人的回答與評註。直接從頭讀到尾的效果差很多。

## 二、0–10 分鐘：釐清需求與估算

> **候選人**：「開始設計之前我想先確認幾件事。第一，誰會用這些資料、用來做什麼？」
>
> **面試官**：「三群人。分析師每天看漏斗與留存報表；資料科學家要原始事件訓練推薦模型；大促期間營運要看即時的活躍人數與下單數。」
>
> **候選人**：「這三種需求的新鮮度要求一樣嗎？報表是隔天早上看到就可以，還是要當天？」
>
> **面試官**：「報表每天早上 8 點前要有前一天的完整資料。即時看板希望延遲在一分鐘內。」
>
> **候選人**：「即時看板的數字需要多準？例如活躍人數可以接受 1% 左右的誤差嗎？還是它會被拿去對帳？」
>
> **面試官**：「看趨勢用，1% 可以。訂單金額的正式數字以交易系統為準。」
>
> **候選人**：「事件來自行動裝置的話，離線時會先存在本機、連線後才送出嗎？最晚可能晚多久？」
>
> **面試官**：「會。大部分幾分鐘內到，但有少數會晚到兩三天。」
>
> **候選人**：「最後兩個：原始事件要保留多久？事件中有沒有需要特別處理的個資？」
>
> **面試官**：「保留兩年。有使用者 ID、裝置 ID 與 IP。」

**評註**：五個問題各對應 Part 1 的一個類別——消費者、新鮮度、正確性、規模特性（晚到）、保留與合規。其中「看板可以接受 1% 誤差」與「晚到兩三天」這兩個答案，會直接決定後面的兩個設計：可以用近似演算法、批次必須重算最近幾天。沒問出來的話，後面就沒有依據做這些取捨。

> **候選人**：「我先估一下規模。每位使用者每天大約產生多少事件？」
>
> **面試官**：「大約 50 個。大促當天流量可以到平常尖峰的三倍以上。」

候選人在白板上寫下（假設每個事件 1 KB、平日尖峰為平均的 3 倍、大促尖峰為平均的 10 倍）：

```
events/day       = 20M users × 50          = 1,000,000,000
raw size/day     = 1B × 1 KB               = 1 TB
avg events/s     = 1B / 86,400             ≈ 11,600 /s
normal peak      = 11,600 × 3              ≈ 35,000 /s    (35 MB/s)
promo peak       = 11,600 × 10             ≈ 116,000 /s   (116 MB/s)

Parquet on disk  = 1 TB / 6 (assumed)      ≈ 170 GB/day
2 years          = 170 GB × 730            ≈ 124 TB
S3 Standard      = 124,000 GB × $0.023     ≈ $2,850 / month
```

> **候選人**：「幾個結論。第一，三種新鮮度代表我不需要讓整個平台都跑串流，只有看板那一條需要。第二，大促尖峰約 116 MB/s，擷取層必須有緩衝，而且容量要以大促而不是平日來規劃。第三，兩年約 124 TB，儲存每月不到三千美元，成本重點會在運算與查詢掃描，所以我會在儲存佈局上多花心思。」

**評註**：估算花了不到三分鐘，而且每個數字都導出一個設計方向。這正是估算的目的。注意候選人主動說出「壓縮比 6 倍是假設」——說明假設比數字本身精確更重要。

## 三、10–15 分鐘：資料契約

> **候選人**：「畫架構之前，我想先定義事件長什麼樣子，因為去重與晚到的處理都取決於它。」

```
event_id      string     -- SDK 產生的 UUID；所有去重的依據
user_id       string     -- 登入前為空
device_id     string
session_hint  string     -- 用戶端的工作階段提示，僅供參考
event_type    string     -- page_view / search / add_to_cart / purchase ...
event_time    timestamp  -- 用戶端時鐘；分析以它為準
ingest_time   timestamp  -- 收集端蓋上；用來衡量延遲、判斷時鐘異常
sdk_seq       long       -- 每個裝置遞增的序號；用來估計遺失率
schema_ver    int
properties    map<string,string>
```

> **候選人**：「三個重點。`event_id` 由 SDK 在產生事件時就決定，所以重送的事件會帶同一個 ID。時間有兩個：`event_time` 是分析基準，但用戶端時鐘不可信，所以收集端另外蓋 `ingest_time`；兩者差距過大的事件我會標記出來。`sdk_seq` 讓我可以從序號的缺口估計端到端的遺失率，這是整條管線的完整性指標。」
>
> **面試官**：「Schema 之後會變，你怎麼處理？」
>
> **候選人**：「固定欄位放在外層，各事件類型自己的屬性放在 `properties`。固定欄位的變更只允許加上可為空的欄位，並由 schema registry 在收集端驗證；不相容的事件不丟棄，寫到隔離區並告警。這樣 App 團隊加新屬性不需要我們改管線，而破壞性變更在入口就會被擋下。」

**評註**：`sdk_seq` 是多數候選人不會想到的欄位。它顯示候選人在設計時就考慮「我怎麼知道資料有沒有掉」，屬於營運意識的訊號。

## 四、15–25 分鐘：架構與三個演進階段

> **候選人**：「我先畫最簡單可行的版本，再說明它在哪裡不夠。」

```
╔══════════════════════════════════════════════════════════════════════╗
║  Phase 1  Managed delivery to the lake (POC)                         ║
╚══════════════════════════════════════════════════════════════════════╝

┌───────┐ batch  ┌───────────┐     ┌──────────────┐     ┌─────────────┐
│ SDK   │───────▶│ Collector │────▶│ Firehose     │────▶│ S3 Parquet  │
└───────┘ HTTPS  │ API       │     │ buffer 60 s  │     │ dt=...      │
                 └───────────┘     └──────────────┘     └──────┬──────┘
                                                               │
                                              daily SQL ┌──────┴──────┐
                                                        │ Athena      │
                                                        └─────────────┘
```

> **候選人**：「這個版本用受管服務把事件直接送到 S3，每天用 SQL 產生報表。元件少、幾乎不需要維運，可以滿足報表與原始資料兩個需求。它不夠的地方是：沒有即時路徑；沒有去重；事件依到達時間落地，晚到的事件會被算到錯的日期。」

```
╔══════════════════════════════════════════════════════════════════════╗
║  Phase 2  Log + two paths (target design)                            ║
╚══════════════════════════════════════════════════════════════════════╝

┌───────┐      ┌───────────┐      ┌──────────────────┐
│ SDK   │─────▶│ Collector │─────▶│ Kafka (MSK)      │
└───────┘      │ validate, │      │ key = device_id  │
               │ stamp     │      │ 48 partitions    │
               │ ingest_ts │      │ retain 3 days    │
               └───────────┘      └───┬──────────┬───┘
                                      │          │
                 speed path (< 1 min) │          │ batch path (T+1)
                                      ▼          ▼
                          ┌──────────────┐  ┌──────────────────────┐
                          │ Flink        │  │ Bronze (Iceberg)     │
                          │ 1-min windows│  │ append, by ingest dt │
                          │ HLL for UV   │  └──────────┬───────────┘
                          └──────┬───────┘             │ Spark, daily
                                 ▼                     ▼
                          ┌──────────────┐  ┌──────────────────────┐
                          │ ClickHouse   │  │ Silver: dedup, clean │
                          │ minute rows  │  │ by event date        │
                          └──────┬───────┘  └──────────┬───────────┘
                                 ▼                     ▼
                          ┌──────────────┐  ┌──────────────────────┐
                          │ Live board   │  │ Gold: funnel,        │
                          └──────────────┘  │ retention -> Athena  │
                                            └──────────────────────┘
```

> **候選人**：「目標設計有四個改變。一，在收集端與下游之間放一個可重播的 log，吸收大促尖峰，並讓兩條路徑各自以自己的速度消費。二，速度路徑只做看板需要的分鐘級聚合，用近似演算法計算不重複人數。三，批次路徑分三層：Bronze 依到達日期只追加，Silver 依事件日期去重，Gold 產出報表。四，表格用 Iceberg，讓回補與查詢不互相干擾。」
>
> **面試官**：「分區 key 為什麼用 `device_id`？分區數怎麼來的？」
>
> **候選人**：「我希望同一個裝置的事件落在同一個分區，下游切分工作階段時不必跨分區重組。要說明的是 Kafka 保的只是到達順序：離線補送的事件仍然會亂序，所以切分時還是依 `event_time` 排序，並搭配晚到策略。至於 `user_id`，它在登入前是空的，會造成大量事件集中在同一個分區，所以不用它。分區數方面，大促尖峰 116 MB/s，以每個分區約 10 MB/s 的保守值需要 12 個；但我希望下游平行度能到 32 以上，再留成長空間，所以取 48。」

**評註**：候選人主動排除了 `user_id` 並說明原因（空值造成傾斜），這是 Part 1 與 Part 2 都強調的陷阱。分區數的回答同時用了吞吐量與平行度兩個依據。

> **候選人**：「如果之後成長到多區域或十倍規模，我會做第三階段的調整。」

| | Phase 1 | Phase 2 | Phase 3 |
|---|---|---|---|
| 擷取 | 受管傳遞服務 | 收集端 + Kafka | 多區域收集端、各區域就近寫入後彙整 |
| 即時 | 無 | Flink + ClickHouse | 加上依事件價值的降級取樣 |
| 批次 | 每日 SQL | 三層 lakehouse | 加上小時級增量、服務引擎承接 BI |
| 治理 | 無 | Schema 驗證、隔離區 | 個資代碼化、欄位層級權限、成本歸屬 |
| 維運元件數 | 2 | 6 | 9 以上 |

## 五、25–40 分鐘：深挖

### 5.1 去重

> **面試官**：「SDK 逾時會重送，你在哪裡去重？」
>
> **候選人**：「兩條路徑的做法不同，因為它們對準確度的要求不同。
>
> 批次路徑要精確。Silver 的每日作業對事件日期的分區以 `event_id` 去重，重複時保留 `ingest_time` 最早的那一筆。因為重複事件可能跨日到達，去重範圍要涵蓋被重算的那幾天，而不只是當天新到的資料。
>
> 速度路徑我不做全量的精確去重。若要以 `event_id` 保留一小時的狀態，大促時是 116,000 × 3,600，約 4.2 億個鍵，以每鍵 100 bytes 估計約 42 GB，為了一個容許 1% 誤差的看板不值得。活躍人數我用 HyperLogLog，它對重複天生免疫——同一個使用者算幾次都是一個。下單數的事件量小得多，以 `order_id` 做精確去重的狀態很小，可以負擔。」
>
> **面試官**：「HyperLogLog 的誤差多大？」
>
> **候選人**：「標準誤差大約是 1.04 除以暫存器數量的平方根。用 16,384 個暫存器時約 0.8%，每個計數器約 12 KB。而且它可以合併：每分鐘各一個，要看過去一小時的不重複人數時，把 60 個合併起來就好，不需要回頭讀原始事件。」

**評註**：這段回答的結構是「需求不同，所以做法不同」，並用估算說明為何不選精確去重。「可以合併」這個性質是主動補充的，顯示理解而非背誦。

### 5.2 晚到資料與時鐘

> **面試官**：「你說有事件會晚到三天。8 點的報表怎麼辦？」
>
> **候選人**：「我把『落地』與『歸屬』分開。Bronze 依**到達日期**分區且只追加，所以任何一天的 Bronze 分區寫完就不再變動，重跑永遠讀到同樣的輸入。Silver 依**事件日期**分區。每天的作業不只處理昨天，而是重新產生最近四個事件日期的 Silver 分區——晚到上限是三天，再加一天涵蓋跨過作業截止點的情況——並以分區覆寫的方式寫入，所以重跑是冪等的。下游的 Gold 表跟著重算這四天。
>
> 這表示報表中最近四天的數字會小幅修正。我會在報表上標示這幾天是『暫定』，之後才是最終值。」
>
> **面試官**：「超過三天才到的呢？」
>
> **候選人**：「它們仍然會進 Bronze，不會遺失，但不會自動進入 Silver。我會監控這類事件的比例；如果長期低於例如 0.01%，就接受這個誤差並寫進資料契約；若偏高，延長重算的天數或每週做一次較長範圍的修正。這是成本與完整性的交換，門檻應該由資料來決定。」
>
> **面試官**：「用戶端時鐘被調到明年呢？」
>
> **候選人**：「所以收集端要蓋 `ingest_time`。`event_time` 比 `ingest_time` 晚超過幾分鐘的事件不可能是真的；我會保留原值、把這筆標記為時鐘異常，並在 Silver 中改用 `ingest_time` 作為歸屬依據。同一條規則也要放在速度路徑上、在產生 watermark 之前就套用，否則一筆未來的事件會把 watermark 往前推，讓後續的正常事件全部變成晚到。」

**評註**：最後一句把時鐘異常連結到 watermark 被推進的後果，這是 Part 3 內容的實際應用，也是區分資深候選人的細節。

### 5.3 工作階段切分與傾斜

> **面試官**：「漏斗報表需要工作階段。你的 Spark 作業跑了四小時，其中一個 task 佔了三個半小時。怎麼辦？」
>
> **候選人**：「這是傾斜。工作階段切分要把同一個裝置的事件放在一起依時間排序，以 30 分鐘閒置為界切開，所以會依 `device_id` shuffle。一個 task 特別慢，表示某個 key 的資料量遠大於其他。
>
> 我會先看那個 key 是什麼。最常見的是空值或測試用的固定 ID，那就在 Silver 過濾掉。第二種是爬蟲或自動化腳本，一個裝置一天產生幾百萬個事件——這不是真實的使用者行為，應該在 Silver 以每個裝置每日事件數的上限標記為機器流量，排除在工作階段計算之外，另存一張表供風控使用。
>
> 這題不能用加鹽解決，因為加鹽會把同一個裝置的事件拆到不同分區，工作階段就切不對了。所以正確的做法是把異常的 key 隔離出來，而不是把它打散。」

**評註**：面試官給的是症狀，候選人依序回答了診斷方法、兩種根因、處置，並說明為何標準技巧（加鹽）在這裡不適用。知道技巧的適用邊界，比知道技巧本身更有價值。

### 5.4 大促尖峰

> **面試官**：「大促當天流量是平常的三倍以上，你的系統哪裡會先出問題？」
>
> **候選人**：「依序看每一層。收集端是無狀態的，SDK 每個請求批次約 20 個事件，大促尖峰約每秒 5,800 個請求，可以依請求數自動擴充，並在活動前預先擴好。Kafka 的分區數無法臨時增加而不影響順序，所以 48 個分區是照大促容量規劃的。
>
> 最可能先落後的是速度路徑的 Flink 作業。我會監控消費延遲換算成的秒數；超過一分鐘時先擴充平行度。如果仍然追不上，我有一個降級方案：依事件類型取樣。捲動、曝光這類低價值的高頻事件在速度路徑中只處理 10% 並把計數乘回去，下單與加入購物車則全數處理。批次路徑不受影響，隔天的報表仍然完整。
>
> 萬一 Kafka 本身不可用，收集端回覆可重試的錯誤，由 SDK 的本機緩衝與退避重試承接。我不會讓收集端只寫到本機磁碟就回覆成功：執行個體一旦被回收，已確認的事件就遺失了，而 SDK 不會重送已確認的請求。若要在伺服器端緩衝，必須先寫入另一個耐久的儲存再回覆。因為有 `event_id`，這些重送不會造成重複計數。」

**評註**：回答沿著資料流逐層檢查，並區分「可以臨時擴充的」與「必須事先規劃的」。降級方案保住了高價值事件，也說明了為何降級不影響正確性的最終來源（批次路徑）。

## 六、40–45 分鐘：失敗、監控與成本

> **面試官**：「最後五分鐘。上線之後，你怎麼知道這個系統是健康的？」
>
> **候選人**：「我會看四類指標，每一類回答一個問題。」

| 問題 | 指標 | 告警門檻（起始值） |
|---|---|---|
| 資料有沒有掉？ | 由 `sdk_seq` 缺口估計的遺失率；各層筆數對比（收集端 → Kafka → Bronze → Silver） | 遺失率 > 0.1%；相鄰層差異 > 0.5% |
| 資料新不新？ | 速度路徑的消費延遲（秒）；Gold 表的完成時間 | 延遲 > 60 秒；7:00 尚未完成 |
| 資料對不對？ | 重複率、時鐘異常比例、隔離區筆數、超過三天的晚到比例 | 任一項偏離 7 日基準 3 倍 |
| 花了多少錢？ | 每日掃描量前 20 名的查詢；各層儲存量成長 | 單一查詢掃描 > 1 TB |

> **候選人**：「成本方面，儲存兩年約 124 TB、每月不到三千美元，超過 90 天的資料可以移到低頻儲存類別再省下一部分。比較大的變數是查詢：如果分析師直接查 Silver，一個掃描 30 天的查詢是 5 TB、約 25 美元，所以我會把常用的漏斗與留存做成 Gold 表，並在目錄上標明哪些表適合直接查。
>
> 如果有更多時間，我想進一步討論的是個資：`user_id`、`device_id` 與 IP 應該在進入 Bronze 前代碼化，對照表另外存放並嚴格控管，這樣刪除請求可以先從對照表下手。不過代碼化只是假名化：`properties` 裡的其他識別資訊、以及衍生表與服務層的副本，仍然要另外清除。」

**評註**：以「如果有更多時間」收尾，主動指出設計中尚未展開的部分。這比假裝設計已經完整更能建立信任。

## 七、精簡示範：即時 Top-K 熱門商品

第二場示範只呈現推導的骨架，用來對比：題目換了，框架不變。

> **面試官**：「設計一個即時排行榜，顯示過去一小時瀏覽次數最高的 100 個商品，每分鐘更新。商品總數約 1,000 萬。」

**釐清**後得到：資料來源是上一場的 `page_view` 事件流；排行榜顯示在首頁，讀取量很高；名次接近的商品順序稍有出入可以接受；刷量行為需要排除。

**估算**：瀏覽事件約佔全部的一半，尖峰約每秒 58,000 筆。一小時內實際被瀏覽的商品假設約 50 萬個。

**關鍵推導一：滑動視窗怎麼算。** 「過去一小時、每分鐘更新」是長度 60 分鐘、每 1 分鐘滑動的視窗。直接實作代表每個事件屬於 60 個視窗。較省的做法是只維護每分鐘的滾動計數，查詢時把最近 60 個分鐘桶加總。

```
per-minute buckets for product p (count of views)

 12:01  12:02  12:03   ...   12:59  13:00  13:01
┌─────┐┌─────┐┌─────┐       ┌─────┐┌─────┐┌─────┐
│ 41  ││ 37  ││ 52  │  ...  │ 48  ││ 55  ││ 60  │
└─────┘└─────┘└─────┘       └─────┘└─────┘└─────┘
└───────── window at 13:00 = sum of 60 ────┘
       └───────── window at 13:01 = previous − 41 + 60 ───┘
```

**關鍵推導二：精確還是近似。** 狀態大小是 50 萬個商品 × 60 個桶 × 約 16 bytes，約 480 MB——完全放得下，所以**用精確計數**。這是值得說出口的判斷：很多人一聽到 Top-K 就直接搬出 Count-Min Sketch，但近似結構是在鍵的數量大到放不進記憶體時才需要（例如全網的網址或搜尋字詞，鍵數達十億級）。

**關鍵推導三：熱門商品造成傾斜。** 依商品 ID 分組時，熱門商品所在的平行實例會過載。做法是兩階段聚合：每個實例先在本地累計數秒，再把「商品、累計次數」送往下一階段合併。熱門商品每秒上千個事件在本地就被合成一筆。

**關鍵推導四：全域 Top-K。** 每個平行實例各自算出自己負責的商品中的前 100 名，再由單一實例合併這些候選並選出最終的 100 名。因為每個商品只會出現在一個實例中，各實例的前 100 名聯集必定包含全域的前 100 名。

**服務層**：結果只有 100 筆，每分鐘整份覆寫到 Redis，首頁直接讀取。排行榜的讀取量再高，也與計算路徑無關。

**防刷量**：計入排行前先以「同一裝置對同一商品在一分鐘內只算一次」去重，並排除上一場標記的機器流量。這等於把排行的指標定義成**去重後的瀏覽次數**而不是原始瀏覽數，正常使用者一分鐘內重看同一商品也只算一次，應該在釐清階段就與面試官確認；前面說的「精確」是指對這個定義精確計數。

| 決定 | 選擇 | 翻轉條件 |
|---|---|---|
| 計數方式 | 精確計數（約 480 MB 狀態） | 鍵數達十億級、放不進狀態時改用 Count-Min Sketch 加上候選堆積 |
| 視窗實作 | 分鐘桶加總 | 要求秒級更新且視窗很長時，改用增量式的加減維護 |
| 聚合 | 本地預聚合 + 全域合併 | 無明顯熱點時，單階段即可 |
| 服務 | 每分鐘覆寫 Redis | 需要依品類、地區等多維度排行時，改存分鐘粒度到 OLAP 引擎 |

## 八、常見情境速查表

十一種最常出現的題型。每一題真正在考的是「核心張力」那一欄，而不是元件清單。

| 題型 | 核心張力 | 一定要談到 | 對應篇章 |
|---|---|---|---|
| 點擊流／行為事件分析平台 | 量大、會重複、會晚到 | `event_id` 去重、事件時間與到達時間、依事件日期重算 | 本篇、Part 2 |
| 交易資料庫同步到資料湖（CDC） | 順序、刪除、schema 演進 | 以主鍵為 key 保序、MERGE、日誌保留期、對帳 | Part 2 |
| 即時指標儀表板 | 新鮮度與準確度的交換 | watermark、暫定值與最終值、冪等 sink、消費延遲 | Part 3 |
| 廣告點擊計數（計費用途） | 不能多算也不能少算 | exactly-once 三段、與批次對帳、無效點擊過濾 | Part 3、Part 7 |
| Top-K／熱門排行 | 滑動視窗、熱點、精確或近似 | 分鐘桶、兩階段聚合、狀態大小估算 | 本篇 |
| 日誌與指標平台 | 寫入量極大、查詢少但要快 | 冷熱分層與保留期、索引成本、高基數標籤的控制 | Part 4 |
| 機器學習特徵平台 | 線上與離線的一致性 | 同一份定義產生兩邊特徵、時間點正確的 join 以避免資料洩漏 | Part 9 |
| 金流對帳與可稽核報表 | 不可變、與外部帳一致、歷史可重現 | 只追加與沖銷、檔案版本化、業務時間與記錄時間 | Part 6 |
| 即時風控／詐欺偵測 | 低延遲下的有狀態判斷 | 鍵值狀態與 TTL、維度補充的 join 方式、規則更新不停機 | Part 3 |
| 資料倉儲建模（叫車、外送、電商） | 粒度與歷史 | 宣告事實表粒度、SCD Type 2、回補與雙軌驗證 | Part 4、Part 8 |
| A/B 測試指標平台 | 曝光與行為的正確歸因 | 分組記錄與事件的 join、樣本比例檢查、指標定義集中管理 | Part 9 |

使用方式：拿到題目後，先判斷它屬於哪一列，把「核心張力」當成你要在深挖階段主動帶到的主題。多數真實題目是兩列的組合，例如「即時風控」加上「特徵平台」。

## 九、為什麼選 X 不選 Y

第一場示範中的關鍵決定彙整。

| 選擇 | 選 X 的理由 | 不選 Y 的理由 | 翻轉條件 |
|---|---|---|---|
| 收集端 + Kafka vs 受管傳遞服務直送 S3 | 可重播、兩條路徑獨立消費、能吸收十倍尖峰 | 直送 S3 沒有即時路徑，也無法讓新的下游從頭消費 | 只需要 T+1 報表、沒有即時需求、團隊不想維運叢集 |
| key 用 `device_id` vs `user_id` | 登入前後都有值、分佈均勻、同一裝置的事件集中在同一分區 | `user_id` 在登入前為空，空值集中造成傾斜 | 產品強制登入，且下游需要跨裝置的使用者層級順序 |
| Bronze 依到達日期 vs 依事件日期分區 | 寫完即不可變，重跑的輸入固定 | 依事件日期落地時，晚到資料會不斷改寫舊分區 | 沒有晚到資料（例如伺服器端產生的事件） |
| 批次精確去重 + 串流近似計數 vs 串流全量精確去重 | 狀態小兩個數量級，滿足 1% 誤差的需求 | 一小時的 `event_id` 狀態約 42 GB，維運成本高 | 即時數字用於計費或對帳，必須精確 |
| HyperLogLog vs 精確的不重複計數 | 每個計數器約 12 KB、可合併、對重複免疫 | 精確計數要保存所有 ID，且跨分鐘無法直接合併 | 人數規模小（數萬以下）或要求零誤差 |
| 固定重算最近四天 vs 只處理新到資料 | 邏輯簡單、冪等、自動納入晚到資料 | 只處理新資料需要追蹤哪些舊分區被影響，容易漏 | 每日資料量大到重算四天的成本無法接受，改為只重算有新資料的分區 |
| 隔離異常 key vs 加鹽 | 工作階段切分需要同一裝置的事件在一起 | 加鹽會拆散同一個 key，破壞計算語意 | 可分解的聚合（計數、加總）遇到傾斜時，加鹽才是正解 |
| 依事件價值取樣降級 vs 無差別丟棄或停止服務 | 保住下單等高價值事件，看板仍可用 | 無差別丟棄會讓關鍵指標失真 | 所有事件同等重要時，只能擴充容量或延長延遲 |

## 十、評分訊號與系列導航

不同資歷的候選人面對同一題，差別不在畫出的架構圖，而在下列訊號。可以用它來檢視自己的練習錄音。

| 維度 | 尚未達標 | 達標 | 超出預期 |
|---|---|---|---|
| 需求 | 直接開始畫圖 | 問出消費者、新鮮度、規模 | 問出會改變設計的限制（誤差容忍、晚到、合規），並說明各自影響什麼 |
| 估算 | 沒有數字 | 算出每秒筆數與儲存量 | 每個數字都導出一個設計決定 |
| 取捨 | 只說用什麼 | 說明為什麼用 | 說明放棄了什麼，以及什麼條件下會改選 |
| 正確性 | 被問才想到重複 | 主動處理重複與重跑 | 主動處理亂序、晚到、時鐘異常，並分辨哪些要精確、哪些可近似 |
| 營運 | 沒提監控 | 列出要監控的指標 | 說明如何偵測靜默的資料遺失、降級方案與成本的主要來源 |
| 溝通 | 沉默地畫圖 | 邊畫邊說明 | 掌握時間、主動提出要深挖的點、誠實指出尚未處理的部分 |

五篇內容濃縮成練習時可以反覆自問的五個問題：

1. 誰在查、要多新鮮、要多準？（Part 1；策略深入見 [Part 10](/posts/de-system-design-interview-part10-freshness-sla-tiers-zh/)）
2. 這個作業重跑一次，結果會一樣嗎？（Part 2；策略深入見 [Part 11](/posts/de-system-design-interview-part11-idempotency-rerun-backfill-zh/)）
3. 事件重複、亂序或晚到時，數字還對嗎？（Part 3；策略深入見 [Part 12](/posts/de-system-design-interview-part12-dedup-ordering-late-data-zh/)）
4. 最常見的查詢需要讀多少資料？（Part 4；策略深入見 [Part 14](/posts/de-system-design-interview-part14-storage-query-efficiency-zh/)）
5. 我怎麼知道它壞了，壞了之後怎麼修？（本篇）

前四個問題各自都還有一整組做法可以選。Part 10、11、12、14 逐題展開不同策略的優缺點與適用條件；第五個問題沒有獨立成篇，它的做法分散在各篇的監控與「症狀到診斷」段落裡。另外補上這份清單沒列到的 [Schema 演進（Part 13）](/posts/de-system-design-interview-part13-schema-evolution-zh/)；Part 15 再用一個資安 SaaS 的案例把它們串起來。
