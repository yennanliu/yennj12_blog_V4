> 多數人看到「每秒 25 萬筆位置更新」，就開始設計一個不能掉任何一筆的管線。  
> 但一筆 8 秒前的司機位置，已經被下一筆取代，把它補回來沒有任何價值。  
> 位置資料的特性是**最新的一筆才重要，舊的會自己過期**；用處理金流的標準來處理它，只會得到一個又貴又慢的系統。  
> 這一題考的是你能不能依資料的性質選擇保證等級，而不是把 exactly-once 當成預設答案。

這是產業案例的第三篇。[Part 6](/posts/de-system-design-interview-part6-payments-ledger-reconciliation-zh/) 的支付題是「量小、每筆都重要」，[Part 7](/posts/de-system-design-interview-part7-adtech-click-billing-attribution-zh/) 的廣告題是「量大、其中 1% 重要」。叫車題的即時部分則是第三種：**量大，而且單筆幾乎不重要，重要的是現在的狀態**。同一題裡還有一個完全相反的部分——行程與車資——必須精確。

---

## 面試情境

> **面試官**：「我們是叫車平台，尖峰時約有 100 萬名司機同時在線，每 4 秒回報一次位置。請設計資料系統，支援三件事：提供各區域的即時供需狀況給動態定價使用、保存行駛軌跡，以及建立行程的資料倉儲供計費與營運分析。」

---

## 一、這一題在考什麼

題目把三種性質不同的資料放在一起，第一步是把它們分開。

| 資料 | 量 | 單筆的價值 | 需要的保證 | 新鮮度 |
|---|---|---|---|---|
| 即時位置（供需用） | 極大 | 幾乎為零，下一筆就取代它 | 寧新勿全：落後時可以跳過舊資料 | 數秒 |
| 軌跡（保存用） | 極大 | 低，但行程中的片段在爭議時需要 | 盡量完整，允許少量遺失 | 分鐘級即可 |
| 行程與車資 | 小 | 高，是計費與司機收入的依據 | 精確、可稽核 | T+1 或小時級 |

三個主軸隨之確定：**把「事件流」轉成「目前狀態」的方法**（即時供需）、**時間與空間兩個維度下的儲存佈局**（軌跡），以及**生命週期很長、事後還會調整的事實表**（行程）。

## 二、0–10 分鐘：釐清與估算

> **候選人**：「先確認即時供需的定義。『供給』是指某個區域內目前空車且在線的司機數嗎？『需求』是指叫車請求嗎？」
>
> **面試官**：「供給是的。需求用過去幾分鐘內該區域的叫車請求數。」
>
> **候選人**：「區域是怎麼劃分的？行政區，還是固定的格網？」
>
> **面試官**：「目前是營運手動畫的區塊，我們想改掉，你可以提議。」
>
> **候選人**：「定價服務需要多新的資料？如果資料管線落後了，它寧可拿到舊資料，還是寧可知道資料不可用？」
>
> **面試官**：「30 秒內的資料。超過的話，定價服務應該退回基本價格，不要用過時的數字。」
>
> **候選人**：「軌跡要保存多久？主要用途是什麼？」
>
> **面試官**：「乘客爭議車資時要能調出該趟行程的路徑，爭議期是 90 天。另外資料科學團隊用它訓練到達時間的模型。」
>
> **候選人**：「行程的車資在行程結束後還會變動嗎？」
>
> **面試官**：「會。小費可以事後給，也會有退款與調整。」

**評註**：「落後時要舊資料還是要知道不可用」這個問題，直接問出了即時路徑的降級行為，也讓後面「跳過舊資料」的設計有了依據。供給與需求的精確定義，則是後面狀態設計的前提。

估算（假設每筆位置更新約 200 bytes、全日平均在線司機 40 萬、每日 2,000 萬趟行程）：

```
peak updates/s    = 1,000,000 drivers / 4 s        = 250,000 /s  (50 MB/s)
avg updates/s     = 400,000 / 4 s                  = 100,000 /s
points/day        = 100,000 × 86,400               ≈ 8.6 billion
raw size/day      = 8.6B × 200 B                   ≈ 1.7 TB
Parquet/day       = 1.7 TB / 8 (assumed, sorted)   ≈ 215 GB
90 days           = 215 GB × 90                    ≈ 19 TB

trips/day         = 20,000,000    (≈ 230 /s average)
```

> **候選人**：「位置更新尖峰每秒 25 萬筆，是整個系統的量體所在；行程每秒只有幾百筆。兩者差了三個數量級，應該走完全不同的路徑。壓縮比我假設 8 倍，因為依司機與時間排序後，相鄰的座標與時間戳差異很小，差值編碼的效果很好——這個數字要用真實資料驗證。」

## 三、10–15 分鐘：區域劃分與資料契約

> **候選人**：「區域我建議用六邊形格網取代手畫區塊。每個位置依固定的解析度對應到一個格子編號，全球一致，不需要人工維護。」

| 解析度（H3） | 單格平均面積 | 邊長約 | 適合 |
|---|---|---|---|
| 7 | 約 5.2 km² | 1.2 km | 郊區、低密度區域 |
| 8 | 約 0.74 km² | 0.46 km | 市區供需的預設粒度 |
| 9 | 約 0.11 km² | 0.17 km | 機場、車站等熱點的細分 |

> **候選人**：「我以解析度 8 作為預設。一個一千平方公里的城市大約是一千三百多個格子，司機步行距離與上車點的精度也大致在這個尺度。六邊形的好處是每個格子到六個鄰居的距離相等，做鄰近區域的平滑時比方格單純。
>
> 接著是位置事件的契約：」

```
driver_id     string
seq           long       -- 裝置端遞增序號
device_time   timestamp  -- 裝置時間
ingest_time   timestamp  -- 收集端時間
lat, lng      double
accuracy_m    float      -- 定位精度（公尺）
speed_mps     float
status        string     -- OFFLINE / AVAILABLE / EN_ROUTE / ON_TRIP
trip_id       string     -- 行程中才有值
cell_r8       string     -- 收集端算好的格子編號
```

> **候選人**：「三個重點。`seq` 用來判斷新舊：行動網路會讓封包亂序，Kafka 只保證到達順序，所以下游要丟棄序號比已見過的更小的更新。`status` 隨位置一起回報，因為供給的定義需要它。`cell_r8` 在收集端就算好，下游不必重複做座標轉換。」

**評註**：候選人主動區分了「Kafka 的到達順序」與「裝置端的實際順序」，並用序號處理。這是前幾篇反覆出現的陷阱，在行動裝置的情境中特別明顯。

## 四、15–25 分鐘：架構與三個演進階段

```
╔══════════════════════════════════════════════════════════════════════╗
║  Phase 1  Latest position in a key-value store (one city)            ║
╚══════════════════════════════════════════════════════════════════════╝

┌─────────┐ location ┌──────────────┐  every 30 s   ┌─────────────────┐
│ Driver  │─────────▶│ Redis GEO    │──────────────▶│ count drivers   │
│ app     │          │ latest only  │  scan zones   │ per manual zone │
└─────────┘          └──────────────┘               └─────────────────┘
```

**可行的範圍**：單一城市、數萬名司機。**失效的原因**：每 30 秒掃描所有區域的成本隨司機數與區域數成長；只有最新位置，沒有歷史軌跡；區塊要人工維護。

```
╔══════════════════════════════════════════════════════════════════════╗
║  Phase 2  Stream to state + archive (target design)                  ║
╚══════════════════════════════════════════════════════════════════════╝

┌─────────┐      ┌───────────┐      ┌────────────────────┐
│ Driver  │─────▶│ Collector │─────▶│ Kafka: locations   │
│ app     │      │ + cell id │      │ key = driver_id    │
└─────────┘      └───────────┘      └───┬────────────┬───┘
                                        │            │
              real-time path            │            │  archive path
                                        ▼            ▼
                         ┌──────────────────┐  ┌──────────────────────┐
                         │ Flink            │  │ S3 trajectories      │
                         │ per-driver state │  │ by date, sorted by   │
                         │ -> cell deltas   │  │ driver_id, time      │
                         └────────┬─────────┘  └──────────────────────┘
                                  ▼
┌──────────────┐  read   ┌──────────────────┐
│ Pricing      │◀────────│ Cell gauges      │   supply, demand, updated_at
│ service      │         │ (Redis)          │
└──────────────┘         └──────────────────┘

┌──────────────┐  CDC    ┌──────────────────┐
│ Trip DB      │────────▶│ Lakehouse: trips │   separate, exact path
└──────────────┘         └──────────────────┘
```

> **候選人**：「位置流分成兩條路徑。即時路徑把事件流轉成每個格子的供需數值，寫入鍵值儲存供定價服務讀取；歸檔路徑把所有點寫入資料湖。行程資料完全獨立，從行程資料庫以 CDC 同步，因為它是計費依據，要求與位置資料不同。」

| | Phase 1 | Phase 2 | Phase 3 |
|---|---|---|---|
| 區域 | 手畫區塊 | 固定六邊形格網 | 依密度使用不同解析度 |
| 供需計算 | 定時掃描 | 串流狀態差量 | 加上鄰近格子的平滑與定期全量校正 |
| 軌跡 | 無 | 全量歸檔 90 天 | 分層：行程中全量、其餘降採樣 |
| 行程資料 | 直接查交易資料庫 | CDC 到 lakehouse | 加上調整事實表與定價決策紀錄 |
| 部署 | 單一城市 | 單一區域 | 依地理區域分叢集 |

## 五、深挖一：從位置流算出每格的供給

> **面試官**：「每個格子的空車數怎麼算？用一分鐘的視窗數不重複的司機嗎？」
>
> **候選人**：「我不用視窗。供給是一個『現在的狀態』而不是『一段時間內發生的事件數』。用視窗計數有兩個問題：一名司機一分鐘內回報 15 次，要去重；更麻煩的是他在這一分鐘內可能從 A 格移到 B 格，或從空車變成載客，視窗結束時他到底該算在哪裡並不明確。
>
> 我的做法是把位置流轉成**狀態變更的差量**：」

```
keyed by driver_id: remember (last_cell, last_status, last_seq)

update arrives                         emitted deltas
───────────────────────────────────    ─────────────────────────────
seq too old                         →  drop
same cell, same status              →  nothing        (the common case)
cell A → cell B, still AVAILABLE    →  (A, −1), (B, +1)
AVAILABLE → ON_TRIP in cell B       →  (B, −1)
no update for 30 s (timer fires)    →  (last_cell, −1), clear state

keyed by cell: supply = running sum of deltas   ->  upsert to cell gauge
```

> **候選人**：「第一層依司機分組，只記住他上一次所在的格子與狀態；只有在格子或狀態改變時才送出差量。第二層依格子分組，把差量累加成目前的供給數，整個值覆寫到鍵值儲存。
>
> 這個設計讓資料量大幅下降。多數更新不會改變格子：解析度 8 的格子寬度約 0.9 公里，以市區時速 30 公里計算，司機大約每 100 秒才跨越一次。尖峰 100 萬名司機，跨格事件大約每秒一萬筆，是原始更新量的二十五分之一左右。」
>
> **面試官**：「司機的 App 當掉了，沒有送出離線訊息。」
>
> **候選人**：「所以每個司機的狀態都有一個計時器。超過 30 秒沒有收到更新，就視為離線，送出一筆負的差量並清除狀態。這也讓狀態大小有上限：只有在線的司機佔用狀態。」
>
> **面試官**：「差量累加會不會隨時間漂移？只要漏了一筆負的，那個格子就永遠多一台車。」
>
> **候選人**：「會，所以要有自我修正的機制。檢查點保證了正常情況下狀態與輸入位置一致，但程式缺陷或升級時的狀態不相容仍可能造成漂移。我會每隔幾分鐘從第一層的司機狀態直接重新計數一次，覆寫各格子的數值，讓任何累積誤差的壽命不超過幾分鐘。兩者的差異同時是一個監控指標：差異變大代表差量邏輯有問題。」

**評註**：候選人先說明為何不用面試官提議的做法，再提出狀態差量的設計，並用數字說明它帶來的縮減。面對漂移的追問，回答了預防（檢查點）、修正（定期全量重算）與偵測（差異指標）三層。

## 六、深挖二：落後時的取捨與熱點

> **面試官**：「即時作業落後了兩分鐘，你怎麼處理？」
>
> **候選人**：「這裡我會做一個和前幾題相反的選擇：**丟掉舊資料，直接處理最新的**。兩分鐘前的位置對定價沒有用，依序把它們處理完只會讓系統持續落後。
>
> 具體做法是在即時路徑的入口比較 `ingest_time` 與目前時間，超過門檻（例如 30 秒）的更新直接略過，只保留每名司機最新的一筆。這樣作業能在幾秒內追上現況。被略過的資料並沒有遺失，歸檔路徑是獨立消費同一個 topic 的，軌跡仍然完整。
>
> 另外，每個格子的數值都帶有 `updated_at`。定價服務讀取時檢查它，超過 30 秒就退回基本價格，如同您一開始說的。管線本身不替下游決定資料是否堪用，而是提供判斷所需的資訊。」
>
> **面試官**：「機場那一格的司機特別多，會不會成為熱點？」
>
> **候選人**：「我檢查過，在這個設計下不會。第一層依 `driver_id` 分組，分佈均勻。第二層依格子分組，但輸入已經是差量：即使機場有五千名司機，每秒進出的差量也只有幾十筆。真正的傾斜發生在『直接依格子聚合原始位置』的設計中，那時機場格每秒會收到上千筆更新。
>
> 機場的問題其實在別處：一格 0.74 平方公里對機場太粗，航廈與等候區的供需完全不同。所以熱點地區改用解析度 9 的格子。」
>
> **面試官**：「司機剛好在兩格的邊界來回移動呢？」
>
> **候選人**：「會造成兩格的供給數值來回跳動。定價不應該只看單一格子，而是把目標格與周圍一圈六個格子加權合計，邊界上的移動在合計中互相抵銷。這個平滑在讀取端或在寫入前計算都可以；我傾向在管線中算好，讓定價服務一次讀取就拿到結果。」

**評註**：「丟掉舊資料」在支付或計費題中是錯誤答案，在這裡卻是正確答案；候選人明確指出這個選擇與前幾題相反，並說明原因與安全邊界（歸檔路徑不受影響）。面對熱點的追問，回答「我檢查過，這裡不會」並指出真正的問題所在，比直接套用加鹽等技巧更有說服力。

## 七、深挖三：軌跡儲存與行程建模

> **面試官**：「軌跡每天 86 億個點，你怎麼存？乘客爭議時要調出某一趟行程的路徑。」
>
> **候選人**：「查詢模式決定佈局。最重要的查詢是『某一趟行程的完整路徑』，也就是某位司機在某段時間內的所有點。所以我依日期分區，分區內依 `driver_id` 與時間排序。這樣一趟行程的點在檔案中是連續的，查詢靠統計值跳過絕大多數檔案；同時相鄰點的差異很小，壓縮效果最好。
>
> 我不會用格子當分區鍵。格子的數量是幾十萬個，會產生大量的小分區；而且一趟行程會跨越很多格子，調出路徑反而要讀很多分區。空間分析的需求，例如各格各小時的平均車速，我會另外產生一張聚合表，而不是為了它改變原始資料的佈局。」
>
> **面試官**：「19 TB 不算多，但資料科學家想保留兩年。」
>
> **候選人**：「那就分層保存，依用途決定精度。」

| 資料 | 精度 | 保留 | 理由 |
|---|---|---|---|
| 行程中的點 | 原始 4 秒 | 90 天 | 爭議期內要能還原路徑 |
| 行程中的點 | 降採樣到約 30 秒 | 2 年 | 模型訓練不需要 4 秒精度 |
| 非行程中的點 | 原始 4 秒 | 7 天 | 僅供問題排查 |
| 各格各小時的聚合 | 聚合值 | 長期 | 體積小，支援長期趨勢分析 |

> **面試官**：「行程的資料表怎麼設計？」
>
> **候選人**：「行程有明確的生命週期：請求、司機接單、抵達上車點、開始、結束或取消。我用一張以**一趟行程為一列**的事實表，每個里程碑一個時間欄位，隨著行程推進逐步填入。」

```
fact_trip (grain: one row per trip request)
┌──────────┬──────────────┬─────────────┬────────────┬──────────────┐
│ trip_id  │ requested_at │ accepted_at │ started_at │ completed_at │ ...
│ rider_key│ driver_key   │ pickup_cell │ drop_cell  │ cancel_reason│
│ distance │ duration     │ base_fare   │ surge_mult │ status       │
└──────────┴──────────────┴─────────────┴────────────┴──────────────┘
        updated by MERGE on trip_id as milestones arrive

fact_trip_adjustment (grain: one row per adjustment, append-only)
┌──────────┬───────────────┬──────────┬──────────────┬─────────────┐
│ trip_id  │ adjustment_id │ type     │ amount_minor │ recorded_at │
└──────────┴───────────────┴──────────┴──────────────┴─────────────┘
        tip / refund / fare correction -> never rewrites fact_trip fares
```

> **候選人**：「兩個設計決定。里程碑欄位會被更新，所以這張表以 `trip_id` 做 MERGE，並比較來源的版本，避免較舊的變更蓋掉較新的狀態。金額則不更新：行程結束時的車資寫入後不再改動，小費、退款與更正都記在另一張只追加的調整表。司機的實際收入是兩張表的合計，而任何一天結算時的金額都可以用 `recorded_at` 重現。
>
> 另外，報表的『一天』要用城市的當地日期。時間戳一律存 UTC，另存一個依城市時區換算的當地日期欄位作為報表的日期鍵，否則跨時區的城市合計會在午夜前後錯位。」

**評註**：軌跡佈局從最重要的查詢出發，並說明為何不選看似自然的空間分區。行程表混用了「里程碑可更新」與「金額不可改、另記調整」兩種策略，與 Part 6 的原則一致。

## 八、為什麼選 X 不選 Y

| 選擇 | 選 X 的理由 | 不選 Y 的理由 | 翻轉條件 |
|---|---|---|---|
| 六邊形格網 vs 手畫區塊或行政區 | 全球一致、免維護、鄰居等距、可換解析度 | 手畫區塊要人工維護，大小不一，難以跨城市比較 | 法規或營運規則以行政區為單位（例如機場專屬費率區）時，另外維護對照表 |
| 狀態差量 vs 視窗內計數 | 直接得到「目前狀態」；下游資料量降到約二十五分之一 | 視窗計數要去重，且無法處理視窗內跨格或換狀態 | 要算的是事件數而非狀態（例如過去五分鐘的叫車請求數），視窗才是對的 |
| 落後時跳過舊位置 vs 依序處理全部 | 幾秒內回到最新狀態；舊位置對定價無價值 | 依序處理會讓落後持續，下游長時間拿到過時資料 | 資料逐筆有價值時（計費、行程事件）絕對不能跳過 |
| 位置與行程走不同路徑 vs 統一管線 | 各自使用符合其性質的保證等級與成本 | 統一管線會讓位置付出精確的成本，或讓行程只有近似的保證 | 無；兩者的量與價值差距太大 |
| 軌跡依日期分區並依司機排序 vs 依格子分區 | 一趟行程的點連續存放；分區數少；壓縮率高 | 格子分區產生大量小分區，取一趟行程要跨多個分區 | 主要查詢是「某區域在某時段的所有軌跡」且很少依行程查詢 |
| 分層保留與降採樣 vs 全量保留兩年 | 儲存成本降一個量級，仍滿足各用途的精度 | 全量 4 秒資料保留兩年，多數從未被讀取 | 法規要求保留原始精度 |
| 里程碑事實表 + 調整表 vs 每個狀態一列的事件表 | 一列即可算出各階段耗時；金額歷史不被覆寫 | 純事件表每次分析都要把多列轉成一列 | 需要分析每一次狀態轉換本身（例如重複派單）時，保留事件表作為 Silver 層 |
| 定期全量校正 vs 完全信任差量 | 累積誤差的壽命有上限，並提供偵測訊號 | 差量一旦漏失，錯誤會永久存在 | 無；校正成本低，沒有理由省略 |

## 九、常見追問與回答要點

**「GPS 訊號漂移或瞬間跳到幾公里外？」**
在收集端或串流入口做合理性檢查：由前後兩點的距離與時間差算出速度，超過不合理的門檻（例如時速 200 公里）就不採用該點作為即時位置；定位精度欄位過差的點同樣略過。原始點仍然歸檔，並標記為異常，讓離線分析決定如何處理。

**「定價被質疑不公平，要說明某次報價為何是那個倍率？」**
供需數值是不斷被覆寫的，事後無法還原。所以每一次報價都要寫一筆不可變的決策紀錄：時間、格子、當時讀到的供給與需求、倍率、使用的規則或模型版本。這張表資料量與行程同級，保留期比照財務紀錄。

**「要測試新的定價演算法，怎麼用歷史資料驗證？」**
把歸檔的位置與請求事件依原始時間順序重播進同一個串流作業的另一個實例，產生「如果當時用新演算法」的供需與倍率。這需要作業以事件時間運作，而不是處理時間，否則重播的結果與當時不同。

**「多個國家要不要共用一個叢集？」**
傾向依地理區域分開。位置資料的延遲要求高，就近處理較快；各地對位置資料的儲存地點也可能有法規要求；一個區域的故障或流量尖峰不會影響其他區域。跨區域的分析在資料湖層以彙整後的資料進行。

**「需求用叫車請求數，會不會低估？有人看到價格就離開了。」**
會，這是指標定義的問題。只計已送出的請求會漏掉看到高價而放棄的使用者，使高價時的需求被低估。較完整的訊號是「輸入目的地並看到報價」的工作階段數。這應該在釐清階段與面試官確認，因為它改變了需要收集的事件。

**「位置資料的隱私怎麼處理？」**
位置是高度敏感的個人資料。分析用的表只保留格子層級的位置；精確座標限制在需要它的用途（爭議處理）並記錄每次存取；上下車點在分析資料中降低精度；保留期依用途設定並自動刪除。

## 十、系統效應與系列導航

從 Phase 1 到 Phase 2 的前後對照，沿用前文的假設；標示為目標的是設計目標。

| 指標 | 改造前（鍵值儲存 + 定時掃描） | 改造後（狀態差量 + 歸檔） |
|---|---|---|
| 供需資料新鮮度 | 30 秒以上，隨規模惡化 | 數秒（目標） |
| 供需計算的輸入量 | 每次掃描所有司機 | 每秒約一萬筆跨格與狀態變更事件 |
| 區域維護 | 人工畫區 | 固定格網，無需維護 |
| 管線落後時的行為 | 無明確定義 | 跳過舊位置；數值附更新時間，逾時由下游降級 |
| 歷史軌跡 | 無 | 行程中 4 秒精度保留 90 天，可依行程調閱 |
| 行程金額的事後變更 | 覆寫原資料 | 另記調整，原金額與歷史可重現 |
| 新增的維運工作 | 無 | 串流作業與其狀態、定期校正、軌跡分層與降採樣作業 |

**本篇重點**

- 先依「單筆價值」分類資料：位置寧新勿全，行程與車資必須精確，兩者分開處理。
- 「目前有幾台空車」是狀態而非事件數；用每位司機的狀態差量維護，並以計時器處理無聲離線。
- 差量會漂移，搭配定期全量校正，差異本身就是監控指標。
- 落後時跳過舊位置，並讓每個數值帶更新時間，由下游決定是否降級。
- 軌跡佈局從最重要的查詢出發；行程表的里程碑可更新，金額不可改、另記調整。
