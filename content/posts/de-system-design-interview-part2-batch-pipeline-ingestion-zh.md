> 多數人設計批次管線時，想的是「怎麼讓它每天跑成功」。  
> 上線三個月後真正花時間的卻是：「上週二的資料錯了，怎麼只重跑那一天而不弄壞別的？」  
> 好的批次設計不以跑通為目標，而以**任何一天都能安全重跑、重跑幾次結果都一樣**為目標。  
> 面試官問 pipeline，其實是在問你怎麼處理它失敗之後的事。

這是系列的第二篇。[Part 1](/posts/de-system-design-interview-part1-framework-fundamentals-zh/) 建立了答題框架與基本功；本篇處理面試中出現頻率最高的題型——**把資料從來源系統搬到分析系統的批次管線**。讀完你應該能說明三種擷取方式各自何時失效、怎麼讓管線可重跑，以及 Spark 作業變慢時先看哪個訊號。

## 面試情境

> **面試官**：「我們的訂單系統跑在 MySQL 上，大約 200 張表，最大的 `orders` 表有 20 億筆、約 300 GB，每天約 2,000 萬筆新增或更新。分析團隊要求每天早上 6 點前能在資料湖查到昨天為止的完整資料。請設計這條同步管線，並說明如果某一天的資料出錯，你怎麼修。」

---

## 一、核心問題：管線的難處在重跑

把一張表從 A 複製到 B 並不難。難的是下面四件事同時成立：

1. **來源會變**：資料列會被更新、被刪除，schema 會加欄位。
2. **作業會失敗**：跑到一半節點掛掉，留下寫了一半的輸出。
3. **邏輯會改**：三個月後發現轉換邏輯有錯，要重算歷史資料。
4. **下游在等**：早上 6 點有人要看報表，晚了或錯了都算事故。

這四件事指向同一個設計原則，也是本篇的主軸：

> **每個作業都是「輸入分區 → 輸出分區」的純函數。相同輸入重跑任意次，輸出相同，而且寫入是原子的。**

做到這一點，失敗就只是「再跑一次」，回補就只是「對一段日期各跑一次」。做不到，每次事故都需要人工清理。

先用情境的數字定出規模（假設每筆變更約 150 bytes）：

```
orders total        = 2,000,000,000 rows ≈ 300 GB
daily changes       = 20,000,000 rows    ≈ 3 GB      (1% of the table)
full dump, 1 thread = 2B / 50,000 rows/s ≈ 11 hours  (assumed JDBC rate)
full dump, 16 way   ≈ 45 minutes, but heavy load on the source replica
incremental         = 20M / 50,000 rows/s ≈ 7 minutes
```

每天只有 1% 的資料在變，卻搬 100% 的資料，這就是全量匯出撐不久的原因。`50,000 rows/s` 是單一 JDBC 連線讀取窄表的假設值，實際取決於列寬與網路，面試時說明這是假設即可。

## 二、三個演進階段

```
╔══════════════════════════════════════════════════════════════════════╗
║  Phase 1  Full dump (POC, total data < ~50 GB)                       ║
╚══════════════════════════════════════════════════════════════════════╝

┌──────────────┐  SELECT * (nightly cron)  ┌──────────────────────────┐
│ MySQL replica│──────────────────────────▶│ S3  /orders/dt=2026-11-20│
└──────────────┘                           │     full snapshot Parquet│
                                           └──────────────────────────┘
```

**作法**：每晚從唯讀副本整張表讀出，寫成當天的快照分區。

**優點**：最簡單，而且天生冪等——重跑就是再覆寫一次快照。刪除也自動正確，因為被刪掉的列不會出現在新快照裡。

**要注意的限制**：用多條連線平行切段讀取時，每條連線看到的是各自的時間點，合起來可能是來源從未存在過的狀態（例如一筆交易的兩張表只讀到一半）。需要一致的快照時，在暫停套用複寫的副本上讀取，讓所有連線對齊同一個位置；否則就要明講這份快照只有「近似某一時刻」的保證。

**何時失效**：表超過數十 GB 之後，匯出時間與副本負載都撐不住；每天存一份快照，以未壓縮的 300 GB 計一年是 110 TB。

```
╔══════════════════════════════════════════════════════════════════════╗
║  Phase 2  Incremental + merge (MVP, most tables fit here)            ║
╚══════════════════════════════════════════════════════════════════════╝

┌──────────────┐ WHERE updated_at >= :lo   ┌───────────────┐
│ MySQL replica│ AND updated_at < :hi      │ S3 raw delta  │
│              │──────────────────────────▶│ dt=2026-11-20 │
└──────────────┘                           └───────┬───────┘
                                                   │ MERGE on order_id
   ┌───────────────────────┐                       ▼
   │ Airflow: schedule,    │              ┌─────────────────────┐
   │ retry, backfill, SLA  │─ ─ ─ ─ ─ ─ ─▶│ Lake table (Iceberg)│
   └───────────────────────┘              │ current state       │
                                          └─────────────────────┘
```

**新增元件**：`updated_at` 水位線、原始增量層、以主鍵 MERGE 的目標表、排程器。

**解決**：每天只搬 1% 的資料，7 分鐘內完成擷取。

**仍存在的問題**：抓不到實體刪除；依賴應用程式確實維護 `updated_at`；一天內多次變更只看得到最後狀態。

```
╔══════════════════════════════════════════════════════════════════════╗
║  Phase 3  Log-based CDC (scale, or when deletes/history matter)      ║
╚══════════════════════════════════════════════════════════════════════╝

┌────────┐ binlog ┌──────────┐      ┌────────────┐      ┌─────────────┐
│ MySQL  │───────▶│ Debezium │─────▶│ Kafka (MSK)│─────▶│ S3 changelog│
└────────┘        └──────────┘      │ 1 topic per│      │ append-only │
                                    │ table      │      └──────┬──────┘
                                    └────────────┘             │ hourly
                                                               │ MERGE
   ┌─────────────────────────┐                                 ▼
   │ Reconciliation job:     │                        ┌─────────────────┐
   │ count + checksum vs src │◀───────────────────────│ Lake table      │
   └─────────────────────────┘                        │ (Iceberg)       │
                                                      └─────────────────┘
```

**新增元件**：CDC 連接器、訊息佇列、只追加的變更日誌層、對帳作業。

**解決**：刪除與每一次中間變更都拿得到；對來源的負載接近零（只讀日誌）；新鮮度可以從每日縮短到每小時甚至分鐘級。

**代價**：多了三個需要維運的元件。連接器斷線、日誌被來源清掉、schema 變更，都是新的失敗模式。

三個階段的對照：

| | Phase 1 全量 | Phase 2 增量 | Phase 3 CDC |
|---|---|---|---|
| 每日搬運量（orders） | 300 GB | 約 3 GB | 約 3 GB |
| 擷取時間 | 45 分鐘–11 小時 | 約 7 分鐘 | 持續進行 |
| 抓得到刪除 | 是 | 否 | 是 |
| 抓得到中間狀態 | 否 | 否 | 是 |
| 來源負載 | 高 | 中（需索引） | 低 |
| 維運複雜度 | 低 | 中 | 高 |

面試中的好答案通常是**混合使用**：200 張表裡，小於 1 GB 的維度表繼續全量（簡單又正確），中型表用增量，只有 `orders` 這種又大又需要刪除語意的核心表走 CDC。這比「全部上 CDC」更能顯示判斷力。

## 三、擷取方式的細節陷阱

### 3.1 增量擷取的三個坑

用 `updated_at` 做水位線看起來簡單，面試官很可能追問它什麼時候會漏資料。

**坑一：實體刪除。** 被 `DELETE` 的列不會出現在任何 `WHERE updated_at >= ...` 的結果裡。解法是要求來源改用軟刪除（`is_deleted` 旗標），或定期做一次主鍵全量比對，或改用 CDC。

**坑二：長交易造成的遲到提交。** `updated_at` 在語句執行時就定了，但資料要到交易提交後才看得見。

```
time ───────────────────────────────────────────────────────────▶
        23:58                  00:00            00:03
          │                      │                │
txn A:  UPDATE (updated_at=23:58) ................ COMMIT
                                 │
extract job reads [yesterday 00:00, today 00:00) at 00:01
                                 └─ row A not visible yet  -> MISSED
next run reads [today 00:00, ...)  -> updated_at=23:58 is out of range
```

解法是**重疊視窗（lookback）**：每次擷取往回多讀一段，例如 `updated_at >= :lo - 15 分鐘`，並靠 MERGE 的冪等性吸收重複。視窗長度要大於來源最長交易時間。

**坑三：`updated_at` 沒有索引或不可靠。** 沒有索引時每次增量都是全表掃描；批次修補資料的 SQL 忘了更新 `updated_at` 則會靜默漏資料。這是該主動向面試官確認的假設。

### 3.2 CDC 的運作方式

**直覺**：與其每天問資料庫「你有什麼變了？」，不如直接讀資料庫自己寫給副本看的那本日記。

**機制**：MySQL 的 binlog（PostgreSQL 則是 WAL）依序記錄每一筆已提交的變更。Debezium 這類連接器偽裝成一個副本去讀它，把每筆變更轉成一則訊息，包含操作類型（insert / update / delete）、變更前後的值，以及日誌位置。

啟動時連接器先做一次**初始快照**讀出全表現況，再從快照當時的日誌位置接續讀取，兩段之間不漏不重疊。

**限制**，也是面試加分點：

- **日誌保留期**：連接器停機超過 binlog 保留時間，就接不回去，只能重做快照。保留期至少設為你能容忍的最長修復時間（例如 3–7 天）。
- **順序保證**：同一筆資料的變更必須依序套用。Kafka 只保證分區內有序，所以訊息 key 要用主鍵。
- **Schema 變更**：來源加欄位時，下游要能相容。通常搭配 schema registry 並規定只做向後相容的變更（加可為空的欄位）。
- **受管替代方案**：在 AWS 上不想自己維運連接器時，DMS 可以做同樣的事，功能較少但維運負擔低。

## 四、ETL 與 ELT

兩者的差別只有一個：**轉換發生在載入目標系統之前還是之後**。

| | ETL | ELT |
|---|---|---|
| 順序 | 擷取 → 轉換 → 載入 | 擷取 → 載入 → 轉換 |
| 轉換在哪跑 | 獨立的運算引擎（Spark、Glue） | 目標倉儲或湖上的 SQL 引擎 |
| 原始資料 | 通常不保留 | 完整保留在落地層 |
| 改邏輯後重算 | 要重新向來源擷取 | 直接從原始層重跑 SQL |
| 轉換語言 | 程式碼（Python / Scala） | SQL（常搭配 dbt） |

現代資料平台偏向 ELT，原因有二：儲存已經便宜到可以把原始資料全部留下（Part 1 算過，34 TB 每月數百美元）；而保留原始資料正是「邏輯改了可以重算」的前提，與本篇的可重跑主軸一致。

ETL 仍然是正確選擇的情況：

- **個資必須在落地前移除或遮罩**，合規不允許原始資料進入資料湖。
- **資料需要重度的非 SQL 處理**，例如解析二進位格式、影像、複雜的工作階段切分。
- **目標系統的運算很貴**，在外部先過濾聚合可以省下大量費用。

面試時不要把這題答成二選一。實務上是分層混用：擷取後原樣落地（EL），在湖上用 Spark 做重度清洗（T），再於倉儲內用 SQL 建立資料模型（T）。

## 五、冪等寫入與回補

這一節是本篇最重要的部分。先看錯誤的寫法為什麼錯：

```sql
-- 錯誤：重跑一次，當天資料就多一倍
INSERT INTO daily_revenue
SELECT order_date, SUM(amount) FROM orders
WHERE order_date = CURRENT_DATE - 1
GROUP BY order_date;
```

兩個問題：`INSERT` 會累加，重跑造成重複；`CURRENT_DATE` 讓作業的行為取決於「什麼時候執行」，三天後補跑會算到錯的日期。

修正後的寫法遵循兩條規則：

```sql
-- 規則一：日期由排程器以參數傳入，不讀系統時鐘
-- 規則二：覆寫整個輸出分區，而不是追加
INSERT OVERWRITE TABLE daily_revenue PARTITION (dt = '{{ ds }}')
SELECT SUM(amount) FROM orders
WHERE order_date = '{{ ds }}';
```

`{{ ds }}` 是 Airflow 傳入的邏輯日期。同一個邏輯日期不論何時執行、執行幾次，都讀同一段輸入、覆寫同一個輸出分區。

這裡有一個前提：**輸入本身必須不可變**。如果 `orders` 是會被持續更新的「目前狀態」表，一張訂單的金額在第一次執行後由 10 改成 20，重跑同一個日期就會算出不同的歷史數字——日期相同不代表輸入相同。所以作業應該讀取該日期保留下來的快照分區，或用 table format 的時間旅行指定當時的版本。

```
           logical date = 2026-11-18 (a parameter, not the clock)
                               │
  input partition              ▼               output partition
┌───────────────────┐   ┌─────────────┐   ┌──────────────────────┐
│ orders            │──▶│  transform  │──▶│ daily_revenue        │
│ dt=2026-11-18     │   │ (pure func) │   │ dt=2026-11-18        │
└───────────────────┘   └─────────────┘   │ atomic OVERWRITE     │
                                          └──────────────────────┘
  run once, run 5 times, run next month  ->  same bytes out
```

三種冪等寫入手法的選擇：

| 手法 | 適用 | 注意 |
|---|---|---|
| 分區覆寫 | 輸出可依日期切開的事實表與聚合表 | 寫入必須原子；直接寫 S3 路徑在失敗時會留下半成品，要用 table format 的原子提交 |
| 以鍵 MERGE | 維護「目前狀態」的表（如同步後的 `orders`） | 要有穩定主鍵；同一批內同鍵多筆時先取最新一筆再 MERGE；並比較來源版本（日誌位置或 `updated_at`），只在來源較新時覆寫，否則重播較舊的批次會蓋掉較新的狀態；刪除以墓碑記錄保留，才不會被舊批次「復活」 |
| 先刪後寫 | 不支援前兩者的舊系統 | 刪與寫要在同一個交易內，否則中間有空窗 |

**回補（backfill）**在這個設計下只是迴圈：對 2026-08-01 到 2026-10-31 的每一天各執行一次同樣的作業。幾個實務細節值得在面試中提：

- **限制並行度**：92 天同時跑會壓垮叢集與來源；設定同時最多 4–8 個。
- **與每日排程隔離資源**：回補用獨立的佇列或叢集，不能讓它擠掉今天早上 6 點要交付的作業。
- **下游連鎖**：重算了上游表，依賴它的下游表也要重算。排程器要能「清除某個任務及其所有下游」。
- **晚到資料**：如果事件會晚到好幾天，每日作業除了處理 T-1，還要重新處理 T-2、T-3 的分區（例如固定重跑最近 3 天），冪等覆寫讓這件事是安全的。

## 六、Spark 必考：Shuffle、Join 與傾斜

批次運算引擎的面試題幾乎都繞著同一個詞：**shuffle**。

**直覺**：把一疊依到貨順序堆放的訂單，改成依客戶分堆。每一張都要被拿起來、看一眼、丟到對應的堆——所有資料都得跨機器移動一次。

**機制**：`GROUP BY`、`JOIN`、`DISTINCT`、視窗函數都需要相同 key 的資料落在同一個分區。Spark 為此把每筆資料依 key 的雜湊寫到本地磁碟的對應檔案，再由下一個 stage 透過網路拉取。這一步同時吃磁碟、網路與序列化的 CPU，通常是作業中最慢的部分。

```
Stage 1 (map side)                     Stage 2 (reduce side)
┌───────────┐                          ┌───────────┐
│ task 1    │─┐   hash(key) % P      ┌▶│ part 0    │  40 MB
├───────────┤ │  ┌────────────────┐  │ ├───────────┤
│ task 2    │─┼─▶│ shuffle files  │──┼▶│ part 1    │  45 MB
├───────────┤ │  │ disk + network │  │ ├───────────┤
│ task 3    │─┘  └────────────────┘  └▶│ part 2    │  9.6 GB  <- skew
└───────────┘                          └───────────┘
                         job time = slowest partition, not the average
```

### 6.1 Join 策略

| 策略 | 何時使用 | 成本 |
|---|---|---|
| Broadcast hash join | 一邊夠小（預設門檻 10 MB，可調高到數百 MB） | 無 shuffle；小表被送到每個 executor |
| Sort-merge join | 兩邊都大 | 兩邊都 shuffle 並排序 |
| Shuffle hash join | 兩邊都大但一邊每個分區放得進記憶體 | shuffle 但不排序 |

事實表 join 維度表是最常見的情況，維度表通常放得進記憶體，所以**讓它走 broadcast 是成本最低的最佳化**。要注意的是門檻看的是 Spark 估計的大小；估計不準時可以用 hint 明確指定。

### 6.2 傾斜的診斷與處理

症狀很固定：Spark UI 的 stage 頁面上，200 個 task 中 199 個在 30 秒內結束，剩下 1 個跑了 40 分鐘；它的 shuffle read size 是中位數的上百倍。

處理順序由便宜到貴：

1. **先確認是不是髒資料**。最常見的傾斜 key 是 `NULL` 或空字串——幾千萬筆沒有 `user_id` 的事件全部雜湊到同一個分區。把它們過濾掉或分開處理，問題常常就消失了。
2. **開啟 AQE 的傾斜處理**。Spark 3.2 起 Adaptive Query Execution 預設開啟，對 join 會在執行期把過大的分區拆開處理（預設判定：分區大於中位數 5 倍且超過 256 MB）。這只適用於 join；`GROUP BY` 的傾斜要改用兩階段聚合（先在加鹽後的 key 上聚合，再去鹽合併）。
3. **讓小的那邊 broadcast**，直接避開 shuffle。
4. **join 的加鹽**。熱 key 那一邊加上隨機後綴 0–N，另一邊複製 N 份對應，join 後再去掉後綴。有效但會放大資料量，留作最後手段。

### 6.3 分區數與小檔案

`spark.sql.shuffle.partitions` 預設是 200，這個值對多數真實作業不是太大就是太小。經驗法則是**每個分區 100–200 MB**：一個 shuffle 300 GB 的 stage 需要約 2,000 個分區；一個只有 2 GB 的作業用 200 個分區，會產生 200 個 10 MB 的小檔案。AQE 會自動合併過小的分區，但輸出檔案的大小仍然值得明確控制。

小檔案是資料湖上最常見的慢性病。10 萬個 1 MB 的檔案和 800 個 128 MB 的檔案資料量相同，但前者光是列出檔案與開檔的時間就可能超過實際讀取資料的時間。處理方式是寫入前重新分區到目標檔案大小，並對既有資料定期做合併（compaction），Part 4 會再回到這個主題。

## 七、排程與相依管理

排程器（Airflow、Dagster、Step Functions、MWAA）在設計中負責四件事：**什麼時候跑、依什麼順序跑、失敗了怎麼辦、有沒有準時**。

情境中的每日管線可以畫成這樣的相依圖：

```
┌──────────────┐   ┌──────────────┐   ┌─────────────┐   ┌─────────────┐
│ extract      │──▶│ merge into   │──▶│ quality     │──▶│ publish     │
│ orders delta │   │ staging      │   │ checks      │   │ (swap ptr)  │
└──────────────┘   └──────────────┘   └──────┬──────┘   └──────┬──────┘
┌──────────────┐          ▲                  │ fail            │
│ extract dims │──────────┘                  ▼                 ▼
└──────────────┘                      ┌─────────────┐   ┌─────────────┐
                                      │ alert, stop │   │ downstream  │
                                      │ keep T-1    │   │ marts       │
                                      └─────────────┘   └─────────────┘
```

設計時要交代的幾個決定：

**重試策略。** 暫時性錯誤（網路抖動、spot 節點被回收）自動重試 2–3 次並採指數退避；確定性錯誤（schema 不符、資料品質不過）不該重試，直接告警。能區分這兩類是面試加分點。

**相依的觸發方式。** 依時間觸發（「上游通常 2 點跑完，我 3 點開始」）很脆弱，上游晚一小時就會讀到不完整的資料。應該依**資料就緒**觸發：等上游任務成功，或等上游分區的完成標記出現。

**SLA 與時間預算。** 6 點要交付，就從 6 點倒推。若整條鏈正常要 90 分鐘，並保留一次完整重跑的時間，最晚啟動時間是 3 點；若上游資料 1 點才齊，餘裕是 2 小時。把這個算式講出來，比只說「我會設定 SLA 告警」有說服力得多。

**排程器只排程，不運算。** 常見的錯誤是在 Airflow worker 裡用 pandas 處理資料。排程器應該只負責提交作業到 Spark、倉儲或容器，自己不持有資料，這樣它的失敗不會影響資料正確性。

## 八、資料品質與發佈閘門

沒有品質檢查的管線，壞資料會一路流到主管的儀表板，然後由主管來通知你。檢查分四類，成本由低到高：

| 類別 | 例子 | 抓到什麼 |
|---|---|---|
| Schema | 欄位存在、型別正確 | 上游改了欄位 |
| 完整性 | 主鍵非空且唯一；外鍵對得到 | 重複載入、join 遺失 |
| 數量 | 今日筆數在過去 7 日平均的 ±30% 內 | 擷取只跑了一半、來源停擺 |
| 業務規則 | 金額 ≥ 0；訂單日期不在未來 | 轉換邏輯錯誤 |

對 CDC 管線還要加一項**對帳（reconciliation）**：定期比對來源與目標的筆數與某些欄位的總和（例如每日 `SUM(amount)`），用來發現「靜默漏資料」。筆數與總和只是粗篩：一筆多 5 元、另一筆少 5 元時兩者都對得上。需要完整性保證的表，再加上依主鍵分桶的雜湊比對，先找出不一致的桶，再逐筆核對。

檢查放在哪裡同樣重要。**Write–Audit–Publish（WAP）**模式把寫入與發佈分開：

```
 write                   audit                    publish
┌──────────────────┐    ┌──────────────────┐    ┌──────────────────────┐
│ write new data   │───▶│ run checks on    │───▶│ atomically move the  │
│ to a staging     │    │ the staging data │    │ "current" pointer to │
│ branch/partition │    │                  │    │ the new snapshot     │
└──────────────────┘    └────────┬─────────┘    └──────────────────────┘
                                 │ fail
                                 ▼
                 consumers keep reading yesterday's snapshot
```

資料先寫到下游看不到的地方，檢查通過才原子地切換。檢查失敗時，下游看到的是**昨天的正確資料**而不是今天的錯誤資料——「晚」通常比「錯」好處理得多。Iceberg 的分支功能與倉儲的 table swap 都能實作這個模式。

對於不合格的資料列，有兩種處理方式要依嚴重程度選擇：**擋下整批**（主鍵重複、筆數腰斬這類結構性問題）或**隔離個別資料列**到 quarantine 表並放行其餘（個別欄位格式錯誤）。全部擋下會讓管線太脆弱，全部放行則等於沒檢查。

## 九、為什麼選 X 不選 Y

| 選擇 | 選 X 的理由 | 不選 Y 的理由 | 翻轉條件 |
|---|---|---|---|
| CDC vs `updated_at` 增量（核心大表） | 抓得到刪除與中間狀態；來源負載低；可縮短新鮮度 | 增量漏刪除、受長交易與不可靠欄位影響 | 表只追加不更新、沒有刪除、團隊無人維運 Kafka 與連接器 |
| 全量快照 vs 增量（小維度表） | 天生冪等、自動處理刪除、零狀態 | 增量要為一張 10 MB 的表維護水位線，不值得 | 表超過數 GB 或匯出時間影響 SLA |
| ELT vs ETL | 保留原始資料，邏輯改了能重算；SQL 門檻低 | ETL 丟掉原始資料，重算得回頭找來源 | 個資必須在落地前遮罩；處理邏輯非 SQL 能表達 |
| 分區覆寫 vs 追加寫入 | 重跑冪等，回補只是迴圈 | 追加在重試時產生重複，需要事後去重 | 純追加的原始事件落地層，且下游以 `event_id` 去重 |
| 資料就緒觸發 vs 固定時間觸發 | 上游延遲時自動等待，不會讀到半成品 | 固定時間假設上游永遠準時 | 來源是外部系統、沒有任何就緒訊號可用，只能加緩衝時間 |
| WAP 發佈閘門 vs 寫完直接可見 | 壞資料不會被下游讀到 | 直接寫入時，檢查失敗前已有人讀到錯的數字 | 探索性資料、沒有下游依賴、延遲比正確重要 |
| Spark vs 倉儲內 SQL（轉換） | 能處理半結構化與非 SQL 邏輯；運算與儲存可分開擴充 | 倉儲內做重度清洗成本高且難測試 | 資料已結構化、轉換是標準 SQL、團隊以分析師為主 |

## 十、系統效應與系列導航

以情境的 `orders` 表為例，從 Phase 1 走到 Phase 3 並加上冪等與品質閘門後的變化。數字沿用前文假設。

| 指標 | 改造前（每晚全量） | 改造後（CDC + MERGE + WAP） |
|---|---|---|
| 每日搬運量 | 300 GB | 約 3 GB |
| 擷取對來源副本的負載 | 45 分鐘高負載 | 持續、可忽略 |
| 資料新鮮度 | T+1 | 每小時（可再縮短） |
| 修正某一天的資料 | 人工刪除後重跑，約半天 | 清除該日期任務重跑，約 15 分鐘 |
| 壞資料被下游看到 | 會，直到有人發現 | 不會，停在 staging |
| 靜默漏資料的偵測 | 無 | 每日對帳；筆數與金額合計的差異可在一天內發現 |
| 需要維運的元件 | 1（cron） | 5（連接器、Kafka、排程器、Spark、table format） |

最後一列是誠實的代價，面試中要自己說出來：**複雜度增加了，所以只在值得的表上用**。

**本篇重點**

- 批次作業設計成「輸入分區 → 輸出分區」的純函數：日期由參數傳入、輸出原子覆寫。
- 擷取三種方式混用：小表全量、中型表增量加重疊視窗、核心大表 CDC。
- Spark 變慢先看 shuffle 與傾斜；傾斜先查 NULL key，再靠 AQE、broadcast，最後才加鹽。
- 相依以資料就緒觸發；SLA 從交付時間倒推並保留一次重跑的餘裕。
- 品質檢查搭配 WAP，讓「晚」取代「錯」。
