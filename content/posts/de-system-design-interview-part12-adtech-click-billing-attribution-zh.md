> 多數人設計廣告資料系統時，把曝光、點擊、轉換當成同一種事件，丟進同一條管線。  
> 接著就得回答一個沒有好答案的問題：一天 100 億筆的資料，要怎麼做到一筆都不能錯？  
> 正確的切入點是先分辨**哪些數字是錢、哪些只是統計**，再分辨**哪些決定要在幾秒內做、哪些可以等到明天**。  
> 同一個點擊同時是計費依據、預算扣款與歸因的起點，而這三個用途對快與準的要求各不相同。

這是產業案例的第二篇。[Part 11](/posts/de-system-design-interview-part11-payments-ledger-reconciliation-zh/) 的支付題資料量小、正確性要求極高；廣告題則是**量極大，而且其中一小部分同樣是錢**。這一題考的是你能不能把一條事件流依用途拆開，分別給它們剛好夠用的保證。

---

## 面試情境

> **面試官**：「我們是一個廣告平台，每天約 100 億次廣告曝光、1 億次點擊，採點擊計費。請設計資料系統，支援三件事：向廣告主收費、在預算用完時停止投放，以及提供轉換歸因報表。」

---

## 一、這一題在考什麼

三個需求用的是同一批事件，但性質差異很大。面試一開始就把這張表畫出來，後面的設計會順很多。

| 用途 | 依據的事件 | 要多快 | 要多準 | 錯了的後果 |
|---|---|---|---|---|
| 計費 | 點擊 | 隔日即可 | 精確，可稽核 | 多收要退款並損害信任 |
| 預算控制 | 點擊（累計花費） | 數秒到一分鐘 | 近似即可 | 超投的部分通常由平台吸收 |
| 歸因報表 | 點擊 + 轉換 | 數小時 | 精確，但會隨晚到的轉換修正 | 廣告主誤判成效 |
| 投放分析 | 曝光 | 分鐘級 | 近似可接受 | 報表略有偏差 |

由此得到本題的主軸：**用批次路徑產生可稽核的計費數字，用串流路徑產生夠快的預算數字，兩者明確分開並每日比對**。把預算控制的即時數字直接拿來開帳單，或者要求計費數字在幾秒內精確，都是常見的錯誤方向。

## 二、0–10 分鐘：釐清與估算

> **候選人**：「先確認計費模式：只有點擊計費嗎？曝光本身會不會收費？」
>
> **面試官**：「目前只有點擊計費。」
>
> **候選人**：「那麼曝光是分析用的資料，點擊才是計費依據。這會影響我給兩者的保證等級。預算方面，是以日預算為單位嗎？超出預算的花費由誰承擔？」
>
> **面試官**：「每個廣告活動有日預算。超出的部分我們不能向廣告主收費。」
>
> **候選人**：「所以超投是平台的直接損失，我需要估算延遲會造成多少超投。預算用完之後，多久內必須停止投放？」
>
> **面試官**：「希望一分鐘內。」
>
> **候選人**：「無效點擊呢？例如重複點擊或機器流量，需要在計費前排除嗎？」
>
> **面試官**：「需要，而且事後發現的也要退還。」
>
> **候選人**：「最後是歸因。轉換資料怎麼進來？歸因的規則與回溯期間是什麼？」
>
> **面試官**：「廣告主的伺服器會回傳轉換事件，帶有點擊 ID。採最後點擊歸因，回溯 7 天。轉換可能晚幾個小時到幾天才回傳。」

**評註**：「曝光會不會收費」決定了 100 億筆資料需不需要精確處理，是本題最關鍵的一個問題。「超投由誰承擔」把預算控制的延遲換算成了金錢損失，讓後面的延遲目標有依據。

估算（假設曝光事件約 0.5 KB、點擊事件約 1 KB、尖峰為平均的 3 倍、平均每次點擊收費 $0.50）：

```
impressions/day   = 10,000,000,000
avg impressions/s = 10B / 86,400              ≈ 116,000 /s
peak              = 116,000 × 3               ≈ 350,000 /s   (175 MB/s)
raw size/day      = 10B × 0.5 KB              = 5 TB

clicks/day        = 100,000,000               (CTR 1%)
avg clicks/s      = 100M / 86,400             ≈ 1,160 /s
peak              ≈ 3,500 /s
raw size/day      = 100M × 1 KB               = 100 GB

billed/day        = 100M × $0.50              = $50,000,000
1% billing error  = $500,000 / day
```

> **候選人**：「兩個結論。第一，曝光是點擊的一百倍，兩者應該走不同的 topic 與不同的處理路徑；需要精確處理的點擊每天只有 100 GB，完全可以用批次做到逐筆正確。第二，每天計費金額約五千萬美元，1% 的誤差就是五十萬，所以計費路徑值得用最保守的設計。」

**評註**：估算的結論是把問題拆成「量大但寬鬆」與「量小但嚴格」兩塊。這一步讓「100 億筆都不能錯」這個不可能的要求消失了。

## 三、10–15 分鐘：資料契約

> **候選人**：「計費的單位是點擊，所以我先定義什麼是一次可計費的點擊，以及點擊事件要帶什麼。」

```
click_id        string     -- 收集端產生，唯一
impression_id   string     -- 來自曝光時簽發的權杖
campaign_id     string
ad_id           string
cpc_minor       long       -- 這次曝光成交的單次點擊價，最小貨幣單位
currency        string
user_key        string     -- 假名化的使用者或裝置識別
click_time      timestamp  -- 收集端時間（伺服器端，可信）
token_issued_at timestamp  -- 曝光時間，來自權杖
ip_hash, ua     string     -- 無效流量判定用
```

> **候選人**：「關鍵設計是**點擊事件自己帶齊計費所需的資訊**。投放廣告時，伺服器把曝光 ID、活動、價格與時間簽章後放進點擊網址。使用者點擊時，收集端驗證簽章與有效期限，然後把這些欄位直接寫進點擊事件。
>
> 這樣做的好處是計費不需要把點擊與曝光做連接。曝光一天 100 億筆，要為了查價格而保留它們的狀態，成本很高，而且曝光資料只要掉一筆，對應的點擊就無法計價。簽章則確保價格與活動無法被竄改。」
>
> **面試官**：「可計費點擊的定義？」
>
> **候選人**：「簽章有效、在權杖有效期限內、通過無效流量規則，而且**每一次曝光最多計費一次**。最後一條以 `impression_id` 去重，連點兩下只算一次。這個定義會同時用在串流與批次兩條路徑。」

**評註**：自帶上下文的簽章權杖，把一個 100 億筆規模的串流連接變成了收集端的一次驗證。面試中「避免做一件昂貴的事」往往比「把昂貴的事做得更快」得分更高。

## 四、15–25 分鐘：架構與三個演進階段

```
╔══════════════════════════════════════════════════════════════════════╗
║  Phase 1  Hourly batch for everything (early stage)                  ║
╚══════════════════════════════════════════════════════════════════════╝

┌───────────┐  logs   ┌──────────┐  hourly job  ┌───────────────────┐
│ Ad servers│────────▶│ S3       │─────────────▶│ spend per campaign│
└───────────┘         └──────────┘              │ billing + budget  │
                                                └───────────────────┘
```

**可行的範圍**：活動預算小、每小時花費遠低於日預算。**失效的原因**：預算檢查每小時一次，最壞情況下超投一整個小時的花費。

```
╔══════════════════════════════════════════════════════════════════════╗
║  Phase 2  Split by purpose (target design)                           ║
╚══════════════════════════════════════════════════════════════════════╝

┌───────────┐ impressions ┌───────────────┐      ┌─────────────────────┐
│ Ad servers│────────────▶│ Kafka         │─────▶│ pre-aggregate by    │
└───────────┘             │ impressions   │      │ campaign/ad/hour    │
                          │ topic         │      │ -> OLAP (reporting) │
                          └───────────────┘      └─────────────────────┘
┌───────────┐ validated   ┌───────────────┐ fast ┌─────────────────────┐
│ Click     │────────────▶│ Kafka         │─────▶│ Flink: spend per    │
│ collector │ clicks      │ clicks topic  │      │ campaign per 10 s   │
│ (verify   │             │ key=campaign  │      └──────────┬──────────┘
│  token)   │             └───────┬───────┘                 ▼
└───────────┘                     │              ┌─────────────────────┐
                                  │ archive      │ Budget store        │
                                  ▼              │ -> ad servers stop  │
                          ┌───────────────┐      └─────────────────────┘
                          │ Bronze clicks │ daily
                          │ (Iceberg)     │─────▶ billable clicks ─▶ invoices
                          └───────────────┘       + attribution join
```

> **候選人**：「三條路徑對應三種保證。曝光只做預先聚合後進 OLAP 引擎，原始資料保留有限天數。點擊走兩條路：串流路徑每 10 秒算一次各活動的花費並更新預算儲存，投放伺服器據此停投；批次路徑每日從歸檔的點擊重新計算可計費點擊，產生帳單，並與轉換做歸因連接。串流的花費數字只用於預算控制，不用於開帳單。」

| | Phase 1 | Phase 2 | Phase 3 |
|---|---|---|---|
| 預算延遲 | 最長 1 小時 | 約 10–30 秒 | 加上接近上限時的節流 |
| 計費 | 每小時批次 | 每日批次，逐筆去重 | 加上調整帳與退款流程 |
| 無效流量 | 無 | 即時規則 | 加上離線模型的事後判定 |
| 歸因 | 無 | 每日批次，重算回溯期 | 小時級增量 |
| 部署 | 單一區域 | 單一區域 | 多區域收集與彙整 |

## 五、深挖一：預算控制與超投

> **面試官**：「你的預算控制有延遲。會超投多少？」
>
> **候選人**：「超投金額大約是『花費速率 × 從點擊發生到投放伺服器停投的總延遲』。延遲由四段組成：點擊進 Kafka、10 秒的聚合視窗、寫入預算儲存、投放伺服器更新本地快取。我估計合計約 20–30 秒。
>
> 以一個日預算一萬美元、尖峰每分鐘花 600 美元的活動為例：」

```
spend rate      = $600 / min = $10 / s
control delay   ≈ 30 s
overspend       ≈ $10 × 30 = $300      (3% of a $10,000 daily budget)
```

> **候選人**：「3% 對小預算的活動比例會更高，所以除了縮短延遲，還要加上**節流**：當已花費達到預算的一定比例（例如 90%）時，投放伺服器依剩餘預算等比例降低該活動的投放機率。這樣花費速率在接近上限時自然下降，最後 30 秒的超投金額就小很多。」
>
> **面試官**：「Flink 作業重啟後，花費會不會被重複累加？」
>
> **候選人**：「如果寫入方式是對一個累計值做遞增，會。重啟後從檢查點重播的那段點擊會被再加一次。所以我不寫遞增，而是寫入『活動、視窗起始時間』為鍵的資料列，值是該視窗的花費，重播時覆寫同一筆。累計花費是讀取時把當日各視窗加總，或由另一個從這些資料列導出的值維護。這和 [Part 3](/posts/de-system-design-interview-part3-streaming-realtime-zh/) 的冪等 sink 是同一個原則。」
>
> **面試官**：「大型活動的點擊量是其他活動的幾千倍，key 用 `campaign_id` 不會傾斜嗎？」
>
> **候選人**：「會。點擊的總量不大，尖峰每秒 3,500 筆，單一分區也處理得了，所以這裡的傾斜不是吞吐量問題，但我仍然會在聚合前做本地預聚合：每個平行實例先把自己收到的點擊依活動累計一兩秒，再送出『活動、小計』。這樣即使某個活動佔了一半流量，下游看到的也只是每秒幾筆小計。」

**評註**：候選人把延遲拆成四段並換算成金額，再提出節流這個不靠「更快」而靠「提早減速」的解法。重啟重複累加的問題，則用視窗粒度的冪等寫入回答。

## 六、深挖二：計費的正確性與無效點擊

> **面試官**：「帳單的數字是怎麼算出來的？和預算控制用的花費數字不同時，以哪個為準？」
>
> **候選人**：「以批次為準。每日作業讀取歸檔的點擊，做四件事：以 `click_id` 去除重送；以 `impression_id` 確保每次曝光最多一次；套用無效流量規則；最後依活動與日期加總。輸出是一張逐筆的可計費點擊表與一張彙總的計費表，帳單上每一塊錢都能連回具體的點擊。
>
> 串流與批次的數字會有差異，原因是可預期的：串流用的是即時規則，批次能看到完整的一天並套用更多規則。我每天比對兩者，各活動的差異若超過門檻（例如 1%）就調查。差異持續偏大代表兩邊的定義開始分歧。」
>
> **面試官**：「三天後風控團隊判定某個來源的點擊全是機器流量，但帳單已經開出去了。」
>
> **候選人**：「已開出的帳單不改。我會產生一筆**調整項**：負數金額、指向被判定無效的點擊、註明原因與判定時間，計入下一期帳單或作為退款。這和 Part 11 的沖銷分錄是同一個原則——已發出的財務紀錄不可變，修正以新的紀錄表達。
>
> 資料模型上，可計費點擊表不會被改寫，而是另外有一張無效判定表，以 `click_id` 記錄判定結果與時間。任何時間點的『有效計費金額』都是兩張表連接的結果，所以也可以重現『帳單開出當時』的數字。」
>
> **面試官**：「即時規則有哪些？」
>
> **候選人**：「我會從成本最低、誤判風險最小的開始：簽章無效或過期；同一次曝光的重複點擊；同一使用者對同一廣告在很短時間內的多次點擊；單一 IP 或裝置的點擊頻率異常；已知的資料中心 IP 範圍。較複雜的行為模式留給離線分析，以調整項處理。即時規則寧可保守，因為誤殺正常點擊等於少收錢，而漏掉的可以事後退。」

**評註**：「誰為準」的回答很明確，並說明差異的來源與監控方式。事後判定無效的處理延續了不可變與調整項的原則，並且兼顧了可重現性。

## 七、深挖三：歸因與晚到的轉換

> **面試官**：「歸因報表怎麼算？」
>
> **候選人**：「轉換事件帶有 `click_id`，所以連接是精確鍵連接，不需要模糊比對。每日作業把轉換連回點擊，並檢查轉換時間是否在點擊後 7 天內。同一筆轉換若對應多次點擊，依最後點擊規則只歸給時間最晚的那一次。
>
> 難處在時間。轉換可能在點擊後 7 天才發生，回傳又可能再晚幾天。所以某一天的歸因結果在之後一週多的時間裡都還會增加。」

```
click day D ──────────────────────────────────────────────▶ time
  D          D+1        D+3              D+7        D+9
  │           │          │                │          │
click     conversion  conversion      attribution  late postback
          (counted)   (counted)       window ends  for a D+6
                                                   conversion arrives

report for day D:  provisional until ~D+10, restated daily until then
```

> **候選人**：「我的做法是每天重算最近 10 天的歸因分區：7 天的回溯期，加上回傳延遲的緩衝。報表上這段期間標示為暫定。實際要重算幾天，由觀察到的回傳延遲分佈決定，並持續監控超出範圍才到達的轉換比例。」
>
> **面試官**：「為什麼不用串流做歸因？廣告主想更快看到成效。」
>
> **候選人**：「可以做，但要先確認值不值得。串流歸因需要把 7 天的點擊保留在狀態中：7 億筆，以每筆約 200 bytes 估計是 140 GB。這個量放得進磁碟型的狀態後端，但檢查點、擴縮容與版本升級時的狀態遷移都會變得沉重。
>
> 如果廣告主能接受一小時的延遲，我會選每小時的增量批次：只處理新到的轉換，連回點擊表。只有在轉換數據要即時回饋給出價系統、延遲直接影響投放效果時，我才會承擔串流歸因的維運成本。」
>
> **面試官**：「廣告主說他們自己統計的點擊數比我們少 8%。」
>
> **候選人**：「兩邊的數字本來就不會完全相同，因為量測點不同：我們在點擊發生時計數，廣告主通常在到達頁載入完成後計數，中間有使用者離開、頁面載入失敗、追蹤碼被阻擋等損耗。時區與無效流量的過濾規則也可能不同。
>
> 我能做的是讓差異可以被解釋：提供逐筆的點擊紀錄供比對，明確記載我們的計數定義與時區，並監控各廣告主的差異比例。穩定的差異通常是量測定義造成的；突然擴大的差異才是需要調查的訊號。」

**評註**：候選人在串流歸因的問題上給了具體的狀態大小估算，再說明選擇批次的理由與翻轉條件。第三方數字差異的回答，重點不是「誰對」，而是把差異變成可解釋、可監控的東西。

## 八、為什麼選 X 不選 Y

| 選擇 | 選 X 的理由 | 不選 Y 的理由 | 翻轉條件 |
|---|---|---|---|
| 曝光與點擊分開處理 vs 同一條管線 | 需要精確的只有 1% 的資料量，可以用最保守的方式處理 | 統一管線要嘛讓 100 億筆都付出精確的成本，要嘛讓計費資料只有近似的保證 | 改為曝光計費時，曝光也成為計費依據，必須提升到相同的保證等級 |
| 點擊自帶簽章上下文 vs 點擊連接曝光 | 免去 100 億筆規模的連接與狀態；不受曝光資料遺失影響 | 連接需要保留大量曝光狀態，曝光掉一筆就無法計價 | 計費需要曝光後才決定的資訊（例如事後結算的競價價格） |
| 批次計費 vs 以串流數字計費 | 可重跑、可套用完整規則、逐筆可稽核 | 串流數字受晚到、重啟與即時規則限制，難以作為帳單依據 | 預付額度需即時扣款的產品，需要另建交易式的扣款服務 |
| 視窗粒度的冪等寫入 vs 累計值遞增 | 重播時覆寫同一筆，不會重複累加 | 遞增在作業重啟後會把重播的部分再加一次 | 儲存支援以交易方式同時提交 offset 與遞增 |
| 接近上限時節流 vs 只縮短延遲 | 降低花費速率，超投金額與延遲不再成正比 | 延遲有物理下限，高花費速率的活動仍會超投 | 預算遠大於單位時間花費的活動，節流沒有必要 |
| 調整項 vs 重開帳單 | 已發出的帳單不變；每次修正可追溯 | 重開帳單讓歷史金額不可重現 | 帳單尚未發出，仍在暫定期內，可直接重算 |
| 每小時增量歸因 vs 串流歸因 | 無需維護 140 GB 的長期狀態 | 串流歸因的狀態遷移與檢查點成本高 | 轉換要即時回饋出價系統，分鐘級延遲有明確的營收影響 |
| 固定重算回溯期 vs 只處理新轉換 | 邏輯簡單、冪等、自動納入晚到資料 | 只處理新資料要追蹤受影響的歷史分區 | 資料量大到重算十天的成本過高時，改為只重算有新轉換的分區 |

## 九、常見追問與回答要點

**「之後要支援曝光計費呢？」**
曝光變成計費依據後，它的保證等級要提升：逐筆去重、可稽核、不能取樣。每天 5 TB 的原始資料仍可用批次處理，但儲存保留期、去重成本與可視性（廣告是否真的被看到）的定義都要重新設計。這是整個架構中影響最大的一個需求變更，值得在釐清階段就問。

**「預算用完之後才到的點擊要不要收費？」**
那些點擊對應的曝光是在停投之前合法送出的，點擊本身有效，但收費總額不能超過預算。做法是計費時以預算為上限封頂，超出的部分記為平台吸收的超投，並作為一項指標持續追蹤。

**「日預算的『一天』是哪個時區？」**
依廣告主帳戶設定的時區。儲存以 UTC 的細粒度時間（例如 15 分鐘）聚合，再依各帳戶的時區組合出它的「一天」。只存 UTC 的整日或整點聚合，會無法正確處理非整點偏移的時區。

**「多區域部署時預算怎麼控制？」**
兩種做法各有代價。集中式：各區域的花費彙整到一處再判斷，數字準確但跨區延遲較高，超投較多。配額式：把預算預先分配給各區域，各自就地判斷，延遲低，但某區域用完時其他區域可能還有剩，造成預算花不完，需要定期重新分配。花費速率高的大型活動適合配額式。

**「Kafka 資料因為 bug 需要重播，會不會重複計費？」**
不會，前提是計費來自批次且以 `click_id` 與 `impression_id` 去重。重播只影響串流的預算數字，而那一側的寫入是冪等的。這正是把兩條路徑分開的好處。

**「頻次控制（同一人一天最多看三次）是不是也歸這個系統？」**
它需要毫秒級的逐使用者讀寫，屬於線上服務的鍵值儲存，不適合由分析管線提供。資料平台可以提供的是事後的頻次分佈分析，用來驗證線上控制是否生效。

## 十、系統效應與系列導航

從 Phase 1 到 Phase 2 的前後對照，沿用前文的假設；標示為目標的是設計目標。

| 指標 | 改造前（每小時批次） | 改造後（依用途拆分） |
|---|---|---|
| 預算控制延遲 | 最長 60 分鐘 | 約 30 秒（目標） |
| 日預算 $10,000、尖峰每分鐘花 $600 的活動的最壞超投 | 約 $36,000（一小時的花費） | 約 $300，加上節流後更低 |
| 需要精確處理的資料量 | 每天 5 TB（全部） | 每天 100 GB（只有點擊） |
| 計費是否逐筆可追溯 | 只有彙總數字 | 每筆金額連回點擊 |
| 事後判定無效點擊 | 重算並覆寫 | 以調整項處理，歷史不變 |
| 歸因報表 | 無 | 每日產出，回溯期內標示暫定 |
| 新增的維運工作 | 無 | 串流作業、預算儲存、串流與批次的每日比對 |

**本篇重點**

- 先分辨哪些事件是錢、哪些是統計，再分別給予剛好夠用的保證。
- 讓點擊事件以簽章權杖自帶計費資訊，避免與曝光做大規模連接。
- 預算控制要快、可近似；計費要準、可稽核；兩者分開並每日比對。
- 超投約等於花費速率乘以控制延遲；接近上限時節流比單純追求低延遲有效。
- 已發出的帳單不可變，事後修正以調整項表達；歸因在回溯期內持續重算並標示暫定。
