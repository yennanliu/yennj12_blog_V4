> *大多數人把 Agent 設計成「一問一答」的延伸版本——輸入一個任務，等待一個輸出。*
> *長時程任務打破了這個假設：任務可能跨越數小時、數天、數十個 LLM 呼叫。*
> *短時程 Agent 的容錯率是 5%，長時程 Agent 的錯誤會複利累積，每步 98% 成功率，五十步後完成率只剩 36%；每步 95%，更只剩 7.7%。*
> *真正的長時程 Agent 工程，是在不確定性中建立可恢復、可審計、可協作的執行系統。*

---

這篇給已經寫過 Agent 迴圈（Phase 14）、但任務一跑超過幾十步就開始不可靠的工程師看。全文用一個貫穿的例子：在 72 小時內分析一個 monorepo 的 3000 個 PR，Agent 跑到第 800 個時崩潰重啟。讀完你會能為這類任務設計分層記憶與版本化的狀態儲存、把任務拆成帶依賴圖的子任務、用 write-ahead checkpoint 讓重啟不重做也不重複副作用、決定哪些決策點需要人工確認，以及用 embedding 相似度和輸出指標偵測目標漂移。

## 一、核心問題：為什麼長時程任務對 Agent 是質的挑戰

### 1.1 短時程 vs 長時程的根本差異

大多數 LLM Agent 的設計假設是「無狀態、單輪、短暫」：使用者提問，Agent 在一個 context window 內完成推理，回傳答案，會話結束。這個模型在 RAG 問答、程式碼補全、單步工具呼叫等場景運作良好。

長時程任務打破了所有這些假設：

- **時間跨度**：任務可能需要 2 小時、2 天、甚至 2 週才能完成
- **狀態複雜度**：中間狀態數量可達數千個節點，無法全部放入 context window
- **錯誤複利**：每一步有 2% 的錯誤率，50 步後完成率僅剩 36%（0.98^50 ≈ 0.364）
- **外部世界變化**：任務執行期間，外部環境可能發生變化（程式碼庫更新、API 回應格式改變）
- **人工干預需求**：某些決策點需要人類確認，無法全程自動化

### 1.2 錯誤複利的數學現實

假設每個子任務的成功率為 p，執行 n 個子任務，整體成功率為 p^n：

```
子任務成功率    10步任務    50步任務    100步任務
────────────────────────────────────────────────
99.0%          90.4%       60.5%       36.6%
95.0%          59.9%        7.7%        0.6%
90.0%          34.9%        0.5%       0.003%
```

這意味著：一個「看起來不錯」的 Agent，在長任務中可能完全不可用。提升長時程 Agent 可靠性的唯一方法是：**Checkpoint、回滾、人工確認點，以及漂移偵測**。

### 1.3 長時程任務失敗的四大根本原因

1. **記憶喪失**：每次 LLM 呼叫後，上下文在 context window 外的部分消失
2. **目標漂移**：隨著任務進行，Agent 對原始目標的理解逐漸偏離
3. **狀態不一致**：崩潰重啟後，已完成的步驟與待完成步驟的邊界不清
4. **無法恢復的副作用**：某些操作（發送郵件、寫入資料庫）不可逆，重試會造成重複

## 二、何時該升級：從單機 JSON 到 Checkpoint DB、再到雙層狀態與漂移偵測的觸發條件

最省事的起點是單機 Agent 迴圈加一個本地 `task_state.json`：已完成步驟清單與中間結果都寫在裡面，崩潰後人工看檔案、刪掉失敗步驟、重跑。只要任務量少、沒有不可逆副作用、而且重跑的錢與時間都付得起，這個形態就夠用。該升級的訊號有三個：任務開始有副作用（寫資料庫、呼叫外部 API、發通知），重跑會造成重複；單一任務的重跑成本超過一次人工介入的成本；或是需要多個 worker 並行。這時把狀態搬進 PostgreSQL，每個子任務完成後寫一次 checkpoint（§五），用 Redis Streams 之類的佇列把子任務分給 worker，高風險操作透過 Slack webhook 走人工確認（§六）。

第二道門檻不是任務量，而是**恢復時間與品質**開始被盯著看。當 checkpoint 的讀寫延遲進入關鍵路徑（P99 > 5 ms 就會拖慢每一步），把熱態狀態放進 Redis、PostgreSQL 退為冷層；當任務跑到後半段輸出明顯變簡略、或 Agent 開始呼叫不該碰的工具，就需要 embedding 相似度與輸出指標的漂移偵測（§七）取代人工觀察；當稽核問「Agent 在某個時間點知道什麼、為什麼這樣決定」，就需要不可變的 audit log 與版本化記憶（§三）。這些元件各自有獨立的觸發條件，不必一次全上。

| 從 | 到 | 觸發訊號 |
|----|----|----------|
| 單機迴圈 + 本地 JSON | PostgreSQL checkpoint + 任務佇列 + worker pool | 出現不可逆副作用；單次重跑成本高於一次人工介入；需要並行 |
| 每子任務寫 PostgreSQL | Redis 熱層 + PostgreSQL 冷層 | checkpoint 讀寫 P99 > 5 ms 進入關鍵路徑；要求崩潰後 < 30 秒自動恢復 |
| 人工觀察品質 | Embedding 漂移偵測 + 不可變 audit log | 任務後段輸出明顯退化或工具使用異常；稽核要求重建任意時間點的決策依據 |

## 三、跨會話記憶：持久化設計與版本管理

### 3.1 記憶的四個層次

長時程 Agent 需要在不同時間尺度上管理記憶：

```
┌─────────────────────────────────────────────────────────────┐
│                    記憶層次架構                              │
│                                                             │
│  ┌────────────────────────────────────────────────────┐    │
│  │  L1：工作記憶 (Working Memory)                      │    │
│  │  ├── Context Window (128K tokens)                   │    │
│  │  ├── 當前任務狀態、最近 N 個工具呼叫結果            │    │
│  │  └── 生命週期：單次 LLM 呼叫                        │    │
│  └────────────────────────────────────────────────────┘    │
│                          │                                  │
│                          ▼                                  │
│  ┌────────────────────────────────────────────────────┐    │
│  │  L2：會話記憶 (Session Memory)                      │    │
│  │  ├── 當前子任務的完整執行歷史                       │    │
│  │  ├── 儲存：Redis，TTL = 24 小時                     │    │
│  │  └── 生命週期：單一任務執行期間                     │    │
│  └────────────────────────────────────────────────────┘    │
│                          │                                  │
│                          ▼                                  │
│  ┌────────────────────────────────────────────────────┐    │
│  │  L3：長期記憶 (Long-term Memory)                    │    │
│  │  ├── 已完成任務的摘要、學到的事實                   │    │
│  │  ├── 儲存：Vector DB（語義搜尋）+ SQL（精確查詢）   │    │
│  │  └── 生命週期：永久（帶版本控制）                   │    │
│  └────────────────────────────────────────────────────┘    │
│                          │                                  │
│                          ▼                                  │
│  ┌────────────────────────────────────────────────────┐    │
│  │  L4：外部知識 (External Knowledge)                  │    │
│  │  ├── 文件庫、程式碼庫、資料庫                       │    │
│  │  ├── 存取方式：工具呼叫（不存入 context）           │    │
│  │  └── 生命週期：獨立於 Agent                         │    │
│  └────────────────────────────────────────────────────┘    │
└─────────────────────────────────────────────────────────────┘
```

### 3.2 持久化記憶的版本管理

長時程任務中，記憶會隨時間演化。必須對記憶進行版本控制，原因有三：

1. **回滾需求**：任務失敗後需要恢復到某個良好狀態
2. **稽核追蹤**：需要了解 Agent 在某時間點「知道什麼」
3. **一致性保障**：避免部分更新造成的記憶不一致

**記憶版本控制 Schema（PostgreSQL）**：

```sql
CREATE TABLE agent_memory (
    id            UUID PRIMARY KEY DEFAULT gen_random_uuid(),
    task_id       UUID NOT NULL,
    memory_key    TEXT NOT NULL,
    memory_value  JSONB NOT NULL,
    version       INTEGER NOT NULL DEFAULT 1,
    created_at    TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    superseded_at TIMESTAMPTZ,           -- NULL = 當前版本
    checksum      TEXT NOT NULL          -- SHA-256，防止靜默損壞
);

-- 取得某任務的當前記憶快照
CREATE VIEW agent_memory_current AS
SELECT * FROM agent_memory
WHERE superseded_at IS NULL;
```

### 3.3 記憶壓縮策略

當長期記憶累積過多時，需要進行摘要壓縮，避免每次查詢都必須處理數千個向量：

- **滾動摘要**：每 20 個步驟，將舊步驟的詳細記錄壓縮為摘要（成本節省 ~80%）
- **重要性加權**：錯誤記錄的保留權重 > 成功記錄（失敗提供更多學習信號）
- **TTL 策略**：> 30 天的任務摘要降級到冷儲存（S3），保持 Vector DB 精簡

## 四、長任務分解：里程碑 / 子目標 / 依賴圖

### 4.1 三層任務結構

長時程任務需要層次化分解，避免單層扁平結構帶來的複雜度爆炸：

```
任務（Task）
├── 里程碑 1：完成資料收集
│   ├── 子目標 1.1：API 資料抓取（獨立，可並行）
│   ├── 子目標 1.2：資料庫查詢（獨立，可並行）
│   └── 子目標 1.3：資料清洗（依賴 1.1、1.2）
├── 里程碑 2：分析處理
│   ├── 子目標 2.1：特徵工程（依賴里程碑 1）
│   └── 子目標 2.2：模型推理（依賴 2.1）
└── 里程碑 3：報告產出
    └── 子目標 3.1：報告生成（依賴里程碑 2）
```

### 4.2 依賴圖的 DAG 表示

使用有向無環圖（DAG）表示子任務依賴關係，支援：

- **拓撲排序**：確定執行順序
- **關鍵路徑分析**：找出影響整體完成時間的瓶頸
- **並行化機會**：識別可以同時執行的子任務

**DAG 資料結構（Python）**：

```python
@dataclass
class SubTask:
    task_id: str
    description: str
    dependencies: List[str]   # task_id 清單
    status: Literal["pending", "running", "completed", "failed"]
    checkpoint_data: Optional[dict] = None
    retry_count: int = 0
    max_retries: int = 3

class TaskDAG:
    def get_ready_tasks(self) -> List[SubTask]:
        """返回所有依賴已完成且尚未執行的任務"""
        return [
            t for t in self.tasks.values()
            if t.status == "pending"
            and all(
                self.tasks[dep].status == "completed"
                for dep in t.dependencies
            )
        ]
```

### 4.3 里程碑的人工確認設計

不是每個里程碑都需要人工確認，需要根據風險等級決定：

| 風險等級 | 典型操作 | 確認方式 | 超時策略 |
|---------|---------|---------|---------|
| 高 | 資料庫寫入、外部 API 呼叫、資金操作 | 同步等待人工批准 | 超過 1 小時自動暫停 |
| 中 | 檔案系統修改、設定變更 | 非同步通知，可選審核 | 超過 4 小時自動繼續 |
| 低 | 唯讀查詢、內部計算 | 僅記錄日誌 | 無超時 |

## 五、斷點恢復：Checkpoint 設計與狀態一致性

### 5.1 Checkpoint 的核心原則

Checkpoint 設計有三個核心原則，違反任何一個都會導致恢復失敗：

1. **冪等性（Idempotency）**：重複執行同一步驟的結果必須相同
2. **原子性（Atomicity）**：Checkpoint 要麼完整寫入，要麼完全不寫入
3. **先寫後執行（Write-Ahead）**：在執行副作用之前，先持久化 Checkpoint

### 5.2 Checkpoint 狀態機

```
┌─────────────────────────────────────────────────────────────┐
│                   Checkpoint 狀態機                          │
│                                                             │
│  ┌──────────┐                                               │
│  │ PENDING  │ ──── 開始執行 ────▶ ┌─────────────┐          │
│  └──────────┘                     │   RUNNING   │          │
│                                   └──────┬──────┘          │
│                                          │                  │
│                         ┌───────────────┼───────────────┐  │
│                         │               │               │  │
│                         ▼               ▼               ▼  │
│                  ┌─────────────┐ ┌─────────────┐ ┌────────┐│
│                  │  COMPLETED  │ │   FAILED    │ │TIMEOUT ││
│                  └─────────────┘ └──────┬──────┘ └───┬────┘│
│                                         │             │     │
│                                         ▼             ▼     │
│                                  ┌─────────────────────┐   │
│                                  │   RETRY_PENDING     │   │
│                                  │   (max 3 retries)   │   │
│                                  └──────────┬──────────┘   │
│                                             │               │
│                              retry < max ───┴─── retry = max│
│                                   │                   │     │
│                                   ▼                   ▼     │
│                              [回 RUNNING]        [DEAD_LETTER│
│                                                  需人工介入] │
└─────────────────────────────────────────────────────────────┘
```

### 5.3 Write-Ahead Checkpoint 實作

```python
class CheckpointManager:
    def execute_with_checkpoint(
        self,
        task_id: str,
        step_id: str,
        action: Callable,
        *args, **kwargs
    ):
        # 1. 先檢查是否已有完成的 Checkpoint（冪等性保障）
        existing = self.db.get_checkpoint(task_id, step_id)
        if existing and existing.status == "completed":
            return existing.result   # 直接返回快取結果，跳過執行

        # 2. Write-Ahead：在執行前記錄「開始」狀態
        self.db.upsert_checkpoint(task_id, step_id, status="running")

        try:
            result = action(*args, **kwargs)

            # 3. 執行成功後，原子性地更新為「完成」
            self.db.upsert_checkpoint(
                task_id, step_id,
                status="completed",
                result=result,
                completed_at=datetime.utcnow()
            )
            return result

        except Exception as e:
            self.db.upsert_checkpoint(
                task_id, step_id,
                status="failed",
                error=str(e)
            )
            raise
```

### 5.4 恢復時的狀態一致性問題

最危險的崩潰時機是「Checkpoint 已寫入，但副作用尚未發生」或「副作用已發生，但 Checkpoint 尚未寫入」。

解決方案：**意圖日誌 + 冪等提交（Intent Log）**——形式上像兩階段提交，但沒有協調者，靠的是副作用本身可重放：

- **Phase 1（Prepare）**：寫入 Checkpoint，狀態為 `PREPARE`，不執行副作用
- **Phase 2（Commit）**：執行副作用，成功後更新 Checkpoint 為 `COMMITTED`
- **恢復邏輯**：找到 `PREPARE` 狀態的步驟，從 Phase 2 重試（副作用必須冪等）

這個設計保障了：即使在任何時間點崩潰，恢復後都能達到一致狀態。注意它**不保證副作用只執行一次**——在「副作用已發生、Checkpoint 還沒更新」的瞬間崩潰，恢復後會再執行一次；它保證的是「至少一次 + 冪等 = 效果上恰好一次」，所以冪等 key 是這個模式的前提而不是加分項。

## 六、人機協作：何時需要人工確認的決策框架

### 6.1 自動化 vs 人工確認的決策樹

並非所有決策都需要人工確認。過度要求人工確認會讓 Agent 失去自動化價值，不足則帶來風險。以下是決策框架：

**需要人工確認的條件（滿足任一即觸發）**：
1. 操作的不可逆程度 > 閾值（刪除資料、金融交易、發送通訊）
2. Agent 信心分數 < 0.75（LLM 自我評估的不確定性）
3. 操作涉及的資源規模超過預設上限（例如：刪除 > 100 筆記錄）
4. 漂移偵測器發出警告（當前行為與原始目標偏差 > 15%）
5. 連續失敗次數 > 2（可能遇到未知情況）

**不需要人工確認的條件（必須全部滿足）**：
1. 操作完全可逆
2. Agent 信心分數 > 0.85（0.75–0.85 之間：自動執行，但標記為事後抽查）
3. 操作規模在預設閾值內
4. 無漂移警告
5. 同類操作在過去 24 小時內成功率 > 95%

### 6.2 人工確認的非同步設計

同步等待人工確認會阻塞整個任務管線。正確設計是非同步模式：

```
Agent 遇到確認點
       │
       ▼
建立 HumanReviewRequest（記錄到 DB）
       │
       ▼
通知人工審查員（Slack / Email / 前端 UI）
       │
       ▼
Agent 暫停此子任務，繼續執行其他獨立子任務
       │
       ▼ （審查員回應後）
Webhook 觸發，恢復子任務執行
```

**關鍵細節**：
- 審查請求必須包含完整的決策上下文（為何需要確認、可能的影響、建議選項）
- 提供「一鍵批准」和「一鍵拒絕 + 重新規劃」兩個選項
- 超時策略：高風險操作超時後暫停（保守），中風險操作超時後繼續（積極）
- 批次確認：將同類確認請求合併，避免審查員疲勞

### 6.3 人工確認的工作量預算

根據任務規模設定人工確認的預期工作量上限：

| 任務規模 | 最大確認次數 | 每次確認時間 | 總人工時間 |
|---------|------------|------------|----------|
| 小型（< 100 步） | 5 次 | 2 分鐘 | < 10 分鐘 |
| 中型（100–1000 步） | 15 次 | 3 分鐘 | < 45 分鐘 |
| 大型（1000+ 步） | 30 次 | 5 分鐘 | < 2.5 小時 |

超過預算時，系統需要自動調整確認閾值，或通知任務設計者重新評估自動化程度。

## 七、漂移偵測：長時程任務中的目標偏移診斷

### 7.1 什麼是目標漂移

目標漂移（Goal Drift）是指 Agent 在長時間執行過程中，其行為逐漸偏離原始任務目標的現象。漂移的三種形態：

1. **語義漂移**：Agent 對任務目標的理解偏移（例如：「分析安全性問題」變成「優化程式碼品質」）
2. **範疇漂移**：任務範圍悄悄擴大（例如：開始分析原本不需要處理的模組）
3. **品質漂移**：輸出品質隨時間下降（例如：前 100 個報告很詳細，後 100 個越來越簡略）

### 7.2 漂移偵測的實作方法

**方法 A：Embedding 相似度監控**

在任務開始時，對原始目標進行 Embedding：

```python
original_goal_embedding = embed("分析每個 PR 的安全性問題")
```

每隔 N 個步驟，對 Agent 最近 K 個動作進行摘要並 Embedding，計算與原始目標的 cosine 相似度。若相似度 < 0.75，觸發漂移警告。

**方法 B：輸出品質指標監控**

對於結構化輸出（例如安全報告），監控以下指標的時序趨勢：
- 報告長度（字數）
- 關鍵欄位填寫率（是否有遺漏項目）
- 嚴重問題識別率（與前期樣本比較）

若任何指標出現顯著下降趨勢（> 20% 下降），觸發品質漂移警告。

**方法 C：行為熵增監控**

追蹤 Agent 工具使用的多樣性（Shannon Entropy）。若熵值異常升高（Agent 開始呼叫不應該呼叫的工具），代表行為發生漂移。

### 7.3 漂移響應策略

| 漂移嚴重程度 | 偵測條件 | 自動響應 | 人工響應 |
|------------|---------|---------|---------|
| 輕微（黃色） | 相似度 0.65–0.75 | 強制重新注入原始目標到 context | 通知，可選審查 |
| 中度（橙色） | 相似度 0.50–0.65 | 暫停，重新規劃後續步驟 | 需確認繼續 |
| 嚴重（紅色） | 相似度 < 0.50 | 完全暫停，保存當前狀態 | 需人工分析根因 |

## 八、為什麼選 X 不選 Y

任務佇列與人工確認通道兩個選擇不需要整張表。佇列方面，已經有 Redis 的團隊用 Redis Streams 就夠：Consumer Group 原生支援重複消費、推送延遲 < 1 ms、訊息格式與 Agent 程式碼一致；RabbitMQ 同樣有持久化佇列與訊息確認，差別只是多一個要維運的服務；Kafka 的流式回放與長期保留要到每日任務量 > 1M、或需要保留訊息 > 7 天回放時才用得上，在此之前是過度設計。人工確認通道方面，初期用 Slack webhook 加 Interactive Components 的按鈕批准就好，審查歷史自動留在頻道；每日確認請求 > 50 個、或審查需要 diff 之類的比較視覺化時，再投資專用審查 UI。下面四個決策才真的需要權衡。

### 決策 1：Checkpoint 儲存 — PostgreSQL vs Redis

| 選擇 | 選 PostgreSQL 的理由 | 不選純 Redis 的理由 |
|------|---------------------|---------------------|
| 主儲存 | ACID 保障，不怕崩潰丟失 | Redis 重啟可能丟失 AOF 未刷盤資料 |
| 查詢 | 原生 JSONB，複雜查詢支援；SQL 讓稽核查詢直觀 | 無法 JOIN 查詢歷史 Checkpoint |
| 營運 | 自動備份、PITR 支援 | 記憶體成本高，不適合長期儲存 |

**Flip condition**：當 Checkpoint 的讀寫延遲成為瓶頸（> 5 ms P99），改用 Redis 作為熱層快取、PostgreSQL 作為冷層持久化的雙層架構（§二的第二道門檻）。

---

### 決策 2：長期記憶 — Vector DB vs 純 SQL 全文檢索

| 選擇 | 選 Vector DB 的理由 | 不選純 SQL 的理由 |
|------|--------------------|-------------------|
| 查詢語意 | 語義搜尋：找「相似概念」不只「相同詞」 | SQL LIKE 只能精確匹配 |
| 延遲 | < 10 ms 近似最近鄰（ANN）查詢 | SQL 全文檢索延遲 50–200 ms |
| 注入方式 | 自然語言記憶注入無需格式化，支援 top-k 語義排序 | 無法做 embedding 相似度排序 |

**Flip condition**：記憶內容是高度結構化的資料（如時序指標、財務數字），SQL 精確查詢反而更合適。混合架構：Vector DB 做語義查詢，SQL 做精確查詢，各司其職。

---

### 決策 3：漂移偵測 — Embedding 餘弦相似度 vs 規則型檢查

| 選擇 | 選 Embedding 的理由 | 不選純規則的理由 |
|------|--------------------|------------------|
| 覆蓋範圍 | 捕捉語義層面的偏移，不只關鍵字 | 規則無法覆蓋所有漂移模式 |
| 維護 | 自適應：不需要為每個任務類型寫規則 | 規則維護成本高，容易遺漏邊緣情況 |
| 警告粒度 | 可以量化偏移程度（0–1 的數值） | 規則是二元判斷，無法做漸進式警告 |

**Flip condition**：任務目標是高度結構化且可量化的（例如：「分析 PR 必須包含這 5 個欄位」），規則型檢查更精準且成本更低（$0 vs 每次 Embedding 呼叫 $0.0001）。

---

### 決策 4：子任務重試策略 — 指數退避 vs 固定間隔

| 選擇 | 選指數退避 + Jitter 的理由 | 不選固定間隔的理由 |
|------|---------------------------|--------------------|
| 下游保護 | 失敗往往是暫時性過載，退避給下游喘息空間 | 多個 Worker 同時重試，對下游壓力更大 |
| 驚群 | Jitter 避免 Thundering Herd | 同步重試讓尖峰疊加 |
| 節奏 | 第 1 次 1 s、第 2 次 4 s、第 3 次 16 s，拉開短暫與永久故障 | 無法區分「短暫故障」和「永久故障」 |

**Flip condition**：當失敗的原因是 Agent 自身邏輯錯誤（例如提示詞問題）而非外部服務問題時，重試無意義，應直接觸發人工確認而非退避重試。

## 九、系統效應：短時程 vs 長時程 Agent 改善前後對比

### Before（使用短時程 Agent 模式處理長任務）vs After（完整長時程 Agent 架構）

| 指標 | Before（短時程模式） | After（長時程架構） | 改善幅度 |
|-----|---------------------|---------------------|---------|
| **50 步任務完成率** | 36%（0.98^50） | 94%（逐步驗證 + 漂移偵測把單步成功率拉到約 99.88%，0.9988^50 ≈ 94%；Checkpoint 負責崩潰後不必重做） | +161% |
| **崩潰後恢復時間** | 需手動重啟，2–8 小時 | 自動恢復，< 30 秒 | -99.9% |
| **重複執行浪費** | 崩潰後從頭重跑，100% 浪費 | 從 Checkpoint 繼續，< 5% 浪費 | -95% |
| **LLM API 費用（1000 個 PR 分析）** | $45（重跑浪費 ~60%） | $18（Checkpoint 避免重複呼叫） | -60% |
| **目標漂移發生率** | 無偵測，~30% 任務靜默漂移 | < 5%（漂移偵測 + 自動糾正） | -83% |
| **人工介入次數** | 高（任何問題都要重跑） | 低（僅高風險決策點） | -70% |
| **可審計性** | 無日誌，無法事後分析 | 完整 Audit Log，100% 可追溯 | N/A → 100% |
| **P99 單任務延遲** | 不穩定，5–20 分鐘 | 穩定，6–8 分鐘（Checkpoint 開銷 ~3%） | -60% (P99) |
| **3000 PR 任務端對端時間** | 無法完成（中途失敗） | 72 小時內完成，SLA 達成 | 0% → 100% |

> *示意估算，非實測數據。*

### 關鍵洞察

**最大的改善點**是「可恢復性」而非「速度」。長時程 Agent 的工程挑戰本質上是**可靠性工程**，而非效能工程。在不增加 LLM 能力的情況下，純粹通過工程手段，可以將 50 步任務完成率從 36% 提升到 94%。但要分清兩種失敗：Checkpoint 與冪等設計解決的是**崩潰**——讓任務重啟時不必重做已完成的步驟，它本身不會降低單步的邏輯錯誤率；完成率從 36% 到 94% 的提升，主要來自逐步驗證（pre/post-condition 檢查）與漂移偵測把**單步錯誤**攔下並修正。
