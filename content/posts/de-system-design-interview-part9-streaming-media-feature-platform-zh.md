> 多數人設計機器學習的資料管線時，把重點放在「特徵算得夠不夠快」。  
> 模型上線後成效卻比離線評估差一截，查了兩週才發現：訓練時用的特徵，包含了預測當下還不存在的資料。  
> 服務模型的資料系統，最難的不是速度，而是**訓練時看到的世界必須和線上預測時看到的世界一模一樣**。  
> 這一題考的是時間：每一個特徵值，在哪一刻才算「已經知道」。

這是產業案例的最後一篇。前三篇的消費者是財務、廣告主與定價服務；這一篇的消費者是**機器學習模型與實驗分析**，它們對資料提出了一種前面沒出現過的要求——時間點上的正確性。

---

## 面試情境

> **面試官**：「我們是影音串流平台，日活躍使用者約 5,000 萬，播放器每 10 秒送出一次心跳。請設計資料系統，支援三件事：計算觀看時數、提供推薦模型在線上與訓練時使用的特徵，以及產出 A/B 實驗的指標。」

---

## 一、這一題在考什麼

| 需求 | 核心難處 | 錯了會怎樣 |
|---|---|---|
| 觀看時數 | 原始心跳量極大；指標定義有很多隱含選擇 | 各團隊算出不同的觀看時數，沒有人相信報表 |
| 模型特徵 | 線上與離線必須一致；訓練資料不能偷看未來 | 離線評估很好，上線後效果變差，而且很難查出原因 |
| 實驗指標 | 分組、曝光與行為的正確連接 | 實驗結論錯誤，把變差的功能推上線 |

三者的共同點是**錯誤不會以失敗的形式出現**。管線照常執行、數字照常產出，只是悄悄地不對。所以這一題的評分重點是：候選人有沒有主動設計出能發現這些錯誤的機制。

## 二、0–10 分鐘：釐清與估算

> **候選人**：「先確認心跳的內容。它只是一個『我還在播』的訊號，還是帶有播放位置與狀態？」
>
> **面試官**：「帶有播放位置、是否正在播放、畫質等資訊。」
>
> **候選人**：「觀看時數有官方定義嗎？例如暫停、快轉、背景播放算不算？」
>
> **面試官**：「目前各團隊算法不太一樣，這也是我們想解決的問題。」
>
> **候選人**：「那我會把統一定義當成交付的一部分。特徵方面，推薦模型在線上讀取特徵的延遲要求是多少？特徵需要多新？」
>
> **面試官**：「讀取要在 10 毫秒內。有些特徵希望反映使用者幾分鐘前剛看的內容，有些每天更新就夠。」
>
> **候選人**：「訓練資料是怎麼產生的？是事後用歷史資料重建特徵，還是線上預測時就把用到的特徵記錄下來？」
>
> **面試官**：「現在是事後重建。我們懷疑這造成了一些問題。」
>
> **候選人**：「實驗方面，分組的單位是使用者還是裝置？一個帳號下有多個個人檔案嗎？」
>
> **面試官**：「一個帳號最多五個個人檔案，推薦是依個人檔案做的。」

**評註**：「訓練資料怎麼產生」是有經驗的人才會問的問題，面試官的回答也透露了真正的痛點。「個人檔案」這個細節決定了特徵與實驗的實體鍵——用帳號當鍵會把家中不同成員的行為混在一起。

估算（假設每人每天平均觀看 60 分鐘、每筆心跳約 300 bytes、尖峰為平均的 3 倍、每人每天約 4 次播放、註冊個人檔案 2 億個）：

```
heartbeats/user/day = 60 min × 6 per min           = 360
heartbeats/day      = 50M × 360                    = 18,000,000,000
avg heartbeats/s    = 18B / 86,400                 ≈ 208,000 /s
peak                = 208,000 × 3                  ≈ 625,000 /s   (190 MB/s)
raw size/day        = 18B × 300 B                  = 5.4 TB

playback sessions   = 50M × 4                      = 200,000,000 /day
reduction           = 18B / 200M                   = 90×

online feature store = 200M profiles × 2 KB        = 400 GB
feature reads        = 50M × 20 / 86,400         ≈ 11,600 /s (peak ~35,000)
```

> **候選人**：「最大的數字是心跳，每天 180 億筆、5.4 TB。但下游真正需要的單位是『一次播放』，每天只有 2 億筆，少了 90 倍。所以我的第一個設計決定是盡早把心跳壓縮成播放紀錄，原始心跳只短期保留。線上特徵儲存約 400 GB、尖峰每秒三萬多次讀取，是一般鍵值儲存可以負擔的範圍。」

## 三、10–15 分鐘：資料契約與指標定義

> **候選人**：「我先定義心跳與觀看時數，因為『各團隊算法不同』通常是因為定義從來沒有被寫下來。」

```
playback_id   string     -- 播放器在每次開始播放時產生
profile_id    string     -- 個人檔案；特徵與實驗的實體鍵
content_id    string
seq           long       -- 這次播放內遞增的心跳序號
device_time   timestamp
ingest_time   timestamp
position_ms   long       -- 影片播放位置
is_playing    boolean    -- 這個 10 秒區間是否實際在播放
is_foreground boolean
```

| 問題 | 採用的定義 |
|---|---|
| 觀看時數怎麼算 | `is_playing` 為真的心跳數 × 10 秒，以 `(playback_id, seq)` 去重 |
| 暫停 | 不計；暫停期間的心跳 `is_playing` 為假 |
| 快轉與倒轉 | 只計實際播放的時間，不看播放位置的差距 |
| 背景或螢幕關閉 | 不計；`is_foreground` 為假（音樂類內容另訂） |
| 一次播放何時結束 | 收到結束事件，或超過 60 秒沒有心跳 |
| 重複觀看同一段 | 計入；指標是觀看時數，不是不重複的內容長度 |

> **候選人**：「兩個要說明的地方。第一，我用『心跳數乘以間隔』而不是『最後一筆時間減第一筆時間』，後者會把暫停的時間算進去。第二，心跳會遺失，所以這個算法會略為低估，低估的比例約等於心跳遺失率。播放器在結束事件中會回報它自己累計的播放毫秒數，我用它作為交叉檢查：兩者差距過大的播放要標記出來。」

**評註**：把口語的「觀看時數」拆成六個明確的選擇，並說明所選算法的偏差方向與檢查方式。面試官說「各團隊算法不同」時，候選人把它當成需求而不是背景資訊。

## 四、15–25 分鐘：架構與三個演進階段

```
╔══════════════════════════════════════════════════════════════════════╗
║  Phase 1  Daily batch features (early stage)                         ║
╚══════════════════════════════════════════════════════════════════════╝

┌──────────┐  logs  ┌──────┐  daily Spark  ┌──────────────┐   ┌────────┐
│ Players  │───────▶│ S3   │──────────────▶│ feature table│──▶│ KV     │
└──────────┘        └──────┘               └──────┬───────┘   │ store  │
                                                  │ training  └────────┘

```

**可行的範圍**：模型只需要每日更新的特徵。**失效的原因**：特徵最多落後一天，使用者剛看完的內容無法反映在推薦中；訓練資料與線上特徵的時間對不齊；每個實驗各寫一份 SQL。

```
                       │ Recommender │  │ Training sets│   A/B metrics
                       └─────────────┘  └──────────────┘
```

> **候選人**：「三個要點。一，串流作業先把心跳依播放彙整成播放紀錄，之後所有下游都以播放紀錄為輸入，原始心跳只保留七天供排查。二，每個特徵只有一份定義，計算結果同時寫到兩個地方：線上儲存只留最新值，離線儲存保留每一次的值與時間戳。三，實驗指標建立在一張『個人檔案 × 日期』的彙總表上，所有實驗共用，而不是每個實驗各算一次。」

| | Phase 1 | Phase 2 | Phase 3 |
|---|---|---|---|
| 心跳 | 全量落地 | 串流彙整成播放紀錄，原始保留 7 天 | 依內容類型調整心跳頻率 |
| 特徵新鮮度 | 每日 | 分鐘級 + 每日 | 依特徵的實際效益分級 |
| 訓練資料 | 事後重建，時間未對齊 | 時間點正確的連接 | 加上線上實際取用值的紀錄 |
| 實驗指標 | 各自寫 SQL | 共用彙總表與曝光表 | 自動檢查樣本比例與指標定義註冊 |
| 治理 | 無 | 特徵定義集中管理 | 特徵擁有者、漂移監控、下線流程 |

## 五、深挖一：把 180 億筆心跳變成觀看紀錄

> **面試官**：「說明一下彙整的作業。」
>
> **候選人**：「依 `playback_id` 分組，使用以 60 秒無活動為界的工作階段視窗。狀態中只保留每次播放的累計值：已計入的最大序號、播放秒數、開始時間、最後的播放位置。每筆心跳到達時更新累計值，不保留心跳本身，所以每次播放的狀態只有幾百 bytes。
>
> 輸出有兩種時機。播放結束時送出最終的播放紀錄；播放進行中每分鐘送出一次目前的累計值。後者是因為一部兩小時的電影不能等到結束才讓下游知道使用者正在看它。下游以 `playback_id` 做覆寫，所以中途的更新與最終紀錄不會重複計算。」
>
> **面試官**：「心跳亂序或重送呢？」
>
> **候選人**：「以 `(playback_id, seq)` 判斷。狀態中記錄已處理的序號範圍，重複的序號直接略過。亂序到達的心跳只要還在視窗內就正常計入，因為我是累加『播放中的區間數』而不是依賴到達順序。」
>
> **面試官**：「使用者下載影片離線觀看，三天後才連上網路。」
>
> **候選人**：「這些心跳會在三天後一次送達，事件時間是三天前。串流路徑的工作階段視窗早已關閉，所以我不讓串流處理它們，而是直接寫入 Bronze，由每日批次以相同的定義重新彙整最近幾天的播放紀錄並覆寫 Silver。觀看時數的報表在這段期間標示為暫定。
>
> 對特徵則要小心：這些三天前的觀看行為是**今天才知道的**。寫入離線特徵儲存時，時間戳要用得知的時間而不是觀看發生的時間，否則訓練資料會以為三天前就知道這件事。」

**評註**：最後一段把離線觀看連結到下一個主題——「何時得知」。這與 [Part 6](/posts/de-system-design-interview-part6-payments-ledger-reconciliation-zh/) 的業務時間與記錄時間是同一個概念，候選人能跨題目認出相同的結構。

## 六、深挖二：線上與離線特徵的一致性

> **面試官**：「你說訓練資料不能偷看未來。具體是什麼意思？」
>
> **候選人**：「訓練資料的每一列是一個過去的預測時刻：某個時間點我們向某位使用者推薦了某部影片，後來他有沒有看。這一列的特徵必須是**那個時間點當下線上實際能讀到的值**。
>
> 以『過去 7 天觀看時數』這個特徵為例。如果訓練時直接連接每日彙總表中當天的值，那個值包含了推薦發生之後的觀看——甚至包含了使用者因為這次推薦而看的那一部。模型在訓練時等於看到了答案，離線評估會非常好，上線後卻沒有這些資訊可用。」

```
profile P, feature "watch_minutes_7d" in the offline feature log

value written:      120            150              210
                     │              │                │
time ────────────────┼──────────────┼────────┬───────┼──────────────▶
                  Mon 03:00      Tue 03:00   │    Wed 03:00
                                             │
                                  label event: recommendation shown
                                  at Tue 20:15

correct join (point in time):  latest value with timestamp <= Tue 20:15 -> 150
wrong join (by calendar date): "Tuesday's value" computed Wed 03:00    -> 210
                               includes what P watched AFTER the event
```

> **候選人**：「所以離線儲存不是一張『每個實體一列』的表，而是一份只追加的紀錄：實體、特徵、值、生效時間。產生訓練資料時做的是時間點連接：對每個標籤事件，取生效時間不晚於事件時間的最新一筆。
>
> 這裡有一個容易錯的細節。每日批次特徵的生效時間，不是它所描述的那一天，而是**它被寫入線上儲存的那一刻**。星期二的彙總在星期三凌晨三點才算完並上線，所以星期二晚上的預測用到的仍是星期一的值。」
>
> **面試官**：「你怎麼確認線上與離線真的一致？」
>
> **候選人**：「最可靠的做法是在線上預測時，把實際讀到的特徵值連同請求一起記錄下來。這份紀錄就是實際發生的事，用它當訓練資料不會有時間對不齊的問題，也能拿來和時間點連接重建的結果比對，差異比例就是一致性的指標。
>
> 它的限制是新特徵沒有歷史：今天才開始記錄的特徵，要累積幾週才夠訓練。所以兩者要並用——既有特徵以線上紀錄為準，新特徵用歷史資料重建來起步，並在上線後以紀錄驗證。」
>
> **面試官**：「新特徵要回補一年的歷史，怎麼做？」
>
> **候選人**：「從 Silver 的播放紀錄以批次重算。這就是為什麼特徵要只有一份定義：如果串流版本與批次版本是兩份各自撰寫的程式，回補出來的歷史值和上線後的即時值就會有細微差異。做法是把特徵定義寫成宣告式的轉換，例如『依個人檔案、過去 7 天、加總播放秒數』，由平台分別轉成串流與批次的執行計畫。」

**評註**：時間軸圖把抽象的「資料洩漏」變成一個可以指出錯在哪一格的具體例子。「生效時間是上線的那一刻」是實務上最常見的洩漏來源。面對一致性的追問，候選人給出線上紀錄與時間點重建兩種方法及各自的限制，而不是宣稱其中一種就夠。

## 七、深挖三：實驗指標

> **面試官**：「A/B 實驗的指標管線怎麼設計？」
>
> **候選人**：「需要三份資料。分組：以個人檔案 ID 與實驗 ID 做雜湊決定組別，結果是確定性的，不需要儲存。曝光：使用者實際遇到實驗功能的那一刻記錄一筆事件。行為：就是前面的播放紀錄。
>
> 分析的對象是**有曝光的使用者**，而且只計入**首次曝光之後**的行為。被分到實驗組但從未打開相關頁面的使用者，兩組的體驗完全相同，把他們算進去只會稀釋差異。」

```
┌───────────────────┐      ┌─────────────────────────┐
│ exposures         │      │ profile_day_metrics     │
│ profile, exp,     │      │ profile, date,          │
│ variant,          │─────▶│ watch_seconds, plays,   │
│ first_exposed_at  │ join │ distinct_titles ...     │
└───────────────────┘      └────────────┬────────────┘
   on profile, date >= first exposure   │
                                        ▼
                         ┌──────────────────────────────┐
                         │ per-profile totals per exp   │
                         │ -> per-variant mean, variance│
                         │ -> sample ratio check        │
                         └──────────────────────────────┘
```

> **候選人**：「管線先產生一張『個人檔案 × 日期』的指標表，所有實驗共用。每個實驗只是把自己的曝光表連上去，先彙總到每個個人檔案一列，再算各組的平均值與變異數。先彙總到個人檔案是必要的：分組單位是個人檔案，如果直接以播放為單位計算變異數，同一人的多次播放並不獨立，信賴區間會被低估。」
>
> **面試官**：「首次曝光當天的行為怎麼處理？你的指標表是以日為單位的。」
>
> **候選人**：「這是一個真實的取捨。精確的做法是首次曝光當天回到播放紀錄層級，只計入曝光時間之後的播放，之後的日子才用彙總表。簡單的做法是從曝光的隔天開始計算，少用一天的資料但管線單純很多。我會先採用精確的做法處理第一天，因為短期實驗少一天的資料影響不小。不論哪一種，兩組必須用同一條規則。」
>
> **面試官**：「實驗設定 50/50，結果曝光的人數是 50.8% 比 49.2%。」
>
> **候選人**：「這是樣本比例不符，要在看任何指標之前先處理。在每組數百萬人的規模下，這個差距幾乎不可能是隨機造成的，代表分組或曝光紀錄有系統性的問題。常見原因是其中一組的功能載入較慢或會出錯，導致曝光事件少送；或是某一組的使用者被爬蟲過濾規則排除得比較多。
>
> 我會把這個檢查做成管線的一部分：每個實驗每天對各組人數做卡方檢定，顯著偏離預期比例時，在報表上標示警告並隱藏指標結果，因為這時的指標差異不可信。」
>
> **面試官**：「少數重度使用者每天看 16 小時，會不會影響結果？」
>
> **候選人**：「會讓平均值的變異數變得很大，實驗需要更久才能得出結論。兩個處理：先排除被判定為非人類的流量；再對每人每日的觀看時數設定上限，例如取第 99 百分位。上限要在實驗開始前決定並對兩組一致套用，而不是看到結果之後才調整。」

**評註**：候選人主動提到分析單位與分組單位必須一致、曝光與分組的差別，並把樣本比例檢查做成管線的閘門。這三點分別對應實驗分析中三種最常見的錯誤。

## 八、為什麼選 X 不選 Y

| 選擇 | 選 X 的理由 | 不選 Y 的理由 | 翻轉條件 |
|---|---|---|---|
| 串流中先彙整成播放紀錄 vs 全量保存心跳再查 | 下游資料量少 90 倍；所有消費者共用同一個觀看定義 | 每個下游各自從心跳計算，成本高且定義分歧 | 需要逐秒分析播放品質（卡頓、畫質切換）時，該用途直接讀心跳 |
| 實體鍵用個人檔案 vs 帳號 | 推薦與實驗都以個人為單位；不混雜家中不同成員的行為 | 帳號層級的特徵會把兒童與成人的喜好平均掉 | 計費、裝置數限制等帳號層級的功能 |
| 一份定義寫入兩個儲存 vs 線上與離線各自實作 | 消除兩份邏輯逐漸分歧造成的訓練與服務偏差 | 兩份實作的細微差異很難被發現，只會表現為模型效果變差 | 特徵只在離線使用（例如分析報表），不需要線上儲存 |
| 時間點連接 vs 依日期連接 | 訓練資料只包含預測當下已知的資訊 | 依日期連接會帶入事後才產生的值，造成洩漏 | 特徵不隨時間變化（例如影片的片長、類型） |
| 記錄線上實際取用值 + 歷史重建並用 vs 只用其中一種 | 紀錄提供事實與驗證基準；重建讓新特徵有歷史可用 | 只用紀錄，新特徵要等數週；只用重建，無從驗證是否一致 | 特徵數量少且穩定時，只用線上紀錄最簡單 |
| 分鐘級與每日特徵分級 vs 全部即時 | 多數特徵（長期偏好）每日更新就夠，成本低很多 | 全部即時代表每個特徵都要維護串流狀態 | 實驗證明某個特徵的新鮮度確實帶來可量測的效果提升 |
| 共用彙總表 + 曝光表 vs 每個實驗各寫查詢 | 指標定義一致；新增實驗不需要新的管線 | 各自撰寫的查詢對同一指標有不同算法，結果無法比較 | 一次性的探索分析，不作為上線決策依據 |
| 以首次曝光之後計算 vs 以分組計算 | 排除從未遇到功能的使用者，差異不被稀釋 | 以分組計算包含大量未受影響的使用者，需要更大的樣本 | 曝光本身受實驗影響（例如實驗改變了入口的可見性）時，要以分組為準以免產生選擇偏差 |

## 九、常見追問與回答要點

**「熱門新片上線，所有人都在看同一部，會有什麼影響？」**
以 `content_id` 為鍵的熱度特徵會出現熱點。做法與前幾篇相同：先在本地累計數秒再合併，並且寫入線上儲存時每個內容每隔數秒才更新一次，而不是每筆播放都寫。讀取端則是所有請求都讀同一個鍵，適合在推薦服務本地快取數秒。

**「使用者刪除觀看紀錄，要怎麼處理？」**
要傳播到四個地方：Silver 的播放紀錄、線上儲存中由它導出的特徵（重新計算或刪除）、離線特徵紀錄，以及尚未使用的訓練資料集。已經訓練完成的模型通常依既定的重新訓練週期更新，具體要求需由法遵確認。把這條傳播路徑在設計時就畫出來，比事後補容易得多。

**「線上儲存中找不到某個使用者的特徵？」**
新使用者或過期的資料都會發生。每個特徵要有明確的預設值，而且訓練時要用相同的預設值，否則又是一種線上與離線的不一致。缺值的比例要監控，突然升高通常代表寫入管線出了問題。

**「怎麼決定一個特徵需要多新？」**
用實驗決定，而不是直覺。先以每日更新的版本上線，再以較新鮮的版本做對照實驗，量測效果差異，並與維護串流特徵的成本比較。多數長期偏好類的特徵從每日提升到分鐘級幾乎沒有效益；「剛剛看了什麼」這類工作階段內的特徵則差異明顯。

**「特徵的分佈慢慢改變了，怎麼發現？」**
對每個特徵持續記錄基本統計：缺值率、平均值、分位數、類別分佈，並與訓練當時的分佈比較。上游的定義變更（例如心跳間隔從 10 秒改成 30 秒）會讓觀看時數相關的特徵一夕之間改變，卻不會造成任何作業失敗。

**「每天 5.4 TB 的心跳，成本怎麼控制？」**
原始心跳只保留七天，長期保存的是小 90 倍的播放紀錄。再進一步可以調整來源：暫停或背景時降低心跳頻率，或由播放器在本地先累計再送出。後者把彙整移到用戶端，資料量最小，但失去了伺服器端重新定義指標的能力，要權衡。

## 十、四個產業案例的對照與系列導航

本篇的前後對照，沿用前文假設；標示為目標的是設計目標。

| 指標 | 改造前（每日批次特徵） | 改造後（一份定義、兩個儲存） |
|---|---|---|
| 長期保存的觀看資料量 | 每天 5.4 TB 心跳 | 每天約 2 億筆播放紀錄；心跳保留 7 天 |
| 觀看時數的定義 | 各團隊各自計算 | 單一定義，附偏差方向與交叉檢查 |
| 特徵新鮮度 | 最長落後一天 | 工作階段類特徵分鐘級；其餘每日 |
| 訓練資料的時間正確性 | 依日期連接，有洩漏風險 | 時間點連接，並以線上紀錄驗證 |
| 線上與離線一致性 | 無法量測 | 以紀錄值與重建值的差異比例持續監控 |
| 新增一個實驗的成本 | 撰寫並驗證新的查詢 | 註冊實驗即可，共用指標表 |
| 樣本比例問題 | 靠分析者自行察覺 | 每日自動檢查，異常時隱藏指標 |

Part 5 到 Part 9 的五個案例放在一起看，會發現架構圖彼此相似，真正不同的是每一題對資料的要求。這張表可以當作拿到新題目時的定位工具。

| 案例 | 資料的性質 | 最關鍵的保證 | 這一題獨有的概念 |
|---|---|---|---|
| 點擊流（Part 5） | 量大、單筆價值低、會晚到 | 去重與依事件時間重算 | 落地與歸屬分離 |
| 支付（Part 6） | 量小、每筆都是錢 | 不可變、可對帳、可重現 | 業務時間與記錄時間 |
| 廣告（Part 7） | 量大，其中 1% 是錢 | 依用途拆分：快的近似、慢的精確 | 自帶簽章的上下文；調整項 |
| 叫車（Part 8） | 量大、只有最新狀態重要 | 寧新勿全；狀態可自我修正 | 事件流轉狀態差量；地理格網 |
| 影音（Part 9） | 量大、消費者是模型與實驗 | 時間點正確；線上離線一致 | 生效時間；曝光與分組 |

拿到任何新題目時，先問三個問題就能找到它在這張表上的位置：**單筆資料值多少？舊資料還有沒有用？消費者會不會被「當時還不知道的事」誤導？**
