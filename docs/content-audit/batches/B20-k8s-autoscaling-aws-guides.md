## Batch summary

Verdicts: **0 Ready / 5 Needs revision / 7 Not ready.** The eight-part autoscaling series is the better half: parts 1, 3, 5 and 7 have been visibly patched since first draft (Karpenter v1 `NodePool`/`EC2NodeClass`, EKS 1.33 + `KubectlV33Layer`, EKS Auto Mode GA note, VPA `InPlaceOrRecreate`, a composite-scenario disclaimer on the war stories) and those patches check out against current sources. Beyond that the series has a run of wrong-as-written artefacts a reader will copy: a Cluster Autoscaler priority-expander ConfigMap with the priorities inverted (part 2), a Fargate profile expressed as a ConfigMap (part 2), a Part 4 monitoring stack whose PVCs can never bind on the Part 3 cluster (no EBS CSI driver, no `gp3` StorageClass), `rate()` on a replica-count gauge in three different alert rules, Prometheus rules built on VPA metrics that kube-state-metrics removed in v2.9, an HPA that "scales on replication lag" and another that scales a Redis Cluster StatefulSet without resharding (part 6), a NodePool toleration for `karpenter.sh/disruption` that part 2 explicitly tells you never to add, and a Part 8 audit pipeline that tails an apiserver log file on EKS worker nodes. The four AWS "complete guides" are a different genre: each is ~70–80 % Java boilerplate (POJOs with getters/setters) around a thin feature list, with no pricing, no quotas, no limits and no "when it breaks" anywhere — none of the ALB LCU, DynamoDB RCU/WCU, API Gateway per-million or NAT Gateway figures the brief asked me to recompute exist in these posts to recompute. Their accuracy problems are structural rather than numeric: a GSI queried with `>=` on its partition key, an API Gateway whose HTTP integrations point at unroutable `.internal` hostnames and force `POST` on every method, a `ModifyTable` API that does not exist, CloudWatch metrics (`AWS/VPC NetworkPacketsIn`, `VPCPeeringConnectionState`) that do not exist, and VPC Flow Log field names that are invented. No post in the batch states a thesis.
